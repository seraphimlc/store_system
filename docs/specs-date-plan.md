# 规格 · 日期计划（半月出勤登记）

> 2026-10 交付 · 分支 `feat/date-plan`。员工在每个半月开始时登记未来半个月的可出勤情况，
> 管理员在后台看全员两周内的可出勤情况，用于分配任务。**计划只是预报，实际出勤以员工自报为准。**

## 1. 需求（用户原话归并）

- 员工在每半个月开始时做好出勤登记：每月 **3 号、18 号前**登记未来半个月的出勤设计。
- 管理员在后台能看到**所有员工两周内**的可出勤情况，便于分配任务。
- **实际出勤以自报为准**。
- 员工端：半个月的表格，**默认每天都出勤**，哪天不出勤就点选哪天。
  **叉=不出勤 / 圈=可出勤 / 方框=已出勤（已自报）**。
- 管理端：一个**大表格，行是员工、列是日期**。

## 2. 口径（已与用户确认，2026-10-01）

| 项 | 结论 |
|---|---|
| 半月划分 | **自然半月**：上半月 `1–15`（H1）、下半月 `16–月末`（H2） |
| 登记截止 | H1 → 当月 **3 号**；H2 → 当月 **18 号**（截止日当天仍算按时） |
| 逾期 | **不锁死**：过了截止日仍可登记/修改，页面提示「已逾期」；管理端可据此催办 |
| 锁定的日期 | **已过去的日期**（`< 今天`）与**已有自报的日期**（当天有每日填报记录）不可改 |
| 「已出勤（方框）」依据 | 复用现有**员工每日填报** `staff_daily_reports`（`/my/report`）：当天有记录 = 方框 |
| 业务日 | **JST**（与每日填报一致，`daily_report.jst_today()`） |
| 代填 | **不做**（管理员不代员工登记计划） |

## 3. 三态与优先级（渲染口径，唯一来源 `date_plan.cell_state()`）

| 状态 | 符号 | 判定 | 含义 |
|---|---|---|---|
| `done` | **□** 方框 | 该日有自报（`staff_daily_reports` 有行） | 已出勤（已自报）；**优先于计划值** |
| `off` | **×** 叉 | 有计划行且 `available=0` | 计划不出勤 |
| `on` | **○** 圈 | 有计划行且 `available=1` | 计划可出勤（默认） |
| `none` | **–** | 该半月**没有任何计划行**（未登记） | 管理端据此标「未提交」 |

- 优先级：`done` > 计划值 > `none`。即"已自报"覆盖计划显示。
- 管理端 `none` 用 `–` 而不是圈：**未登记 ≠ 可出勤**，避免管理员把没登记的人当成能派活。
- 管理端对「过去的日期 + 计划可出勤 + 未自报」的格子加虚线弱化样式（计划落空待核实），
  人数统计里**不计入**已过去的日期（统计的是当天及以后的可用人力）。

## 4. 数据模型

`staff_date_plans`（新增表，**不改任何现有业务表**）

| 列 | 类型 | 说明 |
|---|---|---|
| id | Integer PK | |
| person_code | String(32) FK persons.code | 员工编号（身份键，与每日填报一致） |
| plan_date | Date | 计划日（JST 业务日） |
| available | Boolean | `1`=可出勤（圈）/ `0`=不出勤（叉） |
| source | String(16) | `web`（员工自助）/ `admin`（预留） |
| created_at / updated_at | DateTime | |

- 唯一约束 `uq_sdp_person_date`：`(person_code, plan_date)`（一天一条，重复提交=覆盖）。
- 索引 `ix_sdp_date`：`plan_date`（管理端按日期段取全员）。
- **不存 period_key**：半月归属由 `plan_date` 现算（规则若调整，历史数据不产生歧义）。
- 「该半月是否已登记」= 该人在 `[start, end]` 内是否存在计划行（无需单独的提交表）。

## 5. 服务层 `app/services/date_plan.py`

| 函数 | 作用 |
|---|---|
| `period_key(d)` / `period_bounds(key)` | 日期 ↔ `YYYY-MM-H1/H2`；返回 `(start, end, deadline)` |
| `current_period(today)` / `period_options(today, back=2, fwd=1)` | 默认半月 / 可选半月列表（含是否逾期） |
| `is_locked(db, person_code, d, today)` | 过去了 或 已自报 → 锁定，返回原因（`past` / `reported`） |
| `plan_days(db, person_code, key, today)` | 员工端逐日视图（三态 + 可改/锁定原因 + 星期） |
| `save_plan(db, user, key, unavailable_dates, today)` | 提交/修改：**只写未锁定的日期**，其余保持原值 |
| `is_submitted(db, person_code, key)` | 该半月是否有登记行 |
| `admin_matrix(db, key, today)` | 管理端矩阵：逐员工逐日三态 + 未提交标记 + 按日可出勤小计 |
| `plan_xlsx(db, key, today)` | Excel 导出（员工 × 日期，符号与页面一致） |

关键实现约定：

- `save_plan` **先锁定、后写入**：锁定日期既不新增也不改写（用户明确"历史与已自报的事实不覆盖"）。
  一个半月的日期全被锁定时报错「该半月的日期都已过去或已自报」。
- 表单只提交**不出勤**的日期集合（`unavailable` 多值），其余按默认 `available=1` 落库；
  这样"默认每天都出勤"是数据层事实，不靠前端 JS 兜底。
- 截止日判断用 `deadline`（H1=3 号 / H2=18 号），**逾期只提示不拦截**。

## 6. 路由与页面

| 页面 | 路由 | 说明 |
|---|---|---|
| 员工端·出勤计划 | `GET /my/plan?period=` | 半月表格；`POST /my/plan` 提交（303 + `?msg/err`） |
| 管理端·日期计划 | `GET /staff-plans?period=` | 员工×日期大表格；`GET /staff-plans/export?period=` 导出 xlsx |

- 员工端 `/my/plan` 进 `main.py` 的 `STAFF_ALLOWED` 白名单，并加**底部 tabbar 第 4 项「出勤计划」**。
- 管理端顶部导航加「日期计划」（紧随「填报与对比」）。
- 权限：员工页 `role != staff → /login`；管理页 `role != admin → /my/perf`（与既有页面一致的双层防御）。
- 表单走全站一次性令牌 `{{ form_token() }}` + `csrf_token`。
- 员工端页面自带图例（×/○/□），并在截止日后显示「已逾期」提示；已提交显示提交时间。

## 7. 边界与坑

- **H2 长度随月份变化**（28–31 天中的 16–月末 → 13–16 天），表格列数按 `period_bounds` 现算，
  不写死 15。
- **跨月的 H1/H2** 不跨月（自然半月），表格永远落在同一个自然月，表头月份清晰。
- 员工编号需绑定（`user.person_code`），未绑定 → 拒绝（与每日填报同一条约束）。
- 每日填报的**锁定规则不同**：自报锁在"已对账"（正式数据覆盖），计划锁在"已过去/已自报"，
  两者不要互相套用。
- 管理端列多（16 列）→ 外层 `.tbl-wrap` 横向滚动，≤760px 首列 sticky（现有 H5 规范）。

## 8. 测试

`tests_web/test_date_plan.py`：

- 半月划分：月初/月末/2 月/大小月/H2 天数/截止日；key 往返。
- 数据层：`(person_code, plan_date)` 唯一。
- 三态优先级：自报覆盖计划值；未登记 = `none`。
- 锁定：过去的日期不改、已自报的日期不改、未来日期可改；全锁 → 报错。
- 默认值：只提交"不出勤"集合时其余全为可出勤；重复提交=覆盖（不产生重复行）。
- 管理端矩阵：未提交标记、按日可出勤小计、过去日期不计入统计。
- 路由：员工页渲染 / 提交 / 未登录跳登录 / 员工访问管理页被拦 / 管理员访问正常；
  导出 xlsx 内容与矩阵一致。
