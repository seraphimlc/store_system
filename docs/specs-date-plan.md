# 规格 · 日期计划（半月出勤登记）

> 2026-10 交付 · 分支 `feat/date-plan`。员工在每个半月开始时登记未来半个月的可出勤情况，
> 管理员在后台看全员两周内的可出勤情况，用于分配任务。**计划只是预报，实际出勤以员工自报为准。**

## 1. 需求（用户原话归并）

- 员工在每半个月开始时做好出勤登记：每月 **3 号、18 号前**登记未来半个月的出勤设计。
- 管理员在后台能看到**所有员工两周内**的可出勤情况，便于分配任务。
- **实际出勤以自报为准**。
- 员工端：半个月的表格，**默认每天都出勤**，哪天不出勤就点选哪天。
  **叉=不出勤 / 圈=可出勤 / 方框=已出勤（已自报）**。
- 管理端：一个**大表格，行是员工、列是日期**。

## 2. 口径（已与用户确认，2026-10-01）

| 项 | 结论 |
|---|---|
| 半月划分 | **自然半月**：上半月 `1–15`（H1）、下半月 `16–月末`（H2） |
| 登记截止 | H1 → 当月 **3 号**；H2 → 当月 **18 号**（截止日当天仍可提交） |
| **填报窗口** | **提前 7 天开放，到截止日为止**：H1 = 上月 **24 号**~本月 3 号；H2 = 本月 **9 号**~18 号（2026-10-01 用户确认） |
| 窗口外 | 不能提交（`WindowClosed`）：没开 → 页面提示"X 起开放"；已关 → 无法再补登记，**没填的按"未填默认"处理**（老员工→不出勤，本期新入职→可出勤，见 §3.1） |
| 锁定的日期 | 窗口内，**已过去的日期**（`< 今天`）与**已有自报的日期**不可改 |
| 「已出勤（方框）」依据 | 复用现有**员工每日填报** `staff_daily_reports`（`/my/report`）：当天有记录 = 方框 |
| 业务日 | **JST**（与每日填报一致，`daily_report.jst_today()`） |
| 代填 | **不做**（管理员不代员工登记计划） |
| 窗口关闭后未登记 | **未填默认**：老员工 → **不出勤（浅色 ×）**；本期新入职 → **可出勤（浅色 ○）**（见 §3.1） |
| 待填报提示 | **窗口开着且本期未登记** → 员工端**弹窗提示**（可「稍后再说」）+ 出勤计划 tab 红点 |
| 登录落点 | 同上条件成立 → 第一个页面 = `/my/plan`（填报页）；否则 = `/my/report`（每日自报） |
| 管理端表格 | **不要"登记"列、不要未提交人名清单**：登记过的行有实色标记，没登记的行是 `–`/浅色 ○（2026-10-01 用户要求） |

- 窗口互不重叠（3 日关 → 9 日开；18 日关 → 24 日开），所以同一时刻**最多一期可填报**；
  4–8 号、19–23 号是"没有可填报期"的间隙（此间不催办、不弹窗，页面提示下个窗口）。

## 3. 三态与优先级（渲染口径，唯一来源 `date_plan.cell_state()`）

| 状态 | 符号 | 判定 | 含义 |
|---|---|---|---|
| `done` | **□** 方框 | 该日有自报（`staff_daily_reports` 有行） | 已出勤（已自报）；**优先于计划值** |
| `off` | **×** 叉 | 有计划行且 `available=0` | 计划不出勤 |
| `on` | **○** 圈 | 有计划行且 `available=1`，或"本期新入职没填 → 按可出勤" | 可出勤（默认） |
| `none` | **–** | 该半月**没有任何计划行**（未登记），且还没过截止日 | 还没登记（窗口未关） |

- 优先级：`done` > 计划值 > 未填默认（老员工不出勤 / 新入职出勤）> `none`。
  即"已自报"覆盖一切，登记过的计划不被默认值改写。
- 管理端 `none` 用 `–` 而不是圈：**未登记 ≠ 可出勤**，避免管理员把没登记的人当成能派活。
- **未填默认的格子是浅色**（`.c.assumed`，灰色细体）：管理端一眼分清"他亲手登记的" vs "没填、按默认算的"
  （浅色 ○ = 新入职按可出勤；浅色 × = 老员工按不出勤）。
- 人数统计里**不计入**已过去的日期（统计的是当天及以后的可用人力）。

### 3.1 窗口关闭后没填 → 未填默认（2026-10-01 用户口径，同日改过一次）

> 最初口径是"没填 → 默认全部出勤"；2026-10-01 用户改为：
> "对于老员工，3 号前还没填报计划的，默认全部不出勤——因为可能要离职了；正常的员工都是会填报的。"

`unfilled_default(key, today, roster_start)` 返回 `""` / `"on"` / `"off"`：

| 情况 | 没填的那天按什么算 | 理由 |
|---|---|---|
| **还没过截止日**（今天 ≤ 3 号 / 18 号） | `""`（不猜）→ 仍是 `–` 未登记 | 还来得及填，不能替他做主 |
| **老员工**（名册起点 ≤ 该期窗口关闭日：本来有机会填却没填） | **`off` 不出勤** → **浅色 ×** | 用户："可能要离职了；正常员工都会填" |
| **本期新入职**（名册起点晚于窗口关闭日：还能补填，见 §4.3） | **`on` 可出勤** → **浅色 ○** | 他刚来、正在补填，别当成旷工；管理员催他尽快填 |

- **只对"今天及以后"生效**：过去的日期看事实（有自报 □ / 没自报 ×），**不追认**默认值，
  否则历史格子会凭空变化。
- **登记过的人不受影响**：他亲手标的不出勤仍是不出勤，标的出勤仍是出勤（默认优先级最低）。
- **统计口径**：「计划出勤」只算"计划里标了可出勤 + 新入职默认出勤"的人，**不含**默认不出勤的老员工；
  「未登记人数」= **那天还没填计划的人数**（今天及以后，含按默认算的）——所以"谁没填"这个信号一直在，
  管理员可以据此去催办，不会因为"变成 × 了"而看不出来。
- 管理端图例给出两个浅色项：`浅色 ○ 未填·按可出勤（新入职）`、`浅色 × 未填·按不出勤（老员工）`；
  导出说明行同样写明。测试：`test_unfilled_default_old_staff_off_new_hire_on`、
  `test_admin_matrix_default_all_after_deadline`。

### 4.2 过去的日子看事实（2026-10-01 用户口径）

- 用户例子："今天是 10-04，小川逸 10-03 计划出勤但没自报 → 那一天显示 ×"。
- 规则：`d < 今天` → **有自报 □，没自报 ×**（**计划值不再参与显示**；
  过去也**不启用**"未填默认"）。
- 影响：过去的格子**不存在**"未登记 `–`"这一态，也不计入"未登记人数"；
  "未登记人数"因此只统计今天及以后（`none_cnt`）。
- 员工端同口径（同一 `cell_state`），行内提示"未自报（按不出勤）"，避免两端显示打架。
- **"今天"这一列仍显示计划值**（2026-10-01 用户确认：`今天` 不按事实，次日 0 点起才变 ×）。
  依据：线上实测自报集中在 **JST 16:16–22:54** 提交（当天早上还没人报），
  若当天就按事实显示，上午整列会是 ×，管理员会误以为"今天没人能来"。
  锁定测试：`test_today_keeps_plan_until_next_day`（10-01 看=○，10-02 看=×）。

### 4.3 新入职员工（2026-10-01 用户口径）

用户口径："不用关心入职日，就以填报当天为入职日就行。之前的日期也不需要计划。
如果入职日[是]未来的某一天，那今天愿意咋填就咋填。这个只是个计划而已。"

- **名册起点**（≈入职日，`roster_start_map()`）= 他**最早在系统里出现的那天**（JST）：
  员工账号创建日 / 人员记录创建日 / **首次计划日** 三者取最早。**不人工维护、不加字段**。
  报过自报的人一定有计划行（自报写透），所以**不用查 `staff_daily_reports`**（"渲染路径只读计划表"
  的约定不破）；查询全是单表聚合，**无 join**。
- **入职前的格子留空**（新状态 `STATE_NA = "na"`，"不在职"）：既不算"没出勤 ×"也不算"未登记 –"，
  且**不计入** 计划出勤 / 实际出勤 / 未登记 三个统计行
  （改之前会显示成 × ——等于把没入职的日子算他旷工，是错的）。
  员工端那一行写"不在职（入职前）"；导出留空；矩阵格子 title 写"不在职（X 起）"。
- **新人补登当期**（`personal_window_state()` / `is_late_join()`）：名册起点**晚于该期窗口关闭日**的人，
  该期对他**重新开放到期末**（10-06 入职 → 可填 10-06 ~ 10-15）；期已过完则不特批。
  `save_plan` 走这个"个人窗口"，`needs_plan` 也认这条 →
  **登录就弹窗催他填本期**；员工页状态条显示「你是本期新入职的：可以补登本期到 X 为止」，
  页面默认期 = 本期（`default_period_for()`）。
- **老员工不受影响**：窗口关了照旧 `WindowClosed`；入职后的过去日子照样按事实（□/×）显示。
- 锁定测试：`test_roster_start_takes_earliest_appearance`、
  `test_matrix_blanks_days_before_roster_start`、`test_new_hire_can_backfill_current_period`、
  `test_employee_page_late_join_banner_and_na_rows`、
  `test_matrix_marks_before_start_blank_in_export`。

### 4.4 不在职（停用/离职）员工（2026-10-01 用户口径）

用户口径："对于不在职的员工：1. 如果没有本期数据的就过滤掉，不需要出现。
2. 有本期数据，过去的日期该啥样是啥样，往后的日期全部是叉。"

- **不在职 = 有员工账号但 `can_login == False`**（`status` 不是 `active`/`leave`，即 `resigned` 离职 /
  `disabled` 停用）。没账号的人（只有计划行）**不当作不在职**，避免误判。
- **规则 1（过滤）**：不在职且**本期一条数据都没有**（没有计划行/自报行）→ **不进矩阵**
  （`_matrix_people` 本来就只把"在岗/请假"放进候选，有数据的才补进来；现已被测试钉住）。
- **规则 2（今天及以后全 ×）**：不在职的人**过去**的格子照旧按事实（□ 有自报 / × 没自报），
  **今天及以后一律 ×**（`cell_state(..., inactive=True)`；不再显示"默认出勤 ○"，也不再是 `–`）；
  他们**不计入「计划出勤」**，也不算「未登记」。行名淡色 + 悬停提示「停用/离职：今天及以后按不出勤」。
- **顺手修的相关项**：整行都落在"入职前（`na`）"的人 = 这一期跟他毫无关系 → 整行不显示
  （否则 9 月视图里会挂着一排 10 月才入职的空行）。
- 测试：`test_matrix_hides_inactive_without_period_data`、
  `test_inactive_employee_future_days_all_off`、`test_matrix_hides_rows_entirely_before_roster_start`。

## 5. 服务层 `app/services/date_plan.py`

| 函数 | 作用 |
|---|---|
| `period_key(d)` / `period_bounds(key)` | 日期 ↔ `YYYY-MM-H1/H2`；返回 `(start, end, deadline)` |
| **`period_window(key)`** | 填报窗口 `(期首 − 7 天, 截止日)` |
| **`window_state(key, today)` / `is_window_open`** | `before` / `open` / `closed` |
| **`open_period(today)` / `default_period(today)` / `next_window(today)`** | 正在可填报的那一期 / 页面默认展示的那一期 / 下一个窗口 |
| `current_period(today)` / `period_options(today, back=2, fwd=1)` | 本期 / 可选半月列表（含窗口状态） |
| `is_locked(db, person_code, d, today)` | 过去了 或 已自报 → 锁定，返回原因（`past` / `reported`）——**单表判定** |
| `plan_days(db, person_code, key, today)` | 员工端逐日视图（三态 + 窗口状态 + 可改/锁定原因 + 星期） |
| `save_plan(db, user, key, unavailable_dates, today)` | 提交/修改：**先查窗口**，再**只写未锁定的日期** |
| `is_submitted(db, person_code, key)` | 该半月是否有**登记行**（`source != 'report'`） |
| **`mark_reported(db, code, date, flag)`** | **自报写透**：改/插计划行的 `reported`（每日填报调用） |
| **`rebuild_reported(db, ...)`** | 按 `staff_daily_reports` 重建 `reported`（修复工具，迁移/清理脚本用） |
| `needs_plan(db, person_code, today)` | **现在是否还需要填报**（窗口开着 且 未登记）；返回该期信息或 `{}` |
| `staff_home(db, user)` | **员工登录后第一个页面**（单一来源）：待填报 → `/my/plan`，否则 → `/my/report`，无编号 → `/my/perf` |
| `assumed_default(d, today, deadline)` | 底层日期判定：该日是否落在"窗口已关 + 今天及以后"（默认值的生效区间） |
| `unfilled_default(key, today, roster_start)` | **没填时按什么算**：`""` 不猜 / `"on"` 新入职按可出勤 / `"off"` 老员工按不出勤 |
| `admin_matrix(db, key, today)` | 管理端矩阵：**只查计划表**，逐员工逐日状态 + 逐日"是否默认出勤" + 按日小计 |
| `plan_xlsx(db, key, today)` | Excel 导出（照"排班计划"版式，见 §6.2） |

关键实现约定：

- `save_plan` **先查窗口、再锁定、后写入**：窗口没开/已关 → `WindowClosed`；
  窗口内已过去/已自报的日期既不新增也不改写（用户明确"历史与已自报的事实不覆盖"）；
  整期都锁定时报错 `AllLocked`。锁定判定只看**本行**的 `reported`（不查自报表）。
- 表单只提交**不出勤**的日期集合（`unavailable` 多值），其余按默认 `available=1` 落库；
  这样"默认每天都出勤"是数据层事实，不靠前端 JS 兜底。

### 6.0 员工端交互：15 天顺序表，整行点一下切换（2026-10-01 用户口径）

- 员工页就是**一条一天、从上到下排的半月列表**（H1 15 条、H2 13–16 条，条数按 `period_bounds` 现算）。
- **默认全是"可出勤"**；**点一下那天 → 不出勤**；**再点一下 → 变回可出勤**；点完直接保存。
- **版式（2026-10-01 二次评审后改的，用户："不太好看呢"）**：
  1. 每行左侧一条**状态色条**（可出勤=绿 / 不出勤=红）；
  2. 中间是**日期 + 星期**（上下两行，不占宽）；
  3. 右侧是**开关组件（switch）**：状态文字（可出勤=绿 / 不出勤=红）+ 一个 50×28 的圆角滑块——
     **开=可出勤（绿色、滑块靠右，默认）**，**关=不出勤（红色、滑块靠左）**；
     比"圆圈 + 文字"和"两个选项的分段控件"都更直观（2026-10-01 用户要求"做成一个开关组件"）；
  4. **"今天"不再打标记**（用户明确），日期行保持干净；
  5. 顶部不再堆图例与长句，只留一个**窗口状态条 + 一行摘要**
     （`期内 10-01 ~ 10-15 · 已登记/未登记 · 计划出勤 N/15 天 · 已自报出勤 M 天`）。
- 实现仍是**纯 CSS**（不依赖 JS，CDN 不可达也能用）：
  整行 `<label class="pickrow">` 包住隐藏的 `<input type="checkbox" name="unavailable">`
  （`position:absolute; opacity:0`，**仍在表单里**）；
  开关用兄弟选择器驱动：`input:checked ~ .sw-wrap .sw{background:红}` 与
  `.sw i{left:3px}`（滑块左移）；状态文字用 `input:checked ~ .sw-wrap .sw-txt.off{display:inline}`；
  左侧色条用 `input:checked ~ .bar`。`<input role="switch">` 让读屏软件也读成开关。
- 不可点的行（已过去 / 已自报 / 窗口未开或已关）**不渲染 checkbox**，用 `.pickrow.static`

### 6.1 员工落点与待填报提示（2026-10-01 用户补充）

- **落点**（`date_plan.staff_home`，三处共用同一函数，避免规则漂移）：
  ① 登录 POST（`next` 为空或 `/` 时）；② `GET /` 根跳转；③ 中间件把员工从非白名单页拦回时。
  - **窗口开着且待填报** → `/my/plan`；否则 → `/my/report`（每日自报）；未绑定编号 → `/my/perf`。
  - **首登/口令被重置**优先：登录后直接进 `/my/password?must=1`（不必先跳一次再被中间件拦住）。
  - 带 `next=` 的深链（如 OAuth `/oauth/authorize`）**不覆盖**员工落点，尊重原跳转。
- **弹窗**：中间件每个员工请求算一次 `request.state.plan_pending`，`base.html` 据此渲染弹窗
  （`data-testid="plan-prompt"`，写明填报期到哪天，「去登记」+「稍后再说」）；
  **`/my/plan` 页自身不弹**（正在填）。窗口间隙不催办（没有可填报的期）。
  用 Alpine `x-data` 但**不加 `x-cloak`**：没有 JS 时弹窗照样可见（只是「稍后再说」关不掉），
  避免 CDN 不可达时员工看不到提示。
- tab 角标：待填报时「出勤计划」tab 显示红点（弹窗被关掉后仍留提示）。
- 中间件由此**只开一次 DB 会话**（原先 must_change_password 与白名单检查各开一次），顺带跳过了 `/static`。

## 7. 边界与坑

- **H2 长度随月份变化**（28–31 天中的 16–月末 → 13–16 天），表格列数按 `period_bounds` 现算，
  不写死 15。
- **跨月的 H1/H2** 不跨月（自然半月），表格永远落在同一个自然月，表头月份清晰。
- 员工编号需绑定（`user.person_code`），未绑定 → 拒绝（与每日填报同一条约束）。
- 每日填报的**锁定规则不同**：自报锁在"已对账"（正式数据覆盖），计划锁在"已过去/已自报"，
  两者不要互相套用。
- 管理端列多（16 列）→ 外层 `.tbl-wrap` 横向滚动，≤760px 首列 sticky（现有 H5 规范）。
- **员工落点规则一变，"员工访问管理端被拦"的去向也跟着变**：`test_permission(s)` /
  `test_accounts_export` / `test_report_admin_edit` / `test_token_pages` 里断言 `/my/perf`
  的地方已统一宽松为「员工首页之一」（`/my/plan`、`/my/report`、`/my/perf`）。
- 中间件给每个员工请求多算一次 `needs_plan`（一次索引查询）；`/static` 已跳过。
- **"提前 7 天"的算法**：`期首 − 7 天`（H1 = 上月 24 日）——**不是 25 日**，
  写成 25 会少一天（测试 `test_save_plan_rejects_outside_window` 锁边界）。
- **窗口有间隙**（4–8 号、19–23 号没有任何可填报期）：此时 `needs_plan` 为假 →
  不弹窗、登录直接进自报页，员工页/管理端提示"下个填报期 X 开放"。
- **路由测试要冻结"日期计划的今天"**（`frozen` fixture：`monkeypatch.setattr(date_plan,
  "jst_today", ...)`），否则落点/弹窗用例会随真实运行日期（尤其间隙日）飘红。
- **反范式的代价**：`reported` 是自报的副本 —— 直接改 `staff_daily_reports` 的旁路
  （历史脚本 / 手工 SQL）不会自动同步；要么走 `daily_report` 的 4 个入口，要么跑
  `date_plan.rebuild_reported(...)`。渲染路径**故意不查自报表**（用户要求避免关联查询）。
- **过去的日子没有 `–`**：`none_cnt` 只统计今天及以后，别拿它当"历史未登记"用。
- **写透是 best-effort**：同步失败只 rollback 计划表那一步（`_sync_plan_reported` 捕获异常），
  填报本身照常成功 —— 代价是极端情况下会漏一次 □，可用 `rebuild_reported` 补。
