- **几何法兜底（2026-10-05 用户："补上也行。补吧，不过别太勉强"）**：

    串不全的线（有分叉/复线）放宽到"串起 ≥50% 段"但**仍要求每站贴得上**，否则**宁可空着并如实报出来**。

**实测口径**：队长 `/my/tasks?tab=unassigned`（本队 76 条任务、82 行车站池）——
**188 条 → 30 条 → 22 条**（`can_reject_maps` 批量权限是 188→30 那一步）。

**22 条的构成（打印真实 SQL 归类）**：
- **每请求基座 ~8 条**（跟页面无关）：登录用户 1、身份快照 1（只取 role/lang/status/person_code/
  must_change_password 这几列，给中间件判语言/待改密/越权/待填计划）、名册起点 1（三个标量子查询合成
  一条）、未读消息 COUNT 1、能力表 1、表单令牌 INSERT 1~2。
- **页面数据 ~14 条**：`bd_task` 1（本队任务）、`bd_station_place`+`bd_station` 2（车站/线路名）、
  `bd_task_assign` 2（我担当的 + 本页担当）、`bd_task_progress` 1（最新进展）、`bd_team` 2、
  `bd_team_member` 2（我是不是队长 + 成员列表）、`users(status)` 2（候选人是否请假/离职）、
  `staff_date_plans` 1、`bd_staff_leave` 2（我休假 + 候选人假期）。
- **全部是常数条**（跟 76 行、515 行无关）——原来 188 条是 N+1（每行查一次权限），这才是病根。

**本轮去掉的重复**：登录用户 3 次→2 次（快照+ORM 对象）、最新进展 2→1、`leader_teams` 2→1、
可用性同日期 2→1、名册起点 3 条 SQL→1 条。

⚠️ **踩到的坑（重要）**：一开始为了省查询，让 `current_user` **复用中间件缓存的 ORM 对象** →
中间件用的是**另一个已关闭的 session**，对象处于 detach 状态 → 路由里改 `user.password_hash`
再 commit **静默不生效**（`test_permission` 等 3 个测试红）。修法：中间件只传**身份快照**
（`SimpleNamespace`，列值），ORM 对象仍由 `require_login` 在本请求 session 里取。
**结论：跨 session 传 ORM 对象是雷；要传就传值。**
