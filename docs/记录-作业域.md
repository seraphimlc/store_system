### 域边界 · 角色 · 队长同步

- **域边界（铁律）**：只新增/只写 `bd_*` 表，**绝不碰结算域四表**、不读 `raw_records`。
  **唯一例外** `app/services/bd_store.py`（门店宇宙）**只读** `raw_records` 建 `bd_store`，不写结算域任何表。
  只读不写的还有 `staff_date_plans` / `users`（派工提醒用）。守门测试
  （`test_station_tasks_does_not_touch_settlement_tables` / `test_settlement_code_never_reads_ops_domain` /
  `test_progress_submission_only_writes_bd_tables`）见 `AGENTS.md` 铁律 1–2。
- **角色三档**：`admin` / **`leader`（新）** / `staff`。落点**唯一来源** `app/services/home.py::landing_home()`：
  admin→`/dashboard`、leader→**`/my/tasks`**、staff→`date_plan.staff_home()`。
  ⚠️ **加第三角色会死循环**（`/ → /dashboard → _denied() → /login → /`）；修法是 `auth_r` 的 `GET /`、
  **`GET /login`（关键那一环）**、登录 POST 三处都走 `landing_home`；各 router 的 `_denied()` 保持 `/login`。
- ⚠️ **队长角色必须自动同步（否则必踩）**：`bd_teams.sync_account_roles()` —— 现役队长 → `users.role` 升 `leader`；
  不再带任何队 → 退回 `staff`（**只动 staff/leader，绝不动 admin**）。`set_members` 保存成员后自动调用。
  不同步的实测后果：只在团队表里指定队长 → 队长登录进的是**队员视图**（`/my/tasks` 0 行、没有 tab）。

### 表 · 状态机 · 权限

- **表（6 张，迁移 `b2c3d4e5f6a7`）**：`bd_team` / `bd_team_member`（成员含历史，移出写 `end_date` **不删行**）/
  `bd_station`（车站主数据，`name_norm` 判重）/ **`bd_task`（1 站 1 任务：`team_id` + `assign_date` + `state` + `pct`）** /
  `bd_task_assign`（担当 **≤2 人**，必须是该队现役成员）/ `bd_task_progress`（**每日一条** `UNIQUE(task_id, date)`，当天可改=覆盖）。
- **状态机（唯一口径 `bd_tasks.recompute_state`）**：没担当→`unassigned`；有担当**或已有进度**且 `pct<100`→`doing`；
  `pct=100`→`done`。pct 夹在 0–100；**当前进度冗余在 `bd_task.pct`**（列表直读）。
  ⚠️ "有进度也算进行中"是修过的：旧口径只看担当 → "pct=30 却显示未分配"（队长自己开工、还没分人时踩到）。
- **开始日 / 完成日**（`bd_task.start_date`/`done_date`，迁移 `c1b2a3d4e5f6`）：首次提交=开始、`pct=100`=完成、
  **回退清完成日**；管理端 / 导出 / 队长页都显示。
- **进度审核列**：`reported_pct`（**员工原值，永不覆盖**）/ `reported_by` / `review_status(pending/confirmed/adjusted/rejected)`
  / `reviewed_by` / `reviewed_at` / `review_note`；`pct` = 当前生效值 → 能展示"队员报 80%（已调成 70%）"。
- **权限**：`can_report`（管理员 / 该任务队长 / **本人是担当**）、`can_assign`、`can_adjust`（管理员 / 该任务队长，
  走 `bd_teams.is_leader_of`）。队员**能上报自己担当的**（有滑动条），不能分派、不能碰别人的。
  **换队 `set_task_team` 会清空原担当**。列表批量判权用 `bd_tasks.can_reject_maps`（常数条 SQL，别在循环里调 `can_*`）。
- **页面**：管理端 `/teams`（+`/teams/{id}` 圈人）、`/stations`、`/tasks`；员工端 `/my/tasks`（**同一页**：
  队员=我的任务+上报；队长=多出 tab + 分派/调整）。导航：`base.html` 管理菜单 gate 看 `role == 'admin'`，
  底部 tabbar 对 `staff`+`leader` 都显示并新增「任务」。
- **日志 `bd_log`（一张通用追加表，只写不改不删）**：domain(task/team/member/station) + ref_id + **ref_label 冗余可读**
  + action + field + old→new + actor/actor_name + created_at。⚠️ 价值点：**每日进展表会被覆盖，日志不会**
  —— "员工报 40% → 队长改 60%"查得到。查看：`/tasks/{id}` 详情（可见=管理员/该队队长/担当）+ 管理端 `/logs`（队长只看本队相关）。
- **权限表 `bd_role_cap`**：`(role, capability) → allowed`，9 个能力；**判权与页面按钮共用一份**
  （`app/services/bd_perm.py`；表为空回退 `DEFAULT_CAPS`，**读路径不写库**）。
- **队员状态直接用员工状态**：`bd_team_member` **不另造状态**；`team_members()`/`person_options()` 带出 `users.status`
  （在岗/请假/停用/离职/未开通账号）。**离职/停用不能派工**（`assign_members` 拒绝 + 候选不列出），成员记录保留、任务可改派；
  **移出成员时若他还有未完成任务 → 提示，不自动改派**。
- **任务名先用车站名**（不加独立字段）；**任务编号不显示**（任务页/详情页/车站页都没有编号列，只有表单隐藏字段 `task_id`）。

### 一人一队（死规定）+ 两个唯一约束

> 用户 2026-10-03："不存在跨队借调的情况。只有转出再转入。**这是死规定**。"→ 已钉到数据库层。

- **`uq_bd_team_member_active_person`**：`person_code` 在 **`end_date IS NULL`** 上唯一（部分唯一索引，SQLite/PG 支持；
  MySQL 跳过、靠服务层）。任何代码路径 / 手工 SQL / 并发想让一人同时在两队 → **IntegrityError**；
  `set_members` 捕获它转成一句人话（"保存冲突：有人刚被别的队圈走了…"）而不是 500。
  → `leader_teams()` 复数（一人带多队）与跨队担当**都不可能再发生**。
- **`uq_bd_team_member(team_id, person_code, start_date)`**：历史行的唯一键 —— ⚠️ **它是"移出又加回"事故的根因**
  （同一天移出再加回会撞键，`bd_teams.py` 里专门有识别这两种约束的分支）。
  **调人流程：原队取消「进队」保存 → 新队再圈进来。**
- 圈选候选 = **本队现役成员 + 自由人**；已在别队的人**不显示**（提示行给出被隐藏人数 `data-testid="n-elsewhere"`）。
  `person_options(db, team_id=...)` 传 `team_id` 才过滤（不传=老行为）；唯一判据 `bd_teams.active_team_of()`。
  **写入端也拦**（`set_members` raise「这些人已在别的队…」）—— 界面隐藏只是第一层，构造 POST 仍可绕。
- 自检 `scripts/check_single_team.py`（只读，有违规则非 0 退出，可当发布验收）：一人多队 / 悬空担当 / 无队长的队 / 索引是否存在。

### 假期模式（休假期 · 跨域只读）

- **`bd_staff_leave`（休假期，迁移 `a3b4c5d6e7f8`）**：`end_date` 空 = 未定；**一人同时只有一条 `active`**
  （新开 → 旧的自动 ended 并把 end_date 收到新开始日前一天）。员工端入口 = **出勤计划页顶部「假期模式」卡片**
  （开启/结束；**结束 = 从当天起不算休假**）—— **不做第 5 个 tab**（H5 底栏只有 4 项，且它与出勤计划同源）；开/结束都写 `bd_log`。
- **可用性检查唯一入口** `bd_leave.availability_map(db, codes, date)`（**页面与写端点共用**）：离职/停用 → **block**；
  休假期覆盖该日 / `users.status=请假` / `staff_date_plans` 该日不出勤 → **warn**。**只提醒不阻断**：`assign_members` 返回 `warnings`，
  队长端分派后消息追加「⚠️ 汤静：休假中（至 X）」，**分派照旧成功**；只有离职/停用仍 raise。
- ⚠️ **提醒看哪一天 = `max(分配日期, 今天)`**（任务没开始看开始那天；已开始/过期看今天）—— 否则拿过期分配日期判断，
  提醒永远落不到点上。候选旁打 `休假/计划休/请假` 标签；管理端 `/tasks` 担当后标「休」；员工端 `/my/tasks` 有休假横幅。
- **开假会自动标出勤计划**：`staff_date_plans` 加 `leave_id` + `source='leave'` → 管理端矩阵那几天就是 ×
  （**不做"谁在休假"一览页**，用户说"不要看"），`title` 标「（假期模式）」区分"休假"与"自己点的不出勤"。
  **三条"不抢"规则**：今天之前不标（过去看事实）/ 已自报的不标 / **员工自己点的 × 不认领**。
  **结束或替换休假 → 按 `leave_id` 精确撤销**：`reported=False` 的行删掉（恢复默认规则，不伪造"已登记"），`reported=True` 只解绑保留事实。
- **表的主人仍是日期计划模块**：新增 `app/services/plan_leave.py`（`apply_leave`/`clear_leave`），作业域**调用它**而不是自己
  `StaffDatePlan.add/delete`。**跨域只读**：作业域只读 `staff_date_plans`/`users`（派工提醒），**绝不写**；写只写 `bd_staff_leave`。
  守门测试 `test_availability_reads_never_write`（可用性检查**一个表都没碰**）。
- ⚠️ **顺带修真问题**：`/my/plan` 原 `role != "staff"` → **队长进不去出勤计划页**（与"队长也是员工"矛盾）→
  改为 staff/leader 都能用，并把 `/my/leave` 加进中间件白名单。

### 表格 / 表单 / 分页（硬规矩）

- **表格必须 `class="grid-tbl"` + 外层 `.tbl-wrap`**：`app.css` **没有通用 `table` 规则**，样式全挂 `table.grid-tbl`
  （内边距/行分隔线/表头底色+**粘性表头**/悬停/窄屏首列吸附）→ 裸 `<table>` 会渲染成"没边框没内边距、挤成一坨的文字"。
  守门测试 `test_ops_tables_use_grid_tbl`（作业域模板里出现无 class 的 `<table>` 直接红）。
- **「圈选队员」标准结构**：`筛选(label.f)` → `.form-actions`（保存成员/全不选/已勾选计数）→
  `.tbl-wrap > table.grid-tbl`（全页滚动，**不用嵌套滚动区**）→ 两条说明；只有
  `.pick-cell { width:3.6rem; text-align:center }` 一个自定义类（进队/队长两列窄且居中）。
  ⚠️ **教训：新页面优先复用既有组件与既有页面版式**，别自创滚动容器/工具条（`.pick-bar`）/整行染色（`tr.picked`）/彩色药丸
  （守门测试 `test_team_detail_pick_table_plain` 反向断言这些**都不存在**）。
- **指定队长是两步**：勾「进队」+ 点该行「队长」。旧实现只遍历 `person` → 只点「队长」不勾「进队」会**静默丢弃**；
  已两端修：① 点「队长」**自动勾上「进队」** ② 后端把 `leader` 里的人**兜底并进 entries**（JS 没跑也不丢）。
- **表单 / 筛选行一律照抄既有写法**：`<div class="card"><form class="form-grid">` + `<label class="fld">标签<input></label>` ×N +
  末尾 `<div class="form-actions" style="align-items:flex-end">按钮</div>`（范例 `staff_report_compare.html`）。
  `.form-grid` = `auto-fit minmax(170px,1fr)` → **宽屏一行、窄屏一列**（≤760px）。⚠️ 反例：`label.f`（标签与输入同排）+
  输入框 `width:100%` → 各列宽度不一、标签跳动、按钮另起一行。按钮文案一律 **`查询`**；筛选卡加「清空」（有筛选条件时才出现）。
- **分页唯一实现**：`app/services/paging.py`（`paginate()` + `qs()` 保留筛选条件）+ `app/templates/_pager.html`
  （「共 N 条 · 第 x/y 页」；**单页时只显示「共 N 条」**）。**新页面直接用这两个，别再自己写一套。**
  ⚠️ 批量操作必须作用于**全集**（过滤挪进 SQL，否则 total 算错）；⚠️ **导出绝不能走分页**：`paging.PER_MAX=200`
  会把 `per` 夹住 → 只导 200 行（真 bug）→ 走 `all_rows=True`（回归测试 `test_stations_export_is_not_truncated`）。
- **「圈选队员」故意不分页**：checkbox 表单翻页会**丢未保存的勾选**；有筛选框即可。
- ⚠️ **页码越界必须在"算 offset 的人"那里夹取**（2026-10-17 修的坑）：
  `paging.info_from()` 只夹**显示用的页码**，而自己算 `limit/offset` 的调用方（任务总表、日志页）
  如果拿裸页码算 offset，`?page=99` 就会渲染出「共 N 条 / 第 1 页」+ **空列表**（实测 total=1、rows=0）。
  正确做法（现已如此）：先拿 `total` → 算出 `pages` → 把页码夹到 `[1, pages]` → **用夹后页码重算 offset**
  → 并把真实页码回传给调用方（`task_board` 返回的 `page` 键；路由里 `d["page"] if "page" in d else page`）。
  日志页为此新增 `bd_log.recent_count()`（与 `recent()` 共用 `_recent_q()`，别把筛选条件写两遍）。
  守门测试：`test_task_board_clamps_out_of_range_page` / `test_logs_page_clamps_out_of_range_page`。

### 一都三県入池（线路 + 车站全量，N02）

- **数据源 = 国土数値情報 N02（鉄道）**（MLIT 官方，免费）。字段：`N02_003` 路线名 / `N02_004` 运营公司 /
  `N02_005` 站名 / `N02_005c` 駅コード / **`N02_005g` 同一駅グループコード**（跨线合并的钥匙）；
  `N02_001×N02_002` 是铁道区分（归纳成 kind：jr/shinkansen/private/public/third/monorail/agt/tram/cable）。
  实测：全国 10,220 条车站记录 → **一都三県 1,949 条 → 去重 1,920 个车站 / 131 条线路**
  （東京 871 / 神奈川 408 / 千葉 383 / 埼玉 258）。⚠️ N02 车站属性里**没有都道府県** → 用坐标 + 县界做点在多边形内判定。
  抓取 `scripts/bd_fetch_rail.py` → 落 `scripts/bd_kanto_rail.json`（**随仓库走，导入不需要网络**）。
- **一线一站**：`bd_station` 唯一键从 `name_norm` 改成 **`(line_id, name_norm)`**（部分唯一索引，SQLite/PG；
  `line_id IS NULL` 的行用另一个部分唯一索引保证站名不重复）→ 渋谷/池袋/東京 等**按线路各存一行**（实测同名最多跨 7 条线）。
- **新增 `bd_line`（线路主档）**；`bd_station` 加 `line_id/operator/pref/lon/lat/ekicode/group_code/source`；
  `bd_task.source_type`（今天恒为 `station`；将来片区 = 加 `zone_id` 可空 + `station_id` 改可空 + `source_type='zone'`）。
  ⚠️ **线路名一律用 `bd_lines.line_label()` 显示**（`operator_short + name`）：MLIT 官方线路名会重名
  （「本線」有京急/京成/西武/東武…；都営叫「12号線大江戸線」）→ 简称表在 `OPERATOR_SHORT`。
- **导入 = 幂等 + 必须认领历史站**（`app/services/bd_import_rail.py`，CLI `scripts/bd_import_rail.py`，默认 dry-run）：
  现有 515 个车站（来自 `万总/team_task/*.xlsx`，**带着队伍与担当**）必须被**认领**（enrich 而不是新插）→
  否则同一车站会有两个任务、队伍的派工白做。**认领顺序**：① `(line_id, name_norm)` 已存在 → 用它；
  ② 同名且 `line_id IS NULL` 的历史行：唯一候选就认领，多候选时用**各自**的 `line` 串归一后比对线路名，唯一命中才认领
  （否则记账进 `unmatched`）；③ 其余新建。**实测：1,920 = 认领 515 + 新建 1,405，515 个派工与任务全保留，认领后 0 悬挂**。
- **`norm_name()` 统一 ケ/ヶ**（`app/services/bd_tasks.py`，全站唯一入口）：`箱根ケ崎/箱根ヶ崎`、`茅ケ崎/茅ヶ崎`、
  `南阿佐ケ谷/南阿佐ヶ谷` 必须同键（实测 3 个站因这点对不上）。⚠️ **老库的 `name_norm` 是旧口径写的**（`ケ` 没统一成 `ヶ`）
  → 导入时**顺手改写旧键**（`rep["renorm"]`），否则同名却认领不到而重复建站（实测 3 个）。
- ⚠️ 迁移/脚本坑：**新建 alembic 迁移先查 id 是否被占用**（正则会漏带类型注解 `revision: str = 'x'` 与单引号写法 →
  选到已占用号 → `CycleDetected`）；**dry-run 不能发临时负 id**（131 条线路曾全成负 id）。

### 物理车站层（三层资产）

- **三层结构**：`bd_line`（线路 131）──1:N──> `bd_station`（**站×线** 1,920）──N:1──> **`bd_station_place`（物理车站 1,568）**。

- **分层键 = `N02_005g` 駅グループコード**（MLIT 官方"同一车站"分组，**不用猜**）。实测：1,920 条站×线 →
  **1,568 个物理车站**；**237 个跨线站**（渋谷/新宿/横浜/大宮/池袋 最多 **7 条线**）；**同组站名 100% 一致、坐标 100% 在 1km 内（0 异常）**。

  ⚠️ `n_line` 语义 = **不同线路数**（手工站可为 0）→ 体检对照必须 `COUNT(DISTINCT line_id)`（不是 `COUNT(*)`）。

  ⚠️ 对齐口径用 **`group_code != ''`**，不能按 `source='mlit'`（认领的 515 行 `source=manual` 但属性来自 N02）。
- **资产导出 `scripts/export_station_asset.py`**：两份 CSV、**utf-8-sig**（Excel 双击不乱码）——`stations_places.csv`（物理车站层）+
  `stations_lines.csv`（站×线层，**含任务状态/队伍/担当**）。

### 沿線顺序（seq）：OSM → 几何 → 人工

> 用户口径："顺序**不自己算**，去 OSM 拿现成的"（选 A：OSM，已接受 ODbL 署名），后来补几何兜底 + 最后 3 条人工定稿。

- **三级来源优先级 `OSM → 几何 → 人工`，且⚠️ 一条线只用一个源**（`seq_src` 记 `osm:*` / `geom:N02` / `manual:*`）——
  **绝不混用两个源**（混了 seq 就不可比，排序会错）。OSM 没匹配上、**或只覆盖不到一半**的线路 → 整条改用几何。
  主源必须是 OSM：route relation 的**成员本身有序**（`role=stop`）、**环线直接给一圈**；N02 只有"点 + 线"、**没有顺序字段**。
- ⚠️ **N02 的"线路" ≠ 管理员认知的"线路"**：N02 是**官方线路名**口径（`山手線` 只有 17 站，东弧官方叫東北線、南弧叫東海道線；
  `埼京線`/`湘南新宿ライン`/`総武線快速` 在 N02 里不存在）；OSM 是**运行系统口径**（山手線 = 30 站一圈）。→ seq 用 OSM 口径**是对的**，
  但要接受"同一条 N02 线路内 seq 可能跳号"（排序只看相对大小）。
- **落地**：`bd_station` 加三列 `seq`（1 起）/ `along_km`（沿线里程 km）/ `seq_src`（可审计）；工具
  `scripts/bd_fetch_osm_routes.py`（→ `scripts/bd_osm_routes.json`，**随仓库走**，导入不需要网络）+
  `scripts/bd_fill_seq.py`（按**坐标**把 OSM 有序站对到我们的站，默认 dry-run）。**匹配三档**（同档内优先覆盖我们站最多的班次）：
  ① F1 ≥ 0.70 强匹配；② 召回 ≥ 0.85 且名字相关 = 我们是它的一段；③ 召回 ≥ 0.5 且名字相关 = 只能对上一部分（如实报告）；
  **再加"同名兜底"**：坐标差得多的站在已选线路里按站名匹配（限 2km，防同名异地）。
- **4 行踩坑**：
  ① ⚠️ **绝对不能用 `out geom` 抓关系**：整条线几何一起返回 → 一批直接**静默截断**（527 个 id 只回来 195 个）；
     正确写法 `out body; >; out skel qt;`（只要成员节点）。
  ② Overpass 公开实例会**限流**（连续 429/504，三个镜像全挂）→ 改用 **OSM 官方 API `relation/{id}/full.json`**
     （稳，还带成员标签=站名）；单条要几秒 → **4 并发 + 断点续传 + 每 20 条落盘**。
  ③ 名字匹配的 `.*→.*` 贪婪式会把 `都営大江戸線 : 都庁前→光が丘` **整串吃掉** → 核心词为空 → 所有线路被"名字不相关"误拒
     （覆盖率 74% → 52%）。改成先切 `[:：]`/`[-–—]` 再去后缀。
  ④ F1 只看"召回+精确"会**误配跨线班次**（实测 `多摩線` 被 `多摩快速急行` 抢走）→ 加名字门 + 长度上限。
- **几何法兜底**（`scripts/bd_seq_from_geometry.py` → `scripts/bd_line_seq_geom.json`，随仓库走）：起点 = **离我们的站最近的端点**；
  **质量门槛** = 车站到轨道**最大投影误差 ≤ 250m** 且**每站都贴得上**；串不全的线（分叉/复线）放宽到"串起 ≥50% 段"
  但**仍要求每站贴得上**，否则**宁可空着并如实报出来**。实测 20 条线拿到（误差几乎全 0.0m）；**3 条主动放弃**：
  `総武線`（1466m）、`成田線`（36938m）、`箱根登山鉄道線`（3875m）。⚠️ 几何法**是兜底不是主源**（"自己算"，只配在 OSM 拿不到时用）。
- **最后 3 条人工定稿**（`scripts/bd_line_seq_manual.json`；総武線 46 / 成田線 27 / 箱根登山鉄道線 11 站）：
  **两个独立来源交叉校验** —— ① Wikipedia「駅一覧」小节（`?action=raw`，**只抽该小节**：抽全页链接顺序是错的，实测
  `東京 → 銚子 → 小岩` 这种乱序；还要跟重定向）② 坐标最近邻链；两边**互相补漏**。
  ⚠️ **支线 / Y 字形不适用里程**：総武線含緩行線支线（按地理放在馬喰町与錦糸町之间）；成田線是 **Y 字形** → 线性列表
  **必然有一次大跳** → **`km_mode='none'`（不适用里程）**，只保证顺序，否则页面会出现"成田空港 43km"这种误导数字；
  箱根登山有 **スイッチバック**，里程按站间直线累加会略小于实际。
- **最终覆盖率：1,831/1,920 站（95%）· 131/131 条线都有顺序**（OSM 1,556/108 + 几何 191/20 + 人工 84/3）；
  剩下 89 站分布在 16 条"只取到一部分"的线上。几何输入是 N02 的 `N02-22_RailroadSection.geojson`（**不随仓库走**；
  需要时 `scripts/bd_fetch_rail.py` 重下）。
- 界面：`/stations` 选了线路就**按 seq 排**（`ORDER BY seq IS NULL, seq`），行首显示「顺序 + 里程」（如 `6 · 10.0km`）；
  底部按 ODbL 署名「线路顺序数据 © OpenStreetMap contributors」。⚠️ **排序是增强不是前提**：没顺序的照样列出可勾选
  （用户："如果排序困难，那就算了…让管理员手工选择就好了"）。**不走"从线路图片解析"那条路**（样式不同、有版权、太贵）。

### 建任务（按线路选站）

- **任务概念（定稿，别再动摇）**：**1 个物理车站 = 1 个任务**（跨线站只 1 个；同名异地本来就 2 个），
  **派活是滚动的** —— 用户原话："我分给 A 队的 10 个站，**并不是他这 10 个站作为一个整体任务跑完我再分新的**，
  而是在剩下几个站的时候，我就可以再派发新的一组任务给他"（⚠️ 中途一度按"任务=队×线路批次"设计，被纠正；
  京葉線 10 站给 A + 8 站给 B = **18 个任务**）。
- 表：`bd_task` 加 **`place_id`**（FK `bd_station_place`）+ 部分唯一索引 `uq_bd_task_place`（`place_id IS NOT NULL` 上唯一）；
  `station_id` 改**可空**（老口径留空，`UNIQUE(station_id)` 对 NULL 不生效 → 两种口径共存）。
- `_place_ids_taken(db)` —— **去重的唯一判据（两种口径都算）**：`bd_task.place_id` 直接命中 **或**
  老任务的 `station_id` 所属的 place。⚠️ 只算一边会出现"同一个车站两个任务"（真 bug）。
- ⚠️ **2026-10-17 补的一个同源 bug（测试审查时抓到并复现）**：`bd_tasks.create_tasks(db, station_ids)`
  的 `have` **只查了 `station_id` 这半边**，没走 `_place_ids_taken` → 当该物理车站**已有 place 口径任务**
  时会再建一个（实测同一车站 2 个任务）。唯一生产调用方是 `bd_import_rail(make_tasks=True)`（线路导入的
  ④步）。已修：建之前按 `_place_ids_taken` 判占位，并把**本批内新建的 place** 也记进去
  （否则跨线两行同属一个 place 时会各建一个）。守门测试
  `test_team_task.py::test_create_tasks_never_double_creates_a_physical_station`。
  > 教训：这条铁律已经在 `_place_ids_taken` 的 docstring 里写明了，但**新建任务的入口有两套**
  > （place 口径 `create_tasks_for_places` / 老 station 口径 `create_tasks`），当年只修了前者。
  > 以后凡是"按车站建任务"的新入口，都必须走同一个判据。
- `/tasks/new`（`bd_task_new.html`）交互：**选线路（快速过滤）→ 该线车站按 `seq` 排列（带里程、还经过哪些线、已有任务禁用）
  → 勾选 → 可选派队 → 建**。要点：**线路只是筛子，不要求全选**；**勾选**=点一下勾，**Shift+点=勾中间一整段**，
  **按住鼠标拖过多行=连续勾选**（拖拽只走 mouse 事件，手机只有 tap，免得和滚动打架）；
  **一页不分页**（最长线路京急本線 50 站，一页放得下 → 勾选不会跨页丢失）。建完**留在本页**，提示"已新建 N 个（跳过 M 个已有）"。
  入口：`/tasks` 右上角 + `/stations` 选了线路后的「用这条线建任务」。**不做日期输入**（分配日期=今天）；**不做担当选择**（队长分）。
- **任务视图"place 优先"**：`_rows` 同时取 place 与 station，`station_name`/`line` 两个键名不变但值取 `place` 优先；
  `_base_query` 的**线路筛选**改成 EXISTS（认 `station_id` 或 `place_id` → 跨线站会出现在它经过的每条线的筛选里，这是对的）。

### 车站页 / 任务页（现状，按真实代码）

## AI 派工建议（2026-10-06 · 任务管理的模型介入点）

- **入口**：管理端 `/tasks` →「未分配」tab（车站池）→ 分配卡片上的「**AI 建议**」按钮（htmx `POST /tasks/ai-suggest`
  → 局部刷新 `_ai_suggest.html`，不跳页）。
- **数字全部由程序算**：各队负担（成员/在岗/未完成/进行中/停滞/已完成 + 主要线路）与车站清单由
  `bd_assign_ai.pool_digest()/team_digest()` 查出；**模型只做「分组 + 写理由」**。
- **只建议、绝不写库**：模块里没有任何写操作（不建任务、不派队、不落库）。采纳 = 管理员点「勾选这组」→ 再按既有的
  「分配给该队」→ `assign_team_to_places`。
- **输出必须可核对**：模型给的站名/队伍名**逐个对照真实数据校验** —— 编造的站名、不存在的队伍、重复分站
  **一律丢弃并如实回报**（`dropped` 计数显示在页面上）；一条都没通过 → 报错让管理员手动分配，**宁可少给建议也不给假的**。
  队伍名有小容差（「甘子杰」能对上「甘子杰队」），歧义（匹配到多个）则丢弃。
- **AI 不可用不影响主流程**（未配置/调用失败/输出不可解析 → 片段里一句话 `ai-suggest-err`，车站池与手动分配照常工作）；
  **口径**：车站池 = `list_unassigned_places()` 的**同一口径**（绝不自己再写一套「未分配」，否则建议与页面对不上）；
  一次最多喂 **150 个站**（`POOL_LIMIT`，超了提示先按线路筛）；`PROMPT_VERSION=2`（第 2 版加「一律用简体中文」）。
- ⚠️ **AI 默认直连**：httpx 默认 `trust_env=True` 会读 **macOS 系统代理**（本机 `127.0.0.1:7897` 对 HTTPS 是坏的）
  → **本机所有 AI 调用全部失败**，而 `api.deepseek.com` 直连是通的。→ `ai_chat._client_kwargs()` 默认
  **`trust_env=False`（直连）**；要代理显式配 `AI_PROXY`，`AI_TRUST_ENV=1` 恢复老行为（回归测试
  `test_ai_chat_direct_by_default`）。影响面：**所有**用 AI 的功能（`report_ai` / 看板分析 / 派工建议）。
- 测试锁住：乱编站名/队伍/重复分站被丢弃、**绝不写库**（断言任务数不变）、prompt 含确定性数字、AI 未配置与输出垃圾两条错误路径、默认直连口径。

## SQL 去重（2026-10-06 用户："为什么还有这么多 SQL？一个 tab 一条 SQL 就可以了"）

- **列表 SQL 必须常数条**：队长 `/my/tasks?tab=unassigned`（本队 76 条任务、82 行车站池）实测 **188 条 → 30 条 → 22 条**，
  **与行数无关**。
- **22 条 = 每请求基座 ~8 条 + 页面数据 ~14 条**。基座（与页面无关）：登录用户 1、身份快照 1、名册起点 1、未读消息
  COUNT 1、能力表 1、表单令牌 INSERT 1~2；页面：`bd_task` 1、车站/线路 2、`bd_task_assign` 2、最新进展 1、`bd_team` 2、
  `bd_team_member` 2、`users(status)` 2、`staff_date_plans` 1、`bd_staff_leave` 2。
- **原来 188 条是 N+1（每行查一次权限）——这才是病根**：别在循环里调 `can_*`；批量权限用
  `bd_tasks.can_reject_maps(db, user, tasks)`（担当一次 + 我带的队一次 + 最新进展一次 + 能力表按角色）。
- ⚠️ **跨 session 传 ORM 对象是雷；要传就传值**：复用中间件缓存的 ORM 对象 → 那是**另一个已关闭的 session**，对象
  detach → 路由改属性再 commit **静默不生效**（实测把"改密码"改坏了）。修法：中间件只传**身份快照**（`SimpleNamespace`，
  列值），ORM 对象仍由 `require_login` 在本请求 session 里取。

## 进展复核：管理员批量驳回队长已确认的进展（2026-10-07 · ✅ 已发布 20261008_214046）

**为什么需要**：队长可以一键全确认，但**确认错了没有回退手段**；这个需求补的是"**推翻队长的结论**"。

**口径**（用户当场三选一选定）
- 驳回后：**退回队员上报的原值**（`reported_pct`），状态回 **`pending`（待确认）** —— 队长在待确认队列里重新看到它；**员工侧的锁随之解除**。
- 范围：`confirmed`（队长认可）**和** `adjusted`（队长改了值）**都算**。
- 通知：**队员各自一条**（"确认被撤销，进度回到 X%"）+ **涉及的队长各一条汇总**。
- 无原值的行：新增 `no_origin_pct`（界面「**没有队员原值的退回 X%**」），**只对没有原值的行生效** —— 有原值的行照旧退回**各自的原值**，队长直接填的行退回这个值，两者都不填则跳过并给原因（继续保持"不猜"）→ 一批里两种行可以**一次处理完、互不覆盖**。
- `force_pct`（界面「统一退回到 X%」）：员工原值也是 100% 时靠它才能把"已完成"打回；提示「要把『已完成』打回进行中，请在『统一退回到』里填一个小于 100 的值」。
- ⚠️ **生产实测**：pct=100 的行里 **63 条没有队员原值**（只有 17 条有）→ "队长直接填"是常态，靠"退回原值"根本退不了 ✗。

**实现**
- 服务层 `bd_tasks.settled_reviews()`（清单）+ `bd_tasks.reject_reviews_many()`（批量驳回）
  - 清单是"**按进展记录**"列，不是按任务 —— 要驳回的对象是"队长确认了这条"。
  - 逐条一个 **savepoint**（照 `set_progress_many`）：一条坏不影响其它，跳过要**给原因**。
  - **只有该条是任务最新一天那条**时才改 `bd_task.pct/state`；更早的日期只改历史行（否则会污染"当前生效值"）。
  - 消息：新增 `unconfirmed` 文案（`notify_task_progress`）+ 队长汇总用 `bd_msg.send`。
- 路由 `GET /tasks/reviews`（**管理员**）+ `POST /tasks/reviews/reject`；页面 `bd_reviews.html`（日期区间 + 队伍筛选、全选、统一退回、原因、二次确认）+ 左侧导航「进展复核」。
- 无数据库迁移（`bd_task_progress` 的列都够用）。
- **通知收件人**：只有"**真有队员上报过**"（`reported_pct` 非空）才用 `reported_by` —— 否则队长直接填的行 `submitted_by` 是队长自己，他会既收"确认被撤销"又收汇总（重复打扰 ✗）；没上报人时收件人退化成"任务当前担当"，都没有就不发。

|---|---|
| `uq_bd_team_member_active_person` | `person_code` 在 `end_date IS NULL` 的行上唯一（**一人一队**）|
| `uq_bd_team_member(team_id, person_code, start_date)` | **同队同天只能有一行** |

移出是**软删**（`end_date` 收口），行还在。当天再加回同一个队 → 代码去插 `(队, 人, 当天)` → 撞第二个约束 → 被 `except IntegrityError` **一律**当成"被别的队圈走了"报出去；提示还让人"去原队移出"，而那一行早已 `end_date` 收口、页面上不显示 → **永远加不上**。（线上实例：アサダ 在 A小川队/F甘子杰队/B陳偉鋒队 各留一行 `start=end=2026-10-16`，**没有任何现役行**，但往这三个队都加不上。）

**修法**（`app/services/bd_teams.py`）
1. 插入前先找 `(team_id, person_code, start_date == day)` 那行；找到就**复用** —— 清 `end_date`、更新 `role`、写日志「当天移出后又加回（复用原记录，不新增行）」并 `continue`。（唯一键含 `start_date`，本来也不允许再插一行。）
2. `except IntegrityError` 改为 `raise TeamError(_conflict_msg(e))`；`_conflict_msg()` 按约束分流：命中 `uq_bd_team_member_active_person` 或含 `person_code` 但**不含** `start_date` → 仍是"被别的队圈走"；含 `start_date`（或 `uq_bd_team_member`）→「同一天内在同一个队重复登记了同一个人」；其余给通用文案 + `t[:160]`。（SQLite 报**列名列表**、PG 报**约束名**，两套都要认。）

**"一人一队"死规定没动** —— 那是第一个约束，仍然拦着。

**测试**：`tests_web/test_team_task.py::test_readd_same_person_same_team_same_day`（断言该人只有 1 行、`end_date is None`）、`::test_conflict_msg_tells_which_constraint`（PG 约束名 / SQLite 列名两套）。
