# 线上数据迁移方案（不重导，只建表 + 重建新表数据）

> 用户口径（2026-09-25）：**线上数据不重导**；把新表建好，**直接生成新表里的数据**即可。
> 原则：以线上现有数据为准（工资已发出去，历史口径不可改写）。

## 一、迁移对象（本分支相对 main 的全部新增）

### 新增表（5）
| 表 | 作用 | 数据从哪来（线上） |
|---|---|---|
| `payroll_payments` | 发放台账（人×月×期，实发快照，不可改写） | **由已发月份的分期表重建**（导出即发放，见 §3） |
| `payroll_adjusts` | 找平表（原始/已找平/剩余/状态/结清时间） | **由 `payroll_period_rows.diff_amount` 逐人生成**（`period.sync_adjusts`） |
| `payroll_settlement_links` | 发放↔找平 多对多关联 | 由台账 + 找平表跑 **FIFO 分配**生成 |
| `payroll_paid_marks` | 发薪标记（旧兼容） | 与台账同步生成（可空） |
| `sealed_months` | 封账月份 | 线上按业务确认（如 8 月） |
| `rebuild_snapshots` | 月度重算前快照 | 空表即可（重算时自动写） |
| `api_tokens` / `mcp_audit_log` | MCP 身份与审计 | 空表；上线后由用户自助签发 |

### 新增列
- `api_tokens.expires_at`（有效期，空=永久）
- `payroll_payments.adjust_source_type / adjust_source_month / adjust_source_row_id / adjust_source_task_id / adjust_leftover`（抵扣溯源）

## 二、迁移步骤（线上）

1. **备份**（必做）：`pg_dump` 全库
2. **发布**：走既有流程（rsync + compose build web + up），entrypoint 自动 `alembic upgrade`
   → 迁移链 `…→ f6c7d8e9f0a1 → a1b2c3d4e5f7 → b2c3d4e5f6a8 → c3d4e5f6a7b8 →
   d4e5f6a7b8c9 → e5f6a7b8c9d0 → f6a7b8c9d0e1 → a7b8c9d0e1f2 → a4b5c6d7e8f9`
   → **只建表/加列，不动任何既有数据**
3. **回填新表数据**（一次性脚本 `scripts/backfill_prod_new_tables.py`，见 §3）：
   - 生成 `payroll_adjusts`（按 `payroll_period_rows.diff_amount`）
   - 重建 `payroll_payments`（**已发月份**：按分期表 half 金额逐人逐期登记）
   - 跑 FIFO 分配 → 写 `payroll_settlement_links` + 回填 `payroll_adjusts.settled/remaining/status/settled_at`
   - 生成 `sealed_months`（按业务确认的封账月）
4. **校验**（迁移后立刻跑）：
   - `visit_verify_integrity`（8 项自洽）必须全过
   - 逐人对比迁移前后：`month_perf_records` / `payroll_period_rows` **必须逐字节不变**
     （回填只写新表，不碰老表）
   - `payroll_adjusts` 金额合计 == `payroll_period_rows.diff_amount` 合计
   - `payroll_payments` 合计 == 已发月份的应发合计

## 三、"已发"事实怎么重建（关键设计）

线上没有台账，但**工资已发**。重建依据用户既有流程：**导出发薪表 = 发放事实**。

```
对每个"已发月份" M：
  for each person in payroll_period_rows(M):
    seq=1 → amount = half1_amount, points = half1_points, bonus = half1_bonus
    seq=2 → amount = half2_amount, points = half2_points, bonus = half2_bonus
    （若该期金额为 0 且该期无数据 → 不登记，避免把"未发"记成"已发"）
  然后按 FIFO 把各期可吸收额度冲 open 找平 → 生成 links + 回填 settled
```

**为什么这样做**：
- 让 `recompute_affected_months` 能识别"已发薪月份"并**跳过重算**（用户要求：不改已发口径）；
- 使找平进度从"真实起点"开始（已发月份的债务要么已回收、要么剩余结转）。

## 四、需要用户确认的一项

**线上哪些月份已发薪？**（决定 §3 重建哪些月份）
- 建议：**7 月、8 月、9 月**（线上都有数据且已发）
- 若某月只是"导出了但没发"，需单独说明（该月不登记台账）

## 五、风险与回滚

- 回填**只写新表**，老表零改动 → 回滚 = `alembic downgrade`（删新表）+ 旧版本代码，数据无损失。
- 若回填后发现找平进度不对：删 `payroll_payments`/`payroll_adjusts`/`payroll_settlement_links`
  三表数据重跑回填脚本即可（幂等：脚本先清后建）。
- 迁移期间**不做**：文件重导、月度重算、店铺合并（避免与回填交叉）。
