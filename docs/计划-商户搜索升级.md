# 商户搜索升级执行方案

> 创建：2026-11-12；更新：2026-11-13（Asia/Singapore）。状态：搜索改造待实施，两级样本方案已采纳；生产日志表已于11月13日补齐并开始采集。本次更新仅修改方案，未执行样本导出、算法改造或部署。
> 当前实现依据：NestJS `apps/server`、React `apps/staff`、`packages`；Python 旧实现仅用于历史追溯。开发、Docker、生产交付分别验收，不能混称已上线。

## 1. 目标、范围与原则

目标：员工能用不完整名称、不同字符写法、地址或编号找到正确商户，最相关结果排在前面；逐步补齐多词、别名、日文读音、适度纠错、补全和高亮，达到可衡量的商品搜索式体验。不承诺复刻淘宝的推荐或个性化系统。

首个入口限定为员工端批次网格商户搜索。管理端全局商户、旧任务列表和地图全库搜索不自动纳入。现有网格范围与状态筛选是硬边界；搜索不能偷偷跨网格找店。若日志证明用户实际需要跨网格检索，单独设计有权限控制的明确入口。

- 原始名称、地址、编号、任务快照及历史结果保持原值；搜索字段和索引是可丢弃、可重建的派生数据。搜索归一化不用于商户主档合并。
- 业务逻辑放 Nest 服务层，React 只处理输入和展示。结算域不参与、不加列、不读写。
- 先取样定位原因，再评估引擎。不因总商户数就推定要增加服务；同时测当前网格和总索引规模。
- 空结果可能来自范围、筛选、缺失字段和数据错误；搜索引擎不能凭空补齐缺失信息。
- 第一阶段不依赖付费模型、Google Places、外部商户库或向量模型。自然语言类别搜索另设扩展门槛。

## 2. 当前事实与需要修正的假设

| 当前事实 | 依据与影响 |
|---|---|
| 员工巡店主查询由 `BatchWorkService.visits()` 调用 `mobileVisits()` | `apps/server/src/batch-work.ts`、`apps/server/src/mobile-visits.ts`；名称/地址来自店铺任务快照，编号来自 `store_id` |
| 名称、地址、编号使用原文 `ILIKE` 包含查询 | 标准化后的命中目前用于诊断，不直接返回；`ＡＢＣ　商店` 与 `ABC商店` 可能漏匹配 |
| 关键词直接包裹 `%` | `%`、`_` 当前具有 SQL 通配含义，升级需明确改为字面字符搜索，并补行为回归 |
| 巡店结果先处理 focus，再按距离、ID 排序 | 有关键词时没有名称相关度优先；距离可能使更相关商户排后。focus 是业务定位能力，不能简单删除 |
| 地图和抽屉共用授权网格快照 | 升级仍须共用筛选及排序口径，分页和计数必须来自相同结果集合 |
| `stores()` 另有一条旧式查询 | 实施前核对调用方；仍使用的同一批次搜索入口共享规则，其他入口列为独立范围，避免只改一处便宣称全站统一 |
| 已有 `bd_store_search_log` 和汇总脚本 | `apps/server/test/store-search-log.test.ts`、`scripts/analyze-store-search.mjs`；只读分析可区分空网格、筛选排除、归一化候选、待核查；当前没有完整的点击/成功找到事件，不能声称已有搜索转化率 |

实施前必须用真实反馈确认上述问题各占多少。上一轮讨论中“pg_trgm 可稳定解决任意错字”“几十万条数据一定适合某方案”都不能作为事实：日文短词、汉字、片假名、混排与长地址需分别测量。

## 3. 验收样本与指标定义

### 3.1 两级样本与证据边界

| 层级 | 来源 | 用途 | 正确答案如何确定 |
|---|---|---|---|
| 一级：真实搜索样本 | 生产 `bd_store_search_log`、投诉及后续明确反馈 | 优先衡量真实找店收益，决定改造优先级 | 结合查询当时的授权网格、筛选、任务快照，以及用户期望/人工核实的目标店铺任务ID；有结果不等于正确命中 |
| 二级：历史主档名称样本 | 本地数据库 `store_settle` 的 `public.store_entities.name_local`，候选来源为 `public.kanto_merchants_v20261029.name` | 批量评估名称候选覆盖、字符兼容性、同名区分；核实子集用于检验排序 | 名称一致只产生弱标签；地址/坐标或人工证据确认后才形成实体正确答案，单候选也不自动判同店 |

2026-11-13已只读核对实际表名和数量：`store_settle`是数据库名，不是商户表；主档113,774条、商户620,280条。来源商户表不具备普通自增id字段，应在冻结快照中给样本候选生成稳定键（原有place_id/overture_id/osm_id组合加行内容hash；处理缺失和重复），不能使用会变化的行号或ctid。样本键仅用于离线评估，不建立业务关联、不合并主档。

#### 一级采集与冻结

1. 以生产2026-11-13 15:57（新加坡）只读检查为首个观察点：19条请求、16个不同关键词、1名用户/1个网格，7条有结果、12条零结果，有结果率36.84%；日志时间为14:14:56–14:21:17。零结果原因11条unresolved、1条filters_excluded。此为历史观察快照，不是以后固定分母或整体用户指标。
2. 在执行V0时按明确截止时间与日志ID水位只读导出，完整保留上述窗口及后续样本。字段包括日志ID/时间、脱敏actor、批次/片区/网格ID、query_text、page、状态筛选、used_location、matched_count、诊断计数和原因、耗时；同时记录数据库/部署/查询策略版本和采集时间。私有评估文件放`data/refactor/search-evaluation/<dataset-version>/`（拟定，保持忽略），仓库仅提交脱敏fixture、规则及汇总，不提交生产原日志。
3. 每条补充标签：目标任务ID、证据、标注人/时间、在当时网格内与否、筛选是否排除、正确结果等级、可复现性。优先核实`chocoZAP大久保`、`ｃｈｏｃｏＺＡＰ大久保`等失败词；目标不存在或不在授权范围时标为数据/范围问题，不算算法漏召回。缺少用户期望时标unknown，不以最相似候选猜答案。
4. 保留原始请求时间序列，同时生成找店过程分组。没有sessionId时暂用“同一脱敏用户+批次+网格+筛选、相邻请求间隔≤5分钟”作为可版本化启发规则；人工检查前缀链与目标变化，可拆分不同意图，记录不确定分组。请求级统计与过程级统计并列；19条请求不能当19次独立找店，16个词也不能当16个独立目标。
5. 已有日志未保存完整结果列表、排名、输入坐标或请求时全部数据版本。采集时尽可能只读冻结相关任务快照与scope；不能还原过去坐标/状态/排序时，历史只作诊断证据，另在冻结数据上用同一输入对旧/新策略重放。不得把今天的重放称为当时线上精确结果。
6. 把已确认目标且在范围内的查询纳入正确召回/排序分母；unknown、范围外、空网格、状态排除分别报告数量及处理情况。人工核实的不存在目标可作负例，未匹配本身不能充当负例。一级按请求和找店过程分别报告，过程级以全部已确认找店过程为分母，成功指该过程至少一次前10条含正确目标；另报告首次查询的首位命中与MRR，防止多次重试掩盖体验。

### 3.2 样本划分与必测类别

先固定至少 50 条脱敏且可复现的查询样本，每条记录：查询、授权网格、当前筛选、预期店铺任务 ID、相关性等级、是否应为零结果、原因标签。至少20条来自经核实的真实投诉/日志独立找店过程；当前19条请求不足以证明满足该门槛，不用前缀链或二级主档凑一级数量。不足则先使用合成样本启动竖切，但必须分别标记真实/合成与不足项，不得宣称真实投诉改善已验收。保留原始测试集，新增失败样本，不通过删除难例提高指标。

两级样本分别分为调参集和留出集，建议按商户/品牌分组固定80%/20%并记录seed与样本版本；同一找店过程、同名变体、同一实体及跨两级重复目标归到同一侧，避免泄漏。已用于讨论/调参的当前生产失败词可作为回归样本，但不能再声称是盲测留出集。新增别名不直接根据留出集答案生成。

| 类别 | 必须覆盖 |
|---|---|
| 字符差异 | NFKC 全半角、大小写、全角/半角空格、假名宽度、真实含标点店名 |
| 精确与短词 | 编号含前导零、编号完全命中、同名不同店、1–2 字短词、无关键词 |
| 容错与扩展 | 名称少字/错字、词序变化、多词跨名称/地址、中文写法、假名/罗马字、未知读音 |
| 业务边界 | 其他网格同名店、无权限网格、状态筛除、已关闭批次、focus、分页、坐标缺失、零结果 |
| 异常与并发 | 索引缺文档/延迟、引擎不可用、门店更新/删除、权限变更、旧请求晚返回 |

### 3.3 指标、收益报告与门槛

两级独立出表，不合并命中率或用大量二级样本稀释一级失败。每张收益表记录样本/数据hash、旧新策略版本、样本资格、分母、unknown数、新旧值、绝对增量/百分点、同条件延迟与退步样本。生产无结果日志只能直接证明有结果率，不能直接证明正确召回或排名。

- 一级有结果率：首屏有效关键词请求中matched_count>0的比例；按筛选、scope和过程拆分，保留同词重试的请求分母，不能与去重/过程分母混用。
- 一级首位命中率：经确认且目标在范围内的查询，第一条为正确目标的比例；同时报告过程首次查询与请求级结果。
- 二级名称候选覆盖率：候选数>0的主档记录数/冻结主档总记录数；另报去重名称口径、增量覆盖、多候选分布，零候选不等同真实负例。只有核实子集才能报告正确Recall@10、首位命中率及MRR@10。
- Recall@10：有预期商户的查询中，前 10 条含任一正确结果的比例；按字符、读音、错字等类别分别统计。
- MRR@10：第一个正确结果名次的倒数，超出前 10 或无结果计 0，再取平均。
- 零结果率：仅统计首屏有效关键词搜索；按原因分组，不能把空网格或权限限制当搜索算法失败。
- 错误召回：负例是否返回貌似相似却不相关结果；至少使用 20 条负例检查。短词禁用宽松纠错，编号不自动纠错。
- 延迟：分别记录 API、SQL/引擎、应用处理和浏览器时间，报告 p50/p95、样本数、并发和数据规模；同机同库同条件对照。
- 数据正确性：权限泄漏 0、无重复/漏页、计数一致、原始业务字段变化 0。权限限制不能为提高召回率放宽。

以下量化门槛是本方案的拟定验收标准，不是现有实测值：最小竖切标准化样本 Recall@10=100%，留出集 MRR@10 不低于基线；完整方案留出集 Recall@10≥95%、MRR@10≥0.85，编号精确命中首位率=100%。上述正确召回/排序门槛仅适用于已标注目标的一级和二级核实子集，分别验收；不要求所有历史主档达到95%候选覆盖。二级至少保留原文精确和归一精确两条召回路径，不丢失同快照既有候选，新增模糊/别名候选单列；尚无证据设定二级整体覆盖增长承诺，V0复算后按未匹配原因确定可改善子集及目标。每类单列，核心字符类不得退步；错误召回负例至少 95% 正确判空。真实人工“是否找到”率作为上线观察项，样本不足时不硬算提升百分比。

性能拟定目标：固定本地代表性数据、热身后至少 200 次查询、5 并发，搜索 API p95≤300ms 且无关键词列表 p95 相比基线增加不超过 10%；补全接口 p95≤150ms。未达标先拆解瓶颈，不直接添加缓存。目标修改须记录依据和对用户体验的影响。

## 6. 文档模型、排序和一致性约束

搜索投影以店铺任务为文档单位：`storeTaskId`、`gridTaskId`、`storeId`、快照原文、归一名称/地址/编号、aliases、kana、romaji、sourceHash、sourceVersion、normalizerVersion。实时状态和当前权限以数据库为准；引擎可存过滤副本但不独立授权。坐标及实体扩展字段只有在确认与当前详情/任务快照口径一致后才入索引。

排序使用可解释的分层规则，先确定匹配层级，再比较层内分数；不要用任意相加分数让多个地址弱命中压过一个编号精确命中。地理距离只作相关性同级的辅助，无关键词沿用现有距离顺序。最终以唯一任务ID打破平分；客户端展示名称仍来自原始快照。

归一化不能只做应用侧：PG查询、投影回填、增量写入和外部引擎必须使用同一版本规则及契约样本。NFKC不等于简繁或日文新字体转换；中文高岛屋匹配高島屋由有出处的别名覆盖，避免全局汉字映射误召回。去空格字段用于召回，原始词界信息另保留给多词排序。

分页采用现有页码契约时，以查询/索引版本保持稳定，重建切换后旧分页会话提示刷新；若需cursor必须同步改契约和React。高召回算法如限制候选，只能返回明确的候选数或hasMore，不能把截断候选数冒充全量total。默认保留精确total语义；引擎与数据库不一致时降级到同一PG查询生成items/total。

## 8. 方案选择依据与官方参考

- PostgreSQL `pg_trgm`：三元组相似度、GiST/GIN及LIKE/ILIKE索引支持；模式无法提取有效三元组时可能退化为全索引扫描。因此短日文词必须单独测，不保证任意错字都有效。<https://www.postgresql.org/docs/current/pgtrgm.html>
- OpenSearch Kuromoji：日文形态分析、基本形、读音及补全组件；使用前需安装`analysis-kuromoji`。本项目完整引擎路线优先评估它，但以F6为准。<https://docs.opensearch.org/latest/analyzers/language-analyzers/kuromoji/>
- Meilisearch：可配置typo tolerance；编号字段和短词需配置保护。轻量候选之一，不把默认容错等同于中日文搜索已达标。<https://www.meilisearch.com/docs/capabilities/full_text_search/relevancy/typo_tolerance_settings>
- Typesense：不同数据类型有不同搜索配置，尤其编号和普通名称；作为另一个轻量候选，不与Meilisearch重复落地。<https://typesense.org/docs/guide/tips-for-searching-common-types-of-data.html>

来源核对日期为2026-11-12；具体发行版、许可证、插件兼容与部署资源在F6锁定，不在此编造性能/成本结论。

向量/语义搜索列为远期可选项：仅当已有可靠类别、位置数据，且真实样本包含“车站附近的药妆店”等自然语言需求而词法方案无法满足时，另建样本评估。需补模型部署/费用/数据流向/索引更新依赖，精确编号和词法路径始终保留；不作为本方案完成条件。

## 9. 执行顺序与完成判定

1. 先执行V0采集一级/二级样本并复算、冻结基线；采集产物不等于算法收益；再执行V1–V4，交付可独立验收的最小竖切。未找到足够真实投诉时明确这一限制。
2. 结合V0证据执行F0–F5，按需补投影和模糊检索，不先安装服务；达到目标即可停在PG。
3. 有明确剩余缺口再执行F6；选定一个引擎后按F7–F14完成同步、权限、交互、运维及发布闭环。
4. 最终交付必须分别附一级请求/找店过程、二级全量候选覆盖/核实子集的收益对照表，标记用户提供/复算/人工核实的证据状态及unknown；另附样本分组结果、基线/新版延迟、错误召回、权限与数据不变量、实际部署版本、剩余限制和回退证据。不得仅凭“引擎已运行”或“单测通过”判定搜索效果完成。
