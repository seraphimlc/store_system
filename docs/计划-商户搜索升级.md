# 商户搜索升级执行方案

> 创建：2026-11-12；更新：2026-11-14（Asia/Singapore）。**当前状态：全量商户检索、归属分类、员工端与商户级反馈已接入源码；隔离／浏览器及一轮含日志的全语料性能验收通过，待质量风险收敛与正式生产候选验收；尚未部署本轮搜索升级。** 本节 A–F 为现行执行计划，优先于后文历史方案、完成标记及发布指令。

## A. 纠偏结论与范围

### A.1 原目标不变，检索对象改正

- **目标是找商户，不是找巡店任务。** 先在统一商户数据／索引中检索，再按需要关联用户当前可见的作业信息。批次、片区、网格是作业关联与展示维度，不是商户名称检索的必选分区。
- 当前旧路线通过入口网格的 `ctx.main.id` 找到同一批次的授权网格，再检索 `bd_store_task.snapshot`。这是“同批次跨网格作业搜索”，不是“跨批次商户搜索”。它不再作为本次商户搜索的目标架构。
- 生产恢复库中的 **278,730 是任务行数**。它的超时是旧作业搜索路径的失败证据，不能替代统一商户检索的性能基线，也不再以“优化这条全批次任务 SQL”为主线。
- **唯一商户结果与可见作业关联分开建模。** 商户只检索一次；同一商户关联多个任务不复制成多份商户搜索文档，不按任务数抬高命中率。统一索引不意味着所有账号都可访问全库：商户可见性沿用已有授权规则，规则不明确时先确认，不能以本次改造暗中授予全库权限；任务状态和操作仍按具体任务逐次鉴权。

### A.2 数据源与两级样本

| 对象 | 已核对来源／数量 | 本计划中的角色 |
|---|---|---|
| 统一商户候选数据 | `store_settle` 数据库的 `public.kanto_merchants_v20261029`，冻结样本620,280条 | 本轮已确认候选语料；实施时经源映射访问，不把版本化表名散落到调用方。不擅自引入外部商户库 |
| 二级查询样本 | 同库 `public.store_entities.name_local`，冻结113,774条主档 | 固定查询／评估集；不是批次，也不因为名称匹配而自动合并到商户表 |
| 一级真实样本 | 生产搜索日志及后续明确反馈 | 按旧请求实际范围重放作历史诊断；另报新商户检索结果，不把扩大检索语料的增益全记为算法增益。缺目标／定位的历史请求保持unknown |
| 巡店任务 | `bd_store_task` 及网格／片区／主任务关联 | 搜索后可见关联、分类、状态、跳转和写权限；不是商户检索语料或全量召回分母 |

`store_settle` 是数据库名，不是这里的商户表。先核对来源标识唯一性和缺失情况，再定义可持久重建的商户搜索文档ID及源映射；不得用任务ID、行号、ctid充当商户ID。来源标识重复／缺失时保留来源记录并显式处理身份歧义，不按归一名称自动合店。旧离线样本键仅用于评估，不能未经审计直接升级为业务身份。

### A.3 不变的验收目标与证据边界

1. 固定113,774条主档对620,280条候选，**名称候选覆盖率严格超过50%**：至少56,888条。原文基线24,393（21.44%），NFKC＋小写＋去空白基线36,468（32.05%），分母不去重、不删难例。
2. 已有离线实验57,214（50.2874%）保留为证据，不宣称已完成新运行时接入；需确认其算法、语料、阈值、候选上限与新运行时一致。若这些因素未改变，复用既有证据，不重复无关实验；改变则只复算受影响项。
3. 同时报告单候选、多候选、TopK、候选膨胀及新增候选误召回审查。不能通过任意共有类别词、无限候选、降阈值凑覆盖。未标注时准确率未知，名称命中不等于同店确认或真实搜索成功。
4. 一级无目标标注请求不要求用户回忆历史分店；不伪造“找到”反馈。生产日志真实成功指标在有有效反馈后单独统计。
5. 不洗／合并业务库，不改结算四表，不自动建立主档—商户关系，不创建巡店记录，不读取真实 `raw_records`。允许增加可重建的搜索派生投影／索引，但须独立于业务真值并显式迁移。

## B. 最小竖切：一条真实商户搜索闭环

**交付物：** Nest商户检索服务及独立契约 → 员工端调用 → 商户级结果及服务端命中证据 → 可见网格／片区关联分类 → 商户级搜索日志与反馈 → 同规模验收报告。默认按网格分类，可切换片区；反馈保留抽屉上方的紧凑展示。不是只交付离线覆盖报告，也不是继续扩大任务查询范围。

| 步骤 | 最小改动／预期目标 | 验证条件 | 依赖环境与前置条件 |
|---|---|---|---|
| M1 固定检索边界 | 核对候选表字段、商户稳定身份及源映射、现有商户查看权限、客户端实际入口；输出商户与任务两套身份契约 | 文档ID不含任务／批次身份；同一商户多任务仍只对应一个商户结果；缺失／重复源标识有明确处理；不扩大数据权限 | 本地Nest源码、获准读取的商户字段及冻结快照；身份或授权规则不明则先澄清 |
| M2 建最小检索实现 | 复用已验收名称策略，建立独立商户检索服务与可重建派生投影／索引，索引覆盖获准语料；请求不依赖入口批次／任务快照 | 名称、全半角、假名兼容及已有候选规则按证据分层；服务端返回商户ID、匹配类型、命中字段／词、策略与语料版本；每次请求不得全量扫描任务、复制全部商户到Node或冷建全量索引 | M1；优先现有PostgreSQL，实际索引能力先在隔离环境验证；不预设必须新增搜索引擎 |
| M3 分离作业关联 | 先取得商户结果，再按当前账号权限关联作业；分类统计基于完整商户命中集合与可见关联，分页与分类筛选口径一致 | 默认网格／切片区；同店多任务不重复商户命中；多个分类的计数可重叠，不能直接相加当商户总数；无可见作业关联单列，不标成“商户未找到”；关联查询为常数条、不逐行查权限；跨账号、改派后不泄露任务 | M2；既有任务／网格／片区映射与鉴权。批次如被显式选作作业关联筛选，不改变基础商户召回 |
| M4 接入页面与反馈 | 员工端调用新商户契约；React只按服务端证据高亮；详情区分商户资料与具体作业，写入沿用原任务入口 | 普通／无结果／弱相关／无可见作业均有明确状态；原有任务详情、历史快照与focus定位保留；写权限按目标任务复核；反馈条位于抽屉上方，不提交巡店记录 | M2–M3；现有Vite8002、Nest3000；旧任务接口保留兼容，新返回不能冒充旧任务列表 |
| M5 采集与对照 | 单独记录商户搜索范围、商户结果ID、语料／策略版本、耗时及反馈；任务关联信息独立记录 | 不把商户ID塞进store_task_id，不把商户全库数量塞进total_in_grid；旧日志原样保留；区分旧任务范围与新商户范围；历史unknown保持未知；业务反馈不能伪造成功 | M1–M4；复用既有日志设施，按真实契约选择最小新增／兼容迁移，不机械执行旧003–006全套 |
| M6 验收并形成新候选 | 固定样本覆盖、质量审查、完整语料性能与员工端关键流程通过后，再制作新提交／tag和最小发布包 | 覆盖≥56,888；新商户链路而非旧任务链路验收；B节语义及D节门槛通过；不复用被禁止部署的旧包 | M1–M5；隔离库、完整冻结语料、既有测试与浏览器设施、受控候选环境 |

**最小竖切不包含：** 独立搜索集群、付费模型、向量检索、自动实体合并、品牌知识库、全站入口重构或新增业务作业。这些只有在下列完整路线的证据门槛触发后才实施。

## D. 验证门槛与停止条件

- **正确性：** M1–M5的身份、权限、去重、分类／筛选、分页、高亮、历史快照、反馈语义均有相邻回归。商户主结果不依赖批次；同商户增加任务不改变纯商户名称召回。商户名称匹配不自动赋予作业权限。
- **覆盖与质量：** 固定113,774／620,280语料下覆盖≥56,888，报告单／多候选及候选膨胀；对新增候选分层审查，误召回未完成审查则不能仅凭50.2874%宣布整体完成。
- **性能：** 测完整620,280条商户语料和真实可见关联分布，含普通命中、无结果、宽词、归一／兼容、弱相关、分类筛选及分页。先建立新商户链路基线，再在同机、同配额、相同查询集对照；冷启动、索引构建与稳态请求分别计时。计划服务端目标为5并发、至少200次请求下P95≤1秒、P99≤2秒；这是待实测的验收目标，不是已达成事实。关联分类和可选关联检索也纳入相应请求计时；不能只测索引核心。完整结果统计必须正确，无数据库／名称Worker超时，无OOM。若未达标，先定位存储、算法、关联或序列化瓶颈，不能提高超时或放宽指标冒充通过。
- **环境与验证范围：** 日常 `pnpm dev`，本地业务库保持只读；写回归用现有随机隔离库。按受影响模块顺序运行相关测试、typecheck、build一次；浏览器把新搜索、分类、高亮、详情与反馈关键状态合在一次脚本验收。纯计划更新只校对diff、事实和链接。
- **发布停止条件：** 身份／商户权限未定、候选质量未审、同步删除不一致、性能未达标、索引服务依赖未就绪、候选／回滚未通过均不得上线。旧路线测试或旧API健康不能替代新链路验收。

## E. 环境与发布路径

- 开发：现有React员工端8002、Nest API3000，按需现有Worker；不为小改重建Docker。隔离测试沿用项目运行器，不在统一业务库写fixture。

### 3.3 指标、收益报告与门槛

两级独立出表，不合并命中率或用大量二级样本稀释一级失败。每张收益表记录样本/数据hash、旧新策略版本、样本资格、分母、unknown数、新旧值、绝对增量/百分点、同条件延迟与退步样本。生产无结果日志只能直接证明有结果率，不能直接证明正确召回或排名。

- 一级有结果率：首屏有效关键词请求中matched_count>0的比例；按筛选、scope和过程拆分，保留同词重试的请求分母，不能与去重/过程分母混用。
- 一级首位命中率：经确认且目标在范围内的查询，第一条为正确目标的比例；同时报告过程首次查询与请求级结果。
- 二级名称候选覆盖率：候选数>0的主档记录数/冻结主档总记录数；另报去重名称口径、增量覆盖、多候选分布，零候选不等同真实负例。只有核实子集才能报告正确Recall@10、首位命中率及MRR@10。
- Recall@10：有预期商户的查询中，前 10 条含任一正确结果的比例；按字符、读音、错字等类别分别统计。
- MRR@10：第一个正确结果名次的倒数，超出前 10 或无结果计 0，再取平均。
- 零结果率：仅统计首屏有效关键词搜索；按原因分组，不能把空网格或权限限制当搜索算法失败。
- 错误召回：负例是否返回貌似相似却不相关结果；至少使用 20 条负例检查。短词禁用宽松纠错，编号不自动纠错。
- 延迟：分别记录 API、SQL/引擎、应用处理和浏览器时间，报告 p50/p95、样本数、并发和数据规模；同机同库同条件对照。
- 数据正确性：权限泄漏 0、无重复/漏页、计数一致、原始业务字段变化 0。权限限制不能为提高召回率放宽。

以下量化门槛是本方案的拟定验收标准，不是现有实测值：最小竖切标准化样本 Recall@10=100%，留出集 MRR@10 不低于基线；完整方案留出集 Recall@10≥95%、MRR@10≥0.85，编号精确命中首位率=100%。上述正确召回/排序门槛仅适用于已标注目标的一级和二级核实子集，分别验收；不要求所有历史主档达到95%候选覆盖。二级至少保留原文精确和归一精确两条召回路径，不丢失同快照既有候选，新增模糊/别名候选单列；尚无证据设定二级整体覆盖增长承诺，V0复算后按未匹配原因确定可改善子集及目标。每类单列，核心字符类不得退步；错误召回负例至少 95% 正确判空。真实人工“是否找到”率作为上线观察项，样本不足时不硬算提升百分比。

性能拟定目标：固定本地代表性数据、热身后至少 200 次查询、5 并发，搜索 API p95≤300ms 且无关键词列表 p95 相比基线增加不超过 10%；补全接口 p95≤150ms。未达标先拆解瓶颈，不直接添加缓存。目标修改须记录依据和对用户体验的影响。

## 6. 文档模型、排序和一致性约束

搜索投影以店铺任务为文档单位：`storeTaskId`、`gridTaskId`、`storeId`、快照原文、归一名称/地址/编号、aliases、kana、romaji、sourceHash、sourceVersion、normalizerVersion。实时状态和当前权限以数据库为准；引擎可存过滤副本但不独立授权。坐标及实体扩展字段只有在确认与当前详情/任务快照口径一致后才入索引。

排序使用可解释的分层规则，先确定匹配层级，再比较层内分数；不要用任意相加分数让多个地址弱命中压过一个编号精确命中。地理距离只作相关性同级的辅助，无关键词沿用现有距离顺序。最终以唯一任务ID打破平分；客户端展示名称仍来自原始快照。

归一化不能只做应用侧：PG查询、投影回填、增量写入和外部引擎必须使用同一版本规则及契约样本。NFKC不等于简繁或日文新字体转换；中文高岛屋匹配高島屋由有出处的别名覆盖，避免全局汉字映射误召回。去空格字段用于召回，原始词界信息另保留给多词排序。

分页采用现有页码契约时，以查询/索引版本保持稳定，重建切换后旧分页会话提示刷新；若需cursor必须同步改契约和React。高召回算法如限制候选，只能返回明确的候选数或hasMore，不能把截断候选数冒充全量total。默认保留精确total语义；引擎与数据库不一致时降级到同一PG查询生成items/total。

## 8. 方案选择依据与官方参考

- PostgreSQL `pg_trgm`：三元组相似度、GiST/GIN及LIKE/ILIKE索引支持；模式无法提取有效三元组时可能退化为全索引扫描。因此短日文词必须单独测，不保证任意错字都有效。<https://www.postgresql.org/docs/current/pgtrgm.html>
- OpenSearch Kuromoji：日文形态分析、基本形、读音及补全组件；使用前需安装`analysis-kuromoji`。本项目完整引擎路线优先评估它，但以F6为准。<https://docs.opensearch.org/latest/analyzers/language-analyzers/kuromoji/>
- Meilisearch：可配置typo tolerance；编号字段和短词需配置保护。轻量候选之一，不把默认容错等同于中日文搜索已达标。<https://www.meilisearch.com/docs/capabilities/full_text_search/relevancy/typo_tolerance_settings>
- Typesense：不同数据类型有不同搜索配置，尤其编号和普通名称；作为另一个轻量候选，不与Meilisearch重复落地。<https://typesense.org/docs/guide/tips-for-searching-common-types-of-data.html>

来源核对日期为2026-11-12；具体发行版、许可证、插件兼容与部署资源在F6锁定，不在此编造性能/成本结论。
