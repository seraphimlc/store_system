## 3. 目标工程与运行结构

```text
apps/
  admin/       管理端 React 独立项目
  staff/       员工 H5 React 独立项目
  server/      NestJS API、认证、业务模块、MCP 适配
  worker/      TypeScript 空间算法、批处理和脚本执行入口
packages/
  contracts/   API 类型、枚举、输入输出约束
  i18n/        中日文资源
  domain/      API 与 Worker 共用的业务规则
  geometry/    投影、空间索引及几何算法
 deploy-next/  新系统 Docker/Nginx 配置，不覆盖旧 deploy/
```

新服务按业务模块组织为单体，不拆业务微服务。是否使用外部队列以实际任务持久化需求决定，不默认增加 Redis。

| 容器/产物 | 职责 | 暴露范围 |
|---|---|---|
| gateway | Nginx + 管理端/员工端 HTML；代理 API/MCP | 本地仅绑定 `127.0.0.1:8080`；生产经既有 HTTPS 入口 |
| api | NestJS 普通业务接口、认证；MCP 可同镜像独立入口 | Docker 内网 |
| worker | 独立进程执行重任务，与 API 使用同一版本业务包 | Docker 内网；无公开端口 |
| db（本地 profile） | 独立 PostgreSQL 验收副本 | 默认不公开端口 |
| OSS/CDN | 公开的前端构建静态资源 | HTTPS |

生产连接现有数据库，不重建或替换数据库容器/卷。原始导入文件、私有照片和既有业务附件单独挂载，不能混入公开前端资源目录。

路由：`/admin` 规范跳转至 `/admin/`；`/admin/*` 回退管理端 HTML；员工已登记路由回退员工 HTML；`/api/*`、`/mcp`、OAuth、发现接口、健康和文件下载先匹配服务端规则，不能被 SPA 回退吞掉。不存在的资源返回 404，不能返回 HTML。旧管理路径的兼容映射在 P0 明确，避免与员工路径冲突。

## 4. 本地构建与一条命令部署

### 4.1 配置与凭证

用户提供配置后填写未跟踪的本地配置文件；仓库只提交变量名、校验规则和脱敏示例。

| 配置组 | 需要内容 |
|---|---|
| OSS | endpoint、region、bucket、限定资源目录前缀、凭证来源（优先临时凭证/本地凭证链） |
| CDN | HTTPS 资源域名、目录映射、缓存规则；是否有鉴权、跨域或 Referer 限制 |
| 本地 | Docker context、验收库连接、副本来源、入口端口、文件卷路径 |
| 生产（后续） | 已有部署主机与架构、镜像分发方式、目标目录、数据库/文件卷连接、HTTPS 入口 |

凭证不得写进前端、HTML、source map、构建参数层、镜像或发布清单；服务端配置通过运行时 env/secret 注入。配置校验只输出缺少的键名。

### 4.2 拟定命令契约

以下是 P2 要实现的命令接口，当前不可直接执行：

```bash
pnpm release:build -- --env local --assets local
pnpm release:deploy -- --env local --release <release-id>

# OSS/CDN 配置接入后；仍从本地执行
pnpm release:build -- --env local --assets cdn
pnpm release:deploy -- --env local --release <release-id>

# 完成验收后，从本地向生产部署同一份已验收产物
pnpm release:deploy -- --env production --release <release-id>
pnpm release:rollback -- --env production --release <previous-release-id>
```

- `build`：锁定依赖安装、适用检查、前端构建、API/Worker 编译、本地 Docker 构建及发布清单生成。阶段验收复用同一提交与配置已有检查结果，不无故重复跑已通过的全套检查；代码或构建参数变化必须重新生成对应产物。
- `deploy`：校验产物与配置，上传该 release 的公开资源，验证 CDN，再加载/拉取本地已构建镜像、启动候选服务、检查就绪，最后切换流量。任何前置失败保持当前版本；不现场修数据。
- `rollback`：恢复上一套 HTML、API、Worker 和路由配置；不回滚数据库或删除业务数据。
- 同一目标只允许一个部署命令执行；命令使用失败退出码，提供明确的失败阶段与继续方式，禁止用管道丢失错误。

### 4.3 产物与资源版本

release ID 使用提交标识与构建标识，工作区有未提交修改时禁止生成生产 release。本地开发可明确标记 dirty，不能晋升生产。

发布清单记录：提交、锁文件摘要、构建时间、目标 CPU 架构、各镜像 digest、HTML 校验和、CDN 前缀、资源路径/大小/哈希及兼容版本。环境密钥不进入清单。

- CDN 路径采用 `<prefix>/<release-id>/admin/…`、`staff/…`，文件使用内容哈希；不覆盖旧 release，不自动删除旧资源。
- HTML 使用 `Cache-Control: no-cache`，不进入 CDN；哈希资源使用长期 immutable 缓存及正确 MIME。
- ESM、字体等按实际请求设置 CDN CORS；验收动态 import、字体、懒加载图片与错误页，不能只验首页主 JS。
- source map 不公开发布；调试产物本地保留。压缩交给网关/CDN约定处理，禁止错误 Content-Encoding 或重复压缩。
- 两个前端路由基路径与资源前缀独立配置；通过构建后的 HTML、CSS 和动态 chunk 清单校验，不能仅替换 HTML 字符串。
- API 使用相对同源 `/api`，前端不嵌入环境域名；本地与生产复用同一 release 的前提是共用可访问的 CDN 前缀，否则必须作为不同产物重新验收。
- 处理长时间打开的旧页面：保留旧 chunk；部署后旧页面与新 API 兼容，无法兼容的流程需提示刷新并保护未提交输入。
- 本机与服务器架构不同时，本地 buildx 构建目标架构并验证；不能把本机 ARM 镜像直接部署到 x86 主机。
- 镜像可经仓库按 digest 分发或以 OCI/压缩归档加载，P2 根据已有设施选一种，服务器不执行 build。

### 4.4 部署顺序与失败行为

1. 校验 release 清单、目标、配置、可用磁盘、端口与镜像架构；输出脱敏摘要。
2. 上传该版本全部前端资源，按清单核对对象元数据；从 CDN 验证关键资源可读、MIME/CORS正确，且路径与哈希匹配。
3. 分发并启动候选 API/Worker，不接管线上写请求；Worker 默认暂停取任务，避免新旧同时执行。
4. 就绪检查包括数据库连通、必需配置、文件卷可读写条件；候选阶段使用只读检查，不制造业务记录。
5. 切换前停止接收旧系统新写请求，等待在途事务和任务结束；暂停旧 Worker。不得让两个版本同时消费任务或重复登记发薪。
6. Nginx 配置校验成功后切换该版本 gateway/上游，启用新 Worker，验证匿名入口、授权拒绝、静态资源和只读业务页。
7. 若切换失败，停止新写入口及 Worker，排空或确认事务状态，再恢复旧服务；无法确认已提交写入的兼容性时保留停写并报告，不盲目切回。
8. 保留旧镜像、清单和 CDN 资源。输出 release ID、入口、耗时分段、检查结果和回滚命令。

本地无外网配置时允许 `--assets local`，由网关提供哈希资源；最终验收必须再通过真实 OSS/CDN 路径。测试库复制恢复是显式独立步骤，`deploy` 永不自动恢复数据库。
