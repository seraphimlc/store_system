### 5.5 ✅ 已修：「该扣多少」三个页面三个数（2026-10-17 定位并修）

用户报「小川逸薪资不对 / 是不是把 8 月的找平又扣了一次」→ **确实会重复扣，已修**。

**修前**同一件事三处不一致：

| 出处 | 2026-10 显示 | 读的是 |
|---|---|---|
| 绩效页「找平金额」 | ¥−1,889,000 ← 用户看到的 | 链子 `payroll_period_rows.prev_adjust_amount` |
| 薪资找平页「上年修正」 | ¥−1,741,000 | 同上，且只汇总**当月有行**的人 → 又漏一部分 |
| 找平表 `payroll_adjusts` | ¥−1,386,250 | **账表（正确）** |

**根因**：链子是**生成那一刻的快照**，只算「当月 diff + 未发薪期的可吸收额度」，
**不反映此后实际发生的回收**。8 月那两笔在 9 月发薪时已经扣掉了
（账表里 8 月 `remaining=0 / status=settled`），可 9 月的链子仍写着 −1,889,000
（= 9 月自己 −1,296,500 + 8 月**已经扣过的** −592,500）。

⚠️ **不只是显示错：`record_payment`（真正扣钱的）读的就是这条链子** →
10 月一发薪就按链子扣 → **全公司多扣 ¥592,500**，共 **44 人**。
小川逸（`2188240606634082`）链子 −102,500 vs 账表 −44,250 → **多扣 ¥58,250**，
他那上半月 **88,000 工资会被整笔划走**。（修前 10 月尚无发放记录，未造成实际损失。）

**修法**（`app/services/period.py`）：新增 `prior_debt_map(db, month)` =
`payroll_adjusts` 里 `source_month < month` 且 `status='in_progress'` 的 `remaining` 合计，
作为**"该扣多少"的唯一权威**，三个消费方全部改读它：
1. `record_payment` 的 `carry`（**扣钱**）；
2. `period_rows` 的 `prev_amt`（薪资找平页）；
3. `carry_map` 的金额（绩效页）。

顺带：`record_payment` 不再另减"本月已扣额"（账表已逐笔冲销，再减就重复）；
溯源改为指向**最老的那笔未结清找平**（与 FIFO 冲销口径一致）。

### 5.9 🔴 P0 已修：找平「已实扣」从应付里消失（2026-10-17，钱差点付错）

**用户报**：10 月巡店记录刚导入、**还没发工资**，很多人的工资算错
（例：王俊岩页面 262,750，应为 259,500）。

**根因**：绩效页「找平金额/应该付金额」两列与**发薪表导出**共用
`period.carry_map()`，而它**只读 `payroll_adjusts.remaining`**。欠款一旦被
**本月的发放**回收，`remaining` 归 0、status 变 `settled` → 「已经扣掉的那部分」
从公式里消失 → 应付虚增回毛额。回收记录其实就在 `payroll_settlement_links`，
只是没人读它。

**实测口径（2026-10，56 人）**：

| 量 | 金额 |
|---|---|
| 上半月毛额（56 人，seq1 全部已登记） | 6,036,000 |
| 9 月偏差合计 | **−1,386,250** |
| ├ 已被 10-16 登记的发放实扣（34 人） | −966,750 |
| └ 仍未回收（3 人上页 −244,750 + 21 人无 10 月工资行 −174,750） | −419,500 |
| **修前** 页面/导出「应付」合计 | **5,891,000**（虚增 821,750） |
| **修后** = 台账 `payroll_payments` 实付 | **5,069,250** |

**修复**：`carry_map()` = `payroll_settlement_links`（本月已实扣，**按发放月归属**）
+ `prior_debt_map()`（仍未回收）。两处天然不重叠（已回收部分已从 `remaining`
扣走），相加正好 = 该人本期应承担的原始偏差。
用生产数据逐人验证：**修正后 56/56 与台账完全一致，0 人不符**。

**守门测试**（先变异验证：改回只读余量 → 恰好这 2 条红）：
`test_period.py::test_carry_map_keeps_amount_already_recovered_this_month`
/ `::test_carry_map_does_not_double_count_partial_recovery`。

**顺带查出（未修，需拍板）**：**周期行会被重算，付款快照不会** —— 2026-09 有
**25/44 人** `payroll_period_rows.half1_amount` 与已登记付款的 `amount` 不再相等
（9 月数据在登记后被重导重算过）。台账"不可改写"是设计，所以两者永久分歧；
回看历史月应以台账为准。2026-10 当时 **0/56** 分歧。

**同一坑的三个面（都别踩）**：只读链子 `prev_adjust_amount` → 已冲销的**再扣一次**
（2026-09 链子 −1,889,000 vs 账表 −1,296,500，即原 2026-10-17 修的坑）；
只读 `remaining` → 已扣的**凭空消失**（本次事故）；
**正解 = 已实扣 + 未回收**。⚠️「登记发薪」(`record_payment`) 一直读
`prior_debt_map()`，**台账从来是对的**，错的是展示/导出层 —— 但导出就是
"照此列发薪"的依据，所以同样是钱的问题。

scripts/mcp_restart.sh                                    # 改 mcp_service 后必须重启（自校验 27 工具）

  docker compose up -d --no-deps web mcp"     # ⚠️ mcp 必须一起建

ssh store-prod "rm -f /opt/store-settle/current; ln -s /opt/store-settle/releases/<上一个TS> /opt/store-settle/current; \
