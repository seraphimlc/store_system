**实测（2026-10-17 14:0x，线上 dump = 当天的库）**：54 张表**逐表 `COUNT(*)` 全对齐**
（PG 与 MySQL 都是 **323,001** 行），另抽查 5 组**金额聚合**全部一致（月绩效 人数/点数/工资、
发薪台账 笔数/金额、找平未回收 人数/欠款、任务 总数/已派队、正式记录按日本月）。

**脚本 `scripts/pull_prod_to_mysql.py`**（psql `\copy` 读 → SQLAlchemy 写）踩到并处理了 5 个坑，
都是"MySQL 和 PG 不一样"的真实差异，改脚本前先读它的 docstring：

1. MySQL 不允许 `TEXT/JSON` 列有**默认值** → 建表前摘掉 17 列的默认值。
2. MySQL 的 `TEXT` 只有 **64KB**，而 `rebuild_snapshots.payload_json` 实测单值 **7.6MB** →
   `Text` 一律建成 `LONGTEXT`。
3. **PG 部分唯一索引**（5 个，如 `bd_station` 的同名站"仅当 `line_id IS NULL` 才唯一"）
   MySQL 不支持 → `create_all` 退化成**全表唯一**，然后拒绝线上合法数据
   （实测 `Duplicate entry '印旛日本医大'`）→ 这 5 个索引在副本里不建。
4. SQLAlchemy 2.0 + pymysql 的 `executemany` 喂**元组**会**串列**（`bd_ai_summary` 编译 9 列、
   实际只发 5 列且带默认值）→ 一律用**字典**行。
5. `csv` 默认单字段上限 128KB → 放开。

**⚠️ MySQL 副本只用来"看/查"，别拿它跑应用**（方言差异：`func.substr`、`Date` 比较、
`batch_alter_table` 等）；应用与测试仍走 SQLite，迁移彩排必须走 **PG + 线上 `deploy-web` 镜像**
（本次 `f0a1b2c3d4e5` 就是这么彩排的：临时 `postgres:17` 容器 + 生产 dump + `docker run … alembic upgrade head`，
见 §5.12）。数据是**生产数据（含人名）**→ 只落本机、别提交、别外传。

**一、动钱 / 安全（4 项）**
