## 一、产品定位与设计原则

巡店业务每天产生大量 Excel 巡店记录（每员工每天几十家店）。系统把「原始 Excel → 员工结算」整条链路搬到线上：**看得见**（每行都有原因）、**查得到**（全程留痕）、**改有据**（改判/申诉/对账留痕）。

1. **默认全部认可、只留申诉**：被滤记录默认认可，员工只主动申诉；未决申诉是入表硬门槛，保证正式表永远是「最终裁定口径」。
2. **判定即定稿**：上传即判定，每行打标写明原因；判重规则稳定（月窗口 + 店名归一 + 组内优先级）。
3. **对账自动、差异可解释**：按员工×天比对，差异自动归因，可下载留档。
4. **工资规则简单固定**：每点 250 円 + 每满门槛点奖 3,000 円（按月可配）；37% 仅展示。

## 三、端到端主流程（V3 定稿）

```
上传 Excel（可多文件）
  → upload_and_store（sha256 同内容拒传）→ parse_file → raw_records（原样底账，永不改动）
  → process_import 逐文件判定（§五）→ 每行打 clean_status
  → 绩效确认（员工申诉 → 管理员认可/驳回；未决申诉 = 入表门槛）
  → finalize_import 入正式表（重建该文件 formal_records + 同步 person_daily_stats）
      ├─ 入表后申诉认可/改判 → 「重新入表」补入（valid≠formal 时出现）
      └─ 同月补传/整月口径变化 → 「月度重算」重建整月（保护已认可申诉）
  → 绩效与工资（月绩效 + 日明细[默认最新一天，日期/员工可筛] + 工资 + 导出）
  → 月度对账（上传对账文件 → 任务化 → 人×日比对 → 归因 → 找平 → 报告/下载）
```

## 四、数据模型概要

- **账号/员工**：`users`（role/status/must_change_password/person_code）、`persons`（code/display_name）。
- **数据源**：`imports`（file_name/sha256/status）、`raw_records`（原始列 + 判定列 `clean_status`/`confirm_state`/`filter_reason`）。
- **店铺主从档**：`store_entities`（`store_id_raw` 唯一；`name_local`/`name_norm`；主档 `master_id` 自指）、`store_pairs`（候选对 exact/fuzzy）、`store_merge_logs`（合并留痕）。
- **正式与绩效**：`formal_records`（人/店/日本日期/点数/来源）、`person_daily_stats`（人×日日结算点）、`appeals`（申诉）、`month_perf_records`（月绩效物化）。
- **工资/找平四表**：`payroll_period_rows`（应发快照，可重算）、`payroll_payments`（**实发台账不可改写，导出即登记**）、`payroll_adjusts`（**找平进度唯一权威**，跨月债务读 `remaining`）、`payroll_settlement_links`（发放↔找平核销）；`adjust_records` 是**点数纠偏留痕**（锁存单价、次月生效），**不是债务权威**。
- **对账**：`recon_tasks`（kind/status/params/summary）、`recon_data_rows`（全量人×日×点）、`recon_day_rows`（仅问题行）、`recon_results`（人月差异）。
- **已清理**：旧版表模型类已从代码删除（task_runs/clean_records/person_stats/daily_*/settle_amounts/review_flags/self_report_*/confirm_tasks/manual_decisions）；线上历史表仍在但无 ORM 访问。
- **关键枚举**：`clean_status` = valid / master_late / from_sub / cross_file_dup / visible_blank / no_ref；`confirm_state` = pending / approved / disputed / auto_ok / auto_approved；`recon_tasks.kind` = person_points / daily_records / monthly_v3；`recon_day_rows.side` = both / local_only / report_only。

## 五、文件上传与判定规则（核心）

### 5.1 上传
可一次传多个文件；**同内容（sha256）拒传**（DuplicateUpload）；自动识别表头/起始行，列名匹配 Store ID / Store Name-Local / Modified Time / Submitter / Record ID / A+ POSM Visible / Deploy / 标准点数 等。

### 5.2 逐行判定（clean_status）
| 状态 | 含义 | 入正式表 | 可申诉 |
|---|---|---|---|
| valid | 有效记录（组内胜出） | ✅ 自动 | — |
| master_late | 同店名、同结算月、非组内胜出（同店跨日被顶替） | ❌ | ✅ |
| from_sub | 从档（同店不同编号被归并） | ❌ | ✅ |
| cross_file_dup | 同日同店跨文件重复（同一条导出两次） | ❌ | ❌ |
| visible_blank | A+ POSM Visible 为空（非候选） | ❌ | ❌ |
| no_ref | 空 store_id 或空店名 | ❌ | ❌ |

### 5.3 去重口径（定稿，勿改）
- 窗口 = **结算月**，跨月行**永不互相压制**（7/31 与 8/1 同店不算重复）。
- 键 = **（归一店名，月份）**；**2026-09 起店名**做 **NFKC（全角→半角）+ 去半/全角空格 + lower** 归一（`flow._norm_name`）；历史月沿用原始店名 trim。
- 组内保留优先级（2026-09 起）：① `deploy=YES`（→2 点）② `visible ∈ {OTHER, AUDIT_SUCCESS, YES, NO}`（→1 点）③ 其余（→0 点，不入表）；同级取 `modified` 完整时间戳最早。历史月取最早。
- 可见性候选口径来自该文件布局 `value_map.visible`（`rules.visible_is_candidate`）；非候选行不参与分组。

### 5.4 主从档
同一真实店铺多个 store_id → 归一为一个实体（`store_entities`）：主档 = 该店最早出现的编号，从档行判 `from_sub`；exact 自动合并、fuzzy 可 AI/人工合并并留痕。**判定不依赖主从关系**（主从档用于展示/追溯/人工调档）。

### 5.5 点数（1点/2点）
日期 ≥ **2026-07-09** 且 `Deploy=YES` → 2 点，否则 1 点；文件带「标准点数」列 → 以该列为准；月点数 = 该员工当月有效店点数之和。

### 5.6 员工自动建档
出现新的人员编号 → `persons` 自动开户；`users` 登录名按姓名拼音生成（pypinyin），初始口令统一，首登强制改密。

## 六、申诉与绩效确认

- **可申诉**：`master_late`、`from_sub`（员工「我的申诉」提交，带理由）。
- **默认全部认可**：被滤记录默认 `auto_ok`，不打扰员工。
- **管理员处理**（绩效确认页）：认可 → raw 改判 `valid`（`confirm_state=approved`），下次入表计入（+点数）；驳回 → 维持滤除并定案（`auto_ok`，不可再申诉）；留痕 `handled_by/handled_at/reason`。
- **硬门槛**：文件存在 pending 申诉 → 整个文件不能入表（含 valid 记录一起等）；月度重算同理（当月 pending → 拒绝）。处理完（认可/驳回都算）后一次性入表。
- **入表后新申诉**：员工随时可申诉 → 认可后 `valid > formal` → 绩效确认页出现「重新入表(N)」补入。

## 七、正式表三动作

| 动作 | 粒度 | 行为 | 何时用 |
|---|---|---|---|
| 入正式表 `finalize_import` | 单文件 | 按该文件最新 `valid` 重建（先删后插，幂等）+ 同步 `person_daily_stats` | 上传判定后、申诉处理完后 |
| 重新入表 | 单文件 | 同上（`valid≠formal` 时按钮出现，提示补入 N 条） | 入表后申诉认可/人工改判 |
| 月度重算 `rebuild_month` | 整月 | 重判覆盖该月所有文件（防同月补传双算）、**保护已认可申诉**（重判后恢复 valid）、重建整月正式表+统计表 | 同月补传、申诉改判、对账找平后 |

- 门槛：有未决申诉 → 拒绝并提示；幂等可重复。
- 正式表每行 = 一条有效店记录（人/店/日期/点数/来源），是绩效、工资、对账的**唯一权威**。

## 八、绩效与工资

### 8.1 月绩效
每人：有效店数 / 1点店 / 2点店 / 总点数 / 工资 / 上月找平 / 应付合计（含找平）/ 2点成功率（达标 37% 徽标）。

### 8.2 工资规则（定稿·2026-09 修订）
- **每点 250 円**（按月可配 `per_point`）+ **每满门槛点奖 3,000 円**（默认门槛 68 点；`BONUS_GROUP_SCHEDULE` / `BONUS_AMOUNT_SCHEDULE` 按月可配——当前 2026-09 覆盖为 **75 点 / 1,250 円**，属单月配置而非默认）。
- 奖金**整月滚动、不跨月**：`salary = 点数 × 单价 + (点数 ÷ 门槛) × 奖额`（整除），单点 ≥ 0 才算。
- 例（默认 68 / 3000）：2,326 点 → 2,326×250 + (2326÷68=34)×3,000 = 581,500 + 102,000 = **683,500 円**。
- 两期发薪：上半月 = `h1÷门槛×奖额`；下半月 = `(h1余 + h2)÷门槛×奖额`（上半月余点带下来，整月滚动不跨月）。

### 8.3 汇总卡
员工数 / 有效店 / 1点·2点店 / 总点数 ｜ 工资合计 / 上月找平 / 应付合计（含找平）/ 2点成功率。

### 8.4 日绩效明细
数据源 `person_daily_stats`（入表/重算时同步，与正式表逐日一致）；**默认显示该月最新一天**；日期、员工可筛选（不选=全部）；**只选员工 → 显示其全月**；切月清空筛选；员工端「我的绩效」同规则。

### 8.5 导出工资表 Excel
页签：月度绩效·工资（编号/姓名/有效店/1点/2点/总点数/工资/找平 + 合计行）、日绩效明细。

### 8.6 找平
月度对账确认的差异 → `adjust_records`（按源任务+人，锁存发生月单价）→ **下月工资加/减**（应付合计体现）。跨月债务以 `payroll_adjusts.remaining` 为权威（见 §9.7）。

## 九、月度对账（v3/recon）

### 9.1 任务化生命周期
上传 → `start_task`（pending）→ 后台线程离线执行（`run_task`/`launch_task`；测试环境 `RECON_SYNC=1` 同步）→ done/failed；失败在 `summary.error` 留因，可重传。

### 9.2 对账文件识别（guess_kind）
- `person_points`：表头含姓名+点数；`daily_records`：表头含 Store ID + Modified Time + Submitter（逐条明细）；其他 → `store_list`/`unknown`。
- `daily_records`：sheet 优先「最终有效/有效明细/有效数据」；列自动识别 Visible/Deploy/标准点数；点数按边界规则（同 §5.5）。解析出的日期只有 1 个值 → `single_date=True`，日级仅参考，**以人月差异为准**。

### 9.3 比对与问题行
- 本地侧 = `person_daily_stats`（人×日）；逐人逐日比对，差异（`diff≠0` 或仅一侧有）才写 `recon_day_rows`。
- `side`：both（两边都有但点数不同）/ local_only（仅系统有）/ report_only（仅对账有）；人月差异与「系统有而对账文件无」名单（`sys_only`）一并输出。

### 9.4 差异归因（确定性规则，系统自动）
行级按「店 + 时间戳」判定：`consistent` / `only_system` / `only_report`（按原因 `from_sub`/`master_late`/`cross_file_dup`/`no_ref`/`not_found` 拆分）→ `net` 净差；展示在任务页归因卡 + 报告「差异归因」页签。

### 9.5 AI 对账解读（可选）
按钮「生成/更新解读」→ 大模型读差异与归因输出中文说明并存档（模型/时间）；需配置 `AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`；未配置友好提示；失败不影响对账；**AI 只做解释、不拍板**。

### 9.6 同月重传 = 重新对账（版本化）
同月再上传 → 旧任务标 `replaced/replaced_by`，**保留可查**（「上一版」徽标）；新任务为当前（`version+1`）；找平关联不丢。

### 9.7 找平联动
- 差异确认 → `adjust_records`（锁存发生月单价，下月工资加/减）；可取消调整；配合月度重算同步口径。
- **跨月债务/找平进度的唯一权威 = `payroll_adjusts.remaining`**（发放时按 FIFO 冲销）；`payroll_period_rows.prev_adjust_amount` 只是生成时快照，**不作为扣款依据**。
- ⚠️⚠️ **"该月要扣多少" ≠ "该月还剩多少"（2026-10-17 生产事故，钱差点付错）**：
  绩效页与发薪表导出的「找平金额 / 应该付金额」两列走 `period.carry_map()`。
  它**只读 `remaining`** 时，欠款一旦被**本月的发放**回收就归 0/`settled`，
  于是"**已经扣掉的那部分**"从「应付」里凭空消失 → 应付虚增回毛额。
  实测 2026-10：9 月偏差合计 −1,386,250 = 已实扣 **−966,750**（34 人，10-16 登记）
  + 未回收 −419,500；页面/导出「应付」合计显示 **5,891,000**，而台账
  `payroll_payments` 实付 **5,069,250** → **虚增 821,750**（王俊岩 262,750 应显 259,500）。
  **正确口径 = `payroll_settlement_links`（本月已实扣，按发放月归属）
  + `prior_debt_map()`（仍未回收的余额）**，两处天然不重叠（已回收的部分已从
  `remaining` 扣走），相加正好等于该人本期应承担的原始偏差。
  守门测试：`tests_web/test_period.py::test_carry_map_keeps_amount_already_recovered_this_month`
  / `::test_carry_map_does_not_double_count_partial_recovery`。
  - 同一个坑的**两个反面**（都别踩）：只读链子 `prev_adjust_amount` → 把已冲销的**再扣一次**
    （2026-09：链子 −1,889,000 vs 账表 −1,296,500）；只读 `remaining` → 已扣的**凭空消失**（本次）。
  - 「登记发薪」本身（`record_payment`）读的是 `prior_debt_map()`，**台账一直是对的**；
    错的是**展示/导出**这一层 —— 但导出就是"照此列发薪"的依据，所以同样是钱的问题。
  - **两期发薪规则唯一实现 = `period.pay_plan()`**（绩效页 `settle_r` 与发薪表导出 `report` 共用）：
    上半月不够扣 → 本期发 0、余数转下半月。⚠️ 导出原来**不夹取**（会出负工资）、
    **下半月不显示找平**（余数凭空消失，可 `record_payment` 照扣）。
  - 另注：**周期行会被重算，付款快照不会**。2026-09 有 **25/44 人**
    `payroll_period_rows.half1_amount` 与已登记付款的 `amount` 不再相等
    （9 月数据在登记后被重导重算过）。台账"不可改写"是设计，所以两者会永久分歧；
    回看历史月时**以台账为准**。2026-10 当时 **0/56 人**分歧。

### 9.8 产物（Excel）——对账结果文件设计

**生成机制**：任务 done 时 `run_task` 自动 `build_report` 生成《月度对账报告.xlsx》并落盘 `uploads/recon_result_<task_id>.xlsx`（`params.result_path`）；任务页「下载对账结果」/「对账报告」直接返回该文件；**历史任务产物保留**，任何版本都可再下载。全流程系统自动产出，无人工环节。

| 页签 | 内容 | 出现条件 |
|---|---|---|
| 对账报告摘要 | 月份/来源文件/生成时间/生成人；系统正式口径合计（有效店、1点/2点、总点数、工资、上月找平、应付）；对账比对（人数/差异条数/反向名单数/问题行数/找平）；结论（0 差异 → 完全一致，否则见明细） | 总是 |
| 员工×日对账明细 | 日期/编号/姓名/本地点数/对账点数/差异/说明（点数不一致·仅本地有·仅对账有）——只列问题行 | 日级且存在 day_rows |
| 差异明细 | 人员/编号/系统点数/对账点数/差异(系统−对账)/应找平(円) | 总是（无差异写「无差异」） |
| 系统有而对账文件无 | 编号/姓名（反向名单，漏发风险人工核对） | 总是（无则写「无」） |
| 找平确认 | 编号/姓名/金额(円)/生效月份/原因/确认时间（留痕） | 总是（无则写「无」） |
| 差异归因 | 一致/仅系统有/仅对账有（按原因拆分）/净差 | summary 含 attribution |
| AI 解读 | 模型/生成时间/解读文本 | 生成过 ai_interpret |

## 十一、关键口径决策记录（勿轻易改动）

1. **判重**：结算月窗口 + **店名归一（NFKC + 去空白 + lower，2026-09 起）** + 组内优先级（deploy=YES / 1点候选 / 0点），同级取最早；跨月不互压。
2. **员工确认形态**：默认全部认可、只留申诉；未决申诉是入表硬门槛。
3. **工资**：每点 250 円 + **每满门槛点奖 3,000 円**（默认门槛 68，按月可配，当前 2026-09 为 75 点 / 1,250 円）；37% 仅展示。
4. **对账语义**：问题行 = 差异才存；归因按「店 + 时间戳」行级；「仅系统有/仅对账有」是口径差异（从档/重复/漏列），需人工判断。
5. **数据库**：生产 **PostgreSQL**（docker）；曾评估 MySQL 8 兼容但**已弃用该路线**，不再是待切换项。
6. **找平**：月度对账差异 → 下月工资加/减；跨月债务权威 = `payroll_adjusts.remaining`。
7. **重新对账**：保留历史版并标「上一版」可查。
