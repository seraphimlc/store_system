## 一、产品定位与设计原则

巡店业务每天产生大量 Excel 巡店记录（每员工每天几十家店）。系统把「从原始 Excel 到员工结算」整条链路搬到线上：**看得见（每行都有原因）、查得到（全程留痕）、改有据（改判/申诉/对账留痕）**。

设计原则（与万总对齐后定稿）：
1. **默认全部认可、只留申诉**：被滤记录默认认可，员工心智负担最小；员工主动申诉才进待处理。
2. **判定即定稿**：上传即判定，每行打标并写明原因；判重规则稳定（月窗口+店名+最早）。
3. **申诉是硬门槛**：存在未决申诉的文件/月份不能入表，保证正式表永远是"最终裁定口径"。
4. **对账自动、差异可解释**：按员工×天比对，差异自动归因，可下载留档。
5. **工资规则简单固定**：每点250円，满68点奖3,000円；37% 仅展示。

## 二、角色、权限与安全

### 2.1 角色
| 角色 | 权限 | 演示账号 |
|---|---|---|
| 管理员 admin | 全部管理功能（上传、判定明细、申诉处理、入表/重算、绩效、对账、店铺主档、员工管理、口令重置、导出） | admin/demo123 |
| 员工 staff | 我的绩效（本人）、我的申诉、修改密码 | 全员 demo123（ogawa=小川逸 等 34 个 8 月在岗账号 + 7 月特有账号） |

### 2.2 权限隔离机制（中间件）
- `STAFF_ALLOWED` 白名单：`/my/daily /my/password /static /healthz /login /logout /product /my/confirm /my/appeal /my/perf`。
- **已登录员工访问白名单外路径 → 302 /my/perf**（无论路由本身是否校验，中间件统一兜底）。
- **未登录访问任何业务路径 → 302 /login**（含 /staff-admin 等，已统一）。
- 管理端路由自身也带 `user.role != "admin" → 拒绝` 双保险（confirm-admin/对账/重算/导出/员工管理等）。

### 2.3 登录与口令
- 登录：用户名+密码（argon2 哈希），会话 cookie（ss token）；logout 需 CSRF。
- **首登/口令被重置 → must_change_password=True → 强制先改密**（除改密页与登出外全部 302 /my/password?must=1）。
- 管理员可批量重置全部员工口令为 demo123 并置 must_change=True（员工管理页）。
- 员工状态：active/leave/disabled/resigned；非 active 禁登录；数据永不删除。
- CSRF：所有写操作表单带 csrf_token（会话绑定校验）。

## 三、端到端主流程（V3 定稿）

```
上传 Excel（可多文件）
  → upload_and_store（sha256 同内容拒传）→ parse_file → raw_records（原样底账，永不改动）
  → process_import 逐文件判定（§5）→ 每行打 clean_status
  → 绩效确认（员工申诉 → 管理员认可/驳回；未决申诉=入表门槛）
  → finalize_import 入正式表（重建该文件 formal_records + 同步 person_daily_stats）
      ├─ 入表后申诉认可/人工改判 → 「重新入表」补入（valid≠formal 时出现）
      └─ 同月补传/整月口径变化 → 「月度重算」重建整月（保护已认可申诉）
  → 绩效与工资（月绩效 + 日绩效明细[默认最新一天，日期/员工可筛] + 工资 + 导出）
  → 月度对账（上传对账文件 → 任务化 → 人×日比对 → 归因 → 找平 → 报告/下载）
```

## 四、数据模型概要（全表）

- **账号/员工**：`users`（登录账号，role/status/must_change_password/person_code）、`persons`（员工档案，code/display_name）
- **数据源**：`imports`（文件：file_name/sha256/status/parsed_rows）、`raw_records`（原始行：store_id_raw/store_name_local_raw/modified_raw/submitter_raw/visible/deploy + 判定列 clean_status/confirm_state/filter_reason）
- **店铺主从档**：`store_entities`（store_id_raw 唯一；name_local/name_norm；主档 master_id 自指，从档指向主档；master_store_id/master_raw_data_id 冗余）、`store_pairs`（判重候选 exact/fuzzy + AI 字段）、`store_merge_logs`（合并留痕）
- **正式与绩效**：`formal_records`（正式表：person_code/store_id/japan_date/points/import_id/raw_record_id）、`appeals`（申诉：raw_record_id/status pending|approved|rejected/reason/handled_by/handled_at）、`adjust_records`（找平：source_task_id/person_code/points 加减/note）
- **对账**：`recon_tasks`（kind/status/params/summary JSON）、`recon_data_rows`（对账文件全量 人×日×点）、`recon_day_rows`（仅问题行：side/双方点数/差异）、`person_daily_stats`（人×日：records/p1/p2/points，**日结算点**，入表/重算时同步）
- **已清理**：旧版表模型类已从代码删除（task_runs/clean_records/person_stats/daily_*/settle_amounts/review_flags/self_report_*/confirm_tasks/manual_decisions）；线上库历史表仍在但无 ORM 访问。

**关键枚举**：
- `clean_status`：valid / master_late / from_sub / cross_file_dup / blank / no_ref
- `confirm_state`：pending / approved / disputed / auto_ok / auto_approved
- `appeal.status`：pending / approved / rejected
- `recon_tasks.kind`：person_points / daily_records
- `recon_day_rows.side`：both / local_only / report_only

## 五、文件上传与判定规则（核心）

### 5.1 上传
- 支持一次传多个文件；**同内容（sha256）文件拒绝重传**（DuplicateUpload）。
- 解析 Excel：自动识别表头（标题行/表头行），列名匹配（Store ID / Store Name-Local / Modified Time / Submitter / Record ID / A+ POSM Visible / Existing A+ POSM / NEW A+ POSM / 标准点数 等）。

### 5.2 逐行判定（clean_status）
| 状态 | 含义 | 入正式表 | 可申诉 |
|---|---|---|---|
| valid | 有效记录 | ✅ 自动 | — |
| master_late | 同店名、同结算月、非组内最早时间戳（同店跨日被顶替） | ❌ | ✅ |
| from_sub | 从档（同店不同编号被归并） | ❌ | ✅ |
| cross_file_dup | 同日同店跨文件重复（同一条导出两次） | ❌ | ❌ |
| blank | A+ POSM Visible 为空 | ❌ | ❌ |
| no_ref | 预留（现为 0） | ❌ | — |

### 5.3 去重窗口（定稿，勿改）
- 窗口 = **结算月**（同月内判重）；
- 键 =（**店名 trim**，月份）；组内**最早完整时间戳**行 valid；
- **跨月行永不互相压制**（7/31 与 8/1 同店不算重复）。

### 5.4 主从档
- 同一真实店铺多个 store_id（不同编号）→ 归一为一个实体（store_entities）；
- 主档 = 该店最早出现的编号（master_id 自指）；从档行判 from_sub；
- 店铺自动建档/匹配；疑似同名店进判重列表（exact 自动、fuzzy 可 AI/人工合并，留痕）。

### 5.5 点数（1点/2点）
- 日期 ≥ **2026-07-09** 且 Deploy=YES → 2 点，否则 1 点；
- 若文件带"标准点数"列 → 以标准点为准；
- 月点数 = 该员工当月有效店点数之和。

### 5.6 员工自动建档
- 出现新的人员编号 → persons 自动开户；users 登录名按姓名拼音生成（pypinyin），初始口令统一，首登强制改密。

## 六、申诉与绩效确认

- **可申诉**：master_late、from_sub（员工"我的申诉"提交，带理由）。
- **默认全部认可**：被滤记录默认 auto_ok，不打扰员工。
- **管理员处理**（绩效确认页）：
  - 认可（accept）→ raw 改判 valid（confirm_state=approved），下次入表计入（+点数）；
  - 驳回（reject）→ 维持滤除并定案（auto_ok，不可再申诉）；
  - 留痕：handled_by/handled_at/reason。
- **硬门槛**：文件存在 pending 申诉 → 整个文件不能入表（含 valid 记录一起等）；月度重算同理（当月 pending → 拒绝）。处理完（认可/驳回都算）后一次性入表。
- **入表后新申诉**：员工随时可申诉 → 认可后 valid > formal → 绩效确认页出现「重新入表(N)」补入。

## 七、正式表三动作

| 动作 | 粒度 | 行为 | 何时用 |
|---|---|---|---|
| 入正式表 finalize_import | 单文件 | 按该文件最新 valid 重建正式表（先删后插，幂等）+ 同步 person_daily_stats | 上传判定后、申诉处理完后 |
| 重新入表 | 单文件 | 同上（valid≠formal 时按钮出现，提示补入 N 条） | 入表后申诉认可/人工改判 |
| 月度重算 rebuild_month | 整月 | 重判覆盖该月的所有文件（防同月补传双算）、**保护已认可申诉**（重判后恢复 valid）、重建整月正式表+统计表 | 同月补传、申诉改判、对账找平后 |

- 门槛：有未决申诉 → 拒绝并提示；幂等可重复。
- 正式表每行 = 一条有效店记录（人/店/日期/点数/来源），是绩效、工资、对账的唯一权威。

## 八、绩效与工资

### 8.1 月绩效（v3/perf）
每人：有效店数 / 1点店 / 2点店 / 总点数 / 工资 / 上月找平 / 应付合计（含找平）/ 2点成功率（达标 37% 徽标）。

### 8.2 工资规则（定稿·2026-09 修订）
每点 250 円（按月可配 per_point）；奖金**每满 68 点奖 3,000 円**（整月滚动、不跨月；门槛/奖额可由 BONUS_GROUP/BONUS_AMOUNT 环境变量配置）。
例：2,326 点 → 2,326×250 + (2326÷68=34)×3,000 = 581,500 + 102,000 = **683,500 円**。
（旧规则「满68点奖3,000当月一次」已于 2026-09 改为「每满68点奖3,000」；两期发薪：上半月=h1÷68×3000，下半月=(h1余+h2)÷68×3000。）

### 8.3 汇总卡
8 卡 2 行×4 列：员工数 / 有效店 / 1点·2点店 / 总点数 ｜ 工资合计 / 上月找平 / 应付合计（含找平）/ 2点成功率。

### 8.4 日绩效明细
- 数据源 person_daily_stats（人×日：店数/1点/2点/日结算点，入表/重算时同步，与正式表逐日一致）；
- **默认显示该月最新一天**；日期、员工可筛选（控件在卡片内，不选=全部）；**只选员工 → 显示其全月**；切月清空筛选；
- 员工端「我的绩效」同规则（单员工 + 日期）。

### 8.5 导出工资表 Excel
页签：月度绩效·工资（员工编号/姓名/有效店/1点/2点/总点数/工资/找平 + 合计行）、日绩效明细。

### 8.6 找平
月度对账确认的差异 → adjust_records（按源任务+人）→ **下月工资加/减**（应付合计体现）。

## 九、月度对账（v3/recon）

### 9.1 任务化生命周期
上传 → start_task（pending）→ 后台线程离线执行（run_task/launch_task；测试环境 RECON_SYNC=1 同步）→ done/failed；失败在 summary.error 留因（如解析/比对异常），可重传。

### 9.2 对账文件识别（guess_kind）
- `person_points`：表头含 姓名+点数（人员点数表）；
- `daily_records`：表头含 Store ID + Modified Time + Submitter（逐条明细）；sheet 优先"最终有效/有效明细/有效数据"；列自动识别 Visible/Deploy/标准点数；点数按边界规则（同 §5.5）。

### 9.3 比对与问题行
- 本地侧 = person_daily_stats（人×日）；
- 逐人逐日比对 → 差异（diff≠0 或仅一侧有）才写 recon_day_rows；
- side：both（两边都有但点数不同）/ local_only（仅系统有）/ report_only（仅对账有）；
- 人月差异、系统有而对账文件无的员工名单（sys_only）一并输出。

### 9.4 差异归因（确定性规则，系统自动）
- 行级按「店+时间戳」判定：一致 consistent / 仅系统 only_system / 仅对账 only_report（按原因 from_sub/master_late/cross_file_dup/no_ref/not_found 拆分）→ net 净差；
- 展示：任务页归因卡 + 报告「差异归因」页签。

### 9.5 AI 对账解读（可选）
- 按钮"生成/更新解读" → 大模型读差异与归因输出中文说明，存档（模型/时间）；
- 需配置 AI_API_KEY/AI_BASE_URL/AI_MODEL（OpenAI 兼容）；未配置友好提示；失败不影响对账；AI 只做解释、不拍板。

### 9.6 同月重传 = 重新对账（版本化）
- 同月再上传 → 旧任务标 replaced/replaced_by，**保留可查**（「上一版」徽标）；新任务为当前（version+1）；找平关联不丢。

### 9.7 找平联动
- 差异确认 → adjust_records（下月工资加/减）；可取消调整；配合月度重算同步口径。

### 9.8 产物（Excel）——对账结果文件设计

**生成机制（系统自动，无需人工）**：任务 done 时，`run_task` 自动调用 `build_report` 生成《月度对账报告.xlsx》并落盘到 `uploads/recon_result_<task_id>.xlsx`（`task.params.result_path` 记录路径）；任务页「下载对账结果」/「对账报告」直接流式返回该文件；**历史任务产物保留**，任何版本都可再下载。对账页/对账数据全部由系统按上述流程产出，无任何人工生成环节。

**文件页签设计**（openpyxl 动态生成，条件性页签按任务数据出现）：

| 页签 | 内容 | 出现条件 |
|---|---|---|
| 对账报告摘要 | 对账月份/来源文件/生成时间/生成人；系统正式口径合计（有效店、1点/2点、总点数、工资、上月找平、应付）；对账比对（人数/差异条数/反向名单数/问题行数/找平）；结论（0差异→完全一致，否则见明细） | 总是 |
| 员工×日对账明细 | 日期/员工编号/姓名/本地点数/对账点数/差异/说明（点数不一致·仅本地有·仅对账有）——只列问题行 | 日级且存在 day_rows |
| 差异明细 | 人员/编号/系统点数/对账点数/差异(系统−对账)/应找平(円)（按工资规则折算） | 总是（无差异写"无差异"） |
| 系统有而对账文件无 | 编号/姓名（反向名单，漏发风险人工核对） | 总是（无则写"无"） |
| 找平确认 | 编号/姓名/金额(円)/生效月份/原因/确认时间（留痕） | 总是（无则写"无"） |
| 差异归因 | 一致/仅系统有/仅对账有（按原因拆分）/净差 | summary 含 attribution |
| AI 解读 | 模型/生成时间/解读文本 | 生成过 ai_interpret |

「对账报告」与「对账结果」为同一文件的两个下载入口。

7. 重新对账：保留历史版标记「上一版」可查（曾考虑删除旧版，已定为保留；未来可加开关切回）。
