## 1. 🔴 `period.py:93` 结转扣减符号错误（会多扣钱）

### 位置
`app/services/period.py:88-98`（`record_payment` 内的「本笔实发要吸收多少上月结转」段）

### 现状代码
```python
carry = prev_row.prev_adjust_amount or 0 if prev_row else 0   # 负=要扣
if carry < 0:
    absorbed = 0
    for q in db.query(PayrollPayment).filter(
            PayrollPayment.month == month,
            PayrollPayment.person_code == person_code).all():
        absorbed += q.adjust_applied or 0                    # 已扣的（负）
    remaining = carry + absorbed                             # ← :93 错的
```

`carry` 与 `absorbed` **同为负数**（注释自己写了 "负=要扣"、"已扣的（负）"），相加等于**把已扣的又加了一遍**。应为：

```python
remaining = carry - absorbed                                 # 正确
```

### 实证（内存库，不碰演示库）
构造：8 月结转 `prev_adjust_amount = -2000`（需在 9 月扣回 2000）；9 月两期各实发 3000。

```
seq1: amount=3000  adjust_applied=-2000  leftover=0      ← 正确（扣满 2000）
seq2: amount=3000  adjust_applied=-3000  leftover=-1000  ← 错（债务已扣完，又扣了 3000）

9 月合计抵扣 = -5000   （债务只有 -2000）→ 多扣 3000
```

### 连带影响（比表面更严重）
1. `adjust_leftover`（"扣完仍需递延的金额"）失真；
2. `record_payment` 用它调 `allocate_settlement` 做 **FIFO 核销** → 找平进度 `payroll_adjusts.settled_amount / remaining` 被**超额核销**；
3. 而 `payroll_adjusts.remaining` 是**跨月债务的权威来源**（`period.py:582-595`，注释明确写了"从找平行读会丢债，实测 11 人 / −89,750 收不回"）→ **错误可级联影响下月结转**；
4. 🟡 子代理实测：该场景下数据自洽检查 `verify_payroll_logic.py` 的 **A4 会 fail**（`台账 seq2: 关联合计 0 vs adjust_applied -3000`）。我复核了代码路径与符号方向，**未复现 A4 那一项**。

### 为什么现有测试没发现
`mcp_service/tests/test_payroll_write_ops.py:277-289` 的首期 `amount=0` → `absorbed=0` → 符号问题不暴露。**只在"同月第二次发放 + 债务已被首期吸收完"时触发。**

### 建议修复
1. `period.py:93` 改 `remaining = carry - absorbed`；
2. 补回归测试：**「首期已吸收完 → 次期不得再扣」**（即上文的 seq2 必须为 `adjust_applied=0`）；
3. 修完跑 `scripts/verify_payroll_logic.py`，并**核对线上已发生的找平进度**（历史 `payroll_adjusts` 可能已被超额核销，需要一次性重算或人工核对）。

### ⚠️ 为什么我没有直接修
用户明确约束：**不改动现有结算口径与工资数字**。此修复会改变已发生的金额，属于业务决策，必须由用户确认（且涉及线上历史数据回算）。

## 2. 🔴 线上 `raw_records.visible_raw` 列宽装不下实际值

### 事实链（全部亲自复核）
| 检查点 | 结果 |
|---|---|
| ORM 声明 | `app/models.py:90` → `Column(String(8))`，注释写「YES/NO/空」 |
| 建表迁移 | `migrations/versions/ac89f3182e16_initial_tables_spec_v0_4_4.py:176` → `sa.String(length=8)` |
| 是否有加宽迁移 | **没有**。全仓 `grep visible_raw` 只命中这一处定义 |
| 本地库实际 DDL | `visible_raw VARCHAR(8)` |
| **本地库实际数据** | `AUDIT_SUCCESS`(13 字符) × **19606**、`AUDIT_FAILED`(12) × **1346**、`NOT_REQUEST`(11) × **2** → **合计 20,954 行超长** |

### 新旧格式分水岭（按 import 查）
```
import#1  2026-07  values = YES, NO
import#2  2026-08  values = YES, NO
import#3  2026-08  values = YES, NO
import#4  2026-08  values = YES, NO
import#5  2026-09  values = AUDIT_FAILED, AUDIT_SUCCESS, OTHER, NOT_REQUEST  ← 13 字符
```

### 后果
- **本地 SQLite 不校验 `VARCHAR(n)` 长度** → 静默存下，一切正常；
- **生产是 PostgreSQL 16，`varchar(8)` 是硬约束** → 写入 13 字符抛 `22001 value too long for type character varying(8)`；
- `deploy/entrypoint.sh` 每次启动自动 `alembic upgrade head`，所以线上那张表**就是 varchar(8)**（除非有人手工改过列类型——仓库里找不到任何会这么做的迁移或脚本，`scripts/sync_local_columns.py` 只 ADD COLUMN 且仅用于本地 SQLite）；
- **→ 8 月及以前的文件在线上传得好好的；一旦传 9 月起的新格式文件，会在解析入库那一步直接失败。**

### 附带的自相矛盾（死代码）
`store_settle/loader.py:283-288` 有个值域校验：
```python
if vis_raw is None:                       # ← cell() 永远返回 str，此分支永不成立
    res.errors.append(f"...（仅接受 YES/NO/空白，或 AUDIT_SUCCESS/AUDIT_FAILED）")
```
**报错文案自己承认要接受 `AUDIT_SUCCESS`（13 字符），却把它存进 varchar(8)**；且该校验从未生效过。

### 建议修复
```python
# app/models.py:90
visible_raw = Column(String(32), nullable=True)   # 32 足够容纳现有及未来枚举

# 新增迁移（PG: ALTER COLUMN TYPE；SQLite 本就不校验，可选）
op.alter_column("raw_records", "visible_raw",
                existing_type=sa.String(8), type_=sa.String(32))
```
`deploy_raw` 同样声明 varchar(8)，但实测只有 `YES`/`NO`/`NULL`，**当前没问题**（建议一并加宽以防未来）。

### ⚠️ 未验证的部分
**线上列类型我没实测**（需连 `store-prod`，未擅自连生产机）。判断依据是迁移链。一行可确认：

## 3. 🟠 导出发薪表与页面两期扣减口径不一致

> 证据强度：🟡 子代理实测，本会话**未独立复核**。
