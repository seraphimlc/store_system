**已核实·非缺陷**：2026-09 有 **25/44 人**「上半月应发（`payroll_period_rows.half1_amount`）≠ 发薪台账快照（`payroll_payments.amount`）」。核完结论：**不是 bug，也不用改账**。

- 台账期1 是 **2026-09-26 14:01** 登记的（导出发薪表即登记）；而 9/16–9/30 那份文件 **2026-10-02 04:20** 才上传（import #19，19,038 条 9 月正式记录）。判重窗口是「整月 + (店名,月)」→ 下半月数据到齐后，**跨半月的同店重复记录被剔除**，重算后的上半月点数比登记时少 **63 点 = ¥15,750**（差 = 点数差×250，25/25 人全中）。
- 反证：**10-16 补登记的 10 人金额全部一致**（登记时用的就是重算后的数），09-26 登记的 35 人里 25 人不一致、9 人没受影响。
- 不影响钱：找平偏差 = `recon_results` 快照的（对账点数 − 系统点数），**不读** `payroll_period_rows` 重算值；台账（`payroll_payments`）按设计不可改写，是"实际发了多少"的事实。
- 唯一副作用是**展示**：9 月的「应发」现在比台账低 ¥15,750（`/perf` 与发薪表导出看的是重算值）。若要对账方便，可另开一项"台账 vs 重算"差异视图（用户未要求）。

## 1. ✅ 已修｜`raw_records.visible_raw` 列宽（原判 varchar(8)）

- ORM `app/models.py:90` → `Column(String(8))`（注释写「YES/NO/空」）；建表迁移 `migrations/versions/ac89f3182e16_*.py:176` → `sa.String(length=8)`；**全仓无加宽迁移**（`grep visible_raw` 只命中这一处定义）。`deploy_raw`（`app/models.py:91`）同为 varchar(8)，实测只有 YES/NO/NULL，当前无问题（建议一并加宽）。
- 本地库实测值域：`AUDIT_SUCCESS`(13 字符) 50082、`AUDIT_FAILED`(12) 2998、`NOT_REQUEST`(11) 3、`AUDITING`(8)、`OTHER`、`YES`/`NO`；**长度 > 8 的合计 53083 行**。
- **本地 SQLite 不校验 `VARCHAR(n)`** → 静默存下；**生产是 PostgreSQL 16，`varchar(8)` 是硬约束** → 写入 13 字符抛 `22001 value too long for type character varying(8)`。
- `deploy/entrypoint.sh` 每次启动自动 `alembic upgrade head` → 线上那张表就是 varchar(8)（仓库里没有任何脚本会改列类型）。
- **风险：8 月及以前文件在线上传正常；一旦传 9 月起的新格式文件，会在解析入库那一步直接失败。**
- 修复：`visible_raw = Column(String(32))` + 新增迁移 `op.alter_column("raw_records", "visible_raw", existing_type=sa.String(8), type_=sa.String(32))`。
- **未验证**：线上真实列类型未实测（未连生产机），判断依据是迁移链。一行可确认：
  `ssh store-prod "docker exec deploy-db-1 psql -U store_settle -d store_settle -c '\d raw_records'" | grep visible_raw`

## 2. 🟠 导出发薪表与页面两期扣减口径不一致

2026-10-17 重新核对（原文路径 `app/settle_r.py` / `app/services/report.py` 已变），**结论仍成立**：

| 位置 | 逻辑 |
|---|---|
| 导出发薪表 `app/services/report.py:181-185`（`build_payroll_workbook`） | `carry = adj_amt_map.get(code, 0) if is_h1 else 0` —— **只在上半月 sheet 带找平**，无负值钳制、无转期 |
| 页面 `app/routers/settle_r.py:420-425`（`perf`） | `p1 = h1 + carry; if p1 < 0: pay_map = (0, h2 + p1)` —— 「发 0 + 负数转下半月」 |
| 扣款入账 `app/services/period.py::record_payment` | 按笔扣：`take = max(carry, -paid_amt)`，扣不完递延 `adjust_leftover` |

**风险**：导出表才是「照此发薪」的表，却与页面（及 `record_payment`）口径不同（同一人可能页面 (0, −1000)、导出上半月 −2000 / 下半月 1000）。
**建议**：把两期扣减/转期逻辑**收敛到单点**（period 或 report 之一），页面与导出共用。
