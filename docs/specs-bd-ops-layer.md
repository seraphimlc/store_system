## 一、背景与目标

### 1.1 要解决的问题

当前系统管的是**结算**（事后算钱）。BD 团队的**作业管理**（事前派活、事中盯过程）为零。

具体缺口：

| 缺口 | 现状 |
|---|---|
| 区域划分 | 业务团队**沿地铁线路**分配区域 |
| 网格 | 无任何网格/区域实体 |
| 团队层级 | `users.role` 只有 `admin` / `staff`，**无主管角色** |
| 目标 | 无目标/配额表 |
| 任务 | 无任务实体（"Mission-to-Task" 完全缺失） |
| 门店宇宙 | 只有"扫过的店"，没有"该扫的店" |
| 地理数据 | **解析层为零**（`raw_records` 19 列无地理字段）；但**源文件里有地址**——见 §1.3 |

### 1.2 沿地铁线路分配的结构性问题（已用真实地址量化）

> 下表的每一条都不是推断：§1.3 用**源文件里的真实地址**逐条测过。

| # | 问题 | 说明 | 实测证据 |
|---|---|---|---|
| 1 | **线不是面** | 按线分配得到长条地盘，周长/面积比极差，通勤吃掉产能 | `中野〜吉祥寺` 经度跨度 **8.47km**、纬度跨度仅 **0.68km** → **宽长比 12:1**；`両国・錦糸町・亀戸` 为 **13.8:1**。对照紧凑区域 `池袋` 1.5:1、`新大久保・高田馬場・早稲田` 1.5:1 |
| 2 | **密度不匹配 → 负载失衡** | 站前 CBD 与郊外单站店数差一个数量级。**是组织结构问题，不是执行纪律问题** | 人均负责店数：`銀座` **256 店/人** vs `新宿` 21、`池袋` 45、`大阪ミナミ` 1 → **相差 256 倍** |
| 3 | **线会切碎商圈** | 换乘站多条线路交汇，同一栋楼的店可归多人 → 撞店。现有「同店同月只算最早一条」判重规则本质是在**用扣钱弥补划片错误** | 结构性问题，见 §3.3 |
| 4 | **覆盖不到非地铁商业** | 住宅区商店街、郊外路边店 | 存在 `Default CD-Japan` = **985 家店（11.3%）未归入任何具体区域** |
| 5 | **无法度量覆盖率** | 线是路径不是面，没有分母 | 现有区域字段只有名称，无边界、无面积、无应覆盖门店数 |

### 1.3 关键发现：源文件里**已经有地址与区域**，只是被解析层丢掉了

这是本方案最重要的前置事实，**它把 P0 的成本从"改客户端"降到"改解析"**。

源文件（MarsNavi 导出的宽表）是 **50 列的定位数组**，`raw_records.original_row` 原样保存了它，但**解析层只提取了 8 列**，其余全部丢弃。实测各列语义（`import#1` / `import#4`，50 列布局）：

| 列 | 含义 | 填充率 | 样例 |
|---|---|---|---|
| [0] | 记录号 | 100% | `0101047092026060971271764` |
| [1] / [2] | 店名（本地 / 备用） | 100% / 46% | `TASTING　MARKET` |
| [3] / [4] | **国家 / 都道府県** | 100% / 100% | `Japan` / `Tokyo` |
| [5]–[8] | 各阶段时间戳 | 100% | `2026-08-05 10:34:04` |
| [9] | 提交人 `姓名(编号)` | 100% | `王中豪(2188240623927428)` |
| [12] | **业态** | 100% | `Others` / `Dining` / `Recreational services` |
| [13] | 营业状态 | 100% | `In Operation` |
| **[14]** | **门店照片 URL** | **97%** | `https://gw.alipayobjects.com/...jpg` |
| [15] | 巡店类型 | 100% | `Store Information Confirmation` / `POSM Information Confirmation` |
| [16] | 判定结果 | 100% | `AUDIT_SUCCESS` / `AUDIT_FAILED` |
| **[21]** | **地址（日文）** | **52%** | `東京都墨田区両国2-18-4 PARATTSUO102` |
| **[22]** | **地址（英文）** | **47%** | `Japan, 〒104-0061 Tokyo, Chuo City, Ginza, 3-...` |
| **[23]** | **门店照片 URL** | **52%** | 同上 |
| **[24] / [25]** | **区域名（日文 / 英文）** | **100%** | `両国・錦糸町・亀戸` / `Ryogoku・Kinshicyo・Kameido` |
| **[26]** | **区域编号** | **100%** | `0101002092026072700215566` |
| [27]–[29] | 连锁品牌名 / 编号 | 6% | `セブンイレブン` |
| [30]–[40] | **POSM 物料详情**（码型/位置/状态/照片） | 3–47% | `Marketing Code` / `Cashier Counter` / `Materials are available…` |

**由此得到三条结论：**

1. **地址已经在手**（[21]/[22]），**不需要打卡端配合就能回填地理**。配合 §4.1 已实测的国土地理院接口，`地址 → 坐标 → 丁目 → 网格` 全链路可离线跑通。
2. **已存在一份"区域"主数据**（[24]/[25]/[26]，含区域编号），100% 填充——但它的取值形态正是「沿地铁线/站群」：
   `中野〜吉祥寺`（中央线）、`新大久保・高田馬場・早稲田`（山手线+西武新宿线）、`赤羽・川口・西川口`（京滨东北线北段）、`両国・錦糸町・亀戸`（总武线）。
   → **它是旧体系，不能直接当网格用，但可以作为「迁移映射」的输入**（旧区域 → 新网格一一对照），迁移风险因此大幅降低。
3. **照片与 POSM 详情也已在手**，而 `.env` 里已有 `xytoken` 多模态通道（"判定门头照 + 招牌 OCR"）——**防作弊所需的"照片核验"同样不需要新客户端开发**。

> ⚠️ **列布局逐文件不同**（实测）：`import#1`/`#4` = 50 列；`#3` = 34 列；`#2` = 39 列；`#5` = 7 列。
> 因此**不能按固定下标解析**，必须把列映射做成**按文件布局可配**（现有 `imports.layout` 机制已具备该能力，扩展即可），否则会取错列。**这是 P0 的第一号技术风险。**

### 1.3 目标

引入**网格化区域管理**，使：

1. 区域划分从「线」变成「**面**」——可穷尽、无重叠、可切分、负载均衡；
2. 撞店在**派单时**就不发生（而非事后判重扣钱）；
3. **空间覆盖率立即可度量**（不依赖完整门店名单）；
4. 目标与任务可挂在网格上向下分解、向上汇总。

### 1.4 本阶段明确不做

- ❌ 过程指标**不挂钩工资**（用户已确认：第一阶段只考核、只展示）
- ❌ 不改动 `formal_records` / `person_daily_stats` / `month_perf_records` / `payroll_period_rows` 的任何列与口径
- ❌ 不引入地图前端依赖（先用经纬度 + 行政区划文本，地图可视化后置）

## 二、硬边界：作业域与结算域的隔离

### 2.1 依赖方向（单向）

```
      ┌───────────────── 作业域（新增，bd_*） ─────────────────┐
      │  网格 / 认领 / 团队 / 目标 / 任务 / 门店宇宙 / 过程指标  │
      └───────────────────────────┬───────────────────────────┘
                                  │ 只读（判断任务完成度、算实际产出）
                                  ▼
      ┌───────────────── 结算域（已建成，一行不改） ────────────┐
      │  raw_records → formal_records → person_daily_stats      │
      │              → month_perf_records → payroll_period_rows  │
      └─────────────────────────────────────────────────────────┘
                     ✗ 结算域永不读作业域（无反向箭头）
```

### 2.2 三条硬规则

1. **表级隔离**：作业域全部用 `bd_` 前缀建新表。**绝不往结算域四张表加列**。
2. **依赖单向**：作业域可读结算域；**结算域永不读作业域**。作业数据写坏最多影响看板，绝不动钱。
3. **模块隔离**：`app/services/bd_*.py` + `app/routers/bd_r.py`；MCP 侧新增 `bd_*` 工具复用 `mcp_service/guards.py` 既有闸门。

### 2.3 已有先例

`staff_daily_reports`（员工每日填报）已明确「**不参与工资计算**，只用于对比」，并已长出 `应填未填`、`单日准确率 acc_day` 等过程指标——这正是作业域的第一块孤岛。**本方案是把它养大，而不是把作业字段塞进结算表。**

## 三、网格模型（三层）

### 3.1 L0 行政区划基底 —— 官方编码，不自造

网格骨架**不自造坐标系**，直接用日本官方行政区划：

```
都道府県  →  市区町村（全国地方公共団体コード 5 位，如 13113 = 渋谷区）
          →  町丁目（丁目 = 日本最实用的最小行政单元）
```

**为什么用行政区划做基底：**

| 优点 | 说明 |
|---|---|
| MECE | 不重不漏，天然可穷尽 |
| 边界有法律定义 | 无争议、可交接、可审计 |
| 人人看得懂 | 业务方沟通零成本（"你负责渋谷区道玄坂一〜三丁目"） |
| 统计可对接 | 人口/商业统计按丁目发布，可直接做负载依据 |
| 免费且权威 | 総務省 町丁目コード（全国统一）、e-Stat、国土地理院 |

> ⚠️ 丁目总数须**从官方清单实际拉取**确定（本文件不写未经核实的数字）。

### 3.2 L1 作业网格 —— 在丁目基底上打包

丁目是最小粒度，但**不作为派工单元**（过细）。把若干相邻丁目打包成一个**作业网格**：

**划分原则（按优先级）：**

1. **等负载**：每个网格的门店数（或 面积 × 商业密度）相近，用实测日产能封顶
2. **连通**：网格必须是连续的**面**，不允许飞地
3. **贴自然边界**：河川、铁道、主干道、区界——便于人工理解与交接
4. **单网格 ≤ 一个人扫得完的量**：扫不完的网格注定注水

**划分算法（离线脚本，非运行时）：**

```
输入：丁目清单（含质心经纬度、面积）+ 各丁目门店数
方法：带连通约束的区域生长 / 加权 k-means
  - 以最大日产能为容量上限做装箱
  - 每次扩张只并入与当前网格邻接的丁目（保证连通）
  - 目标函数：min 各网格负载方差
输出：grid → [丁目] 的划分，落库 bd_grid_area
```

**双层结构的理由**：丁目给出**稳定、权威、不可争辩的边界**；作业网格给出**可调整的派工单元**。业务变化只需重打包，不必动地理基底。

### 3.3 L2 认领 —— 网格 × 时间窗 × 负责人

**这是防撞店的核心机制。**

```
bd_grid_assignment: (grid_id, start_date) 唯一
```

**同一网格、同一时段，有且只有一个负责人** → 撞店在**结构上不可能发生**。

- 认领对象可以是**团队**（`owner_type=team`）或**个人**（`owner_type=person`）
- 人离职 → 网格整体转交（`end_date` 收口 + 新行开启），无需重新理解地盘
- 负载变化 → 重新打包网格 + 重新认领

## 四、地理数据闭环（已实测可行）

### 4.1 三个官方数据源（本机实测通过）

| 用途 | 接口 | 实测结果 |
|---|---|---|
| **地址 → 坐标** | 国土地理院 住所検索 API<br>`https://msearch.gsi.go.jp/address-search/AddressSearch?q=<地址>` | ✅ `東京都渋谷区道玄坂2丁目` → `lng=139.698318, lat=35.659397`；且自动规范为漢数字 `道玄坂二丁目` |
| **坐标 → 丁目** | 国土地理院 逆地理コーダ<br>`https://mreversegeocoder.gsi.go.jp/reverse-geocoder/LonLatToAddress?lat=&lon=` | ✅ `(35.6580,139.7016)` → `muniCd=13113, lv01Nm=渋谷二丁目` |
| **统计对接** | e-Stat / 総務省 町丁目コード | ✅ 门户可达 |

**关键结论：给定坐标就能直接拿到丁目。** 所以**网格骨架不必等门店名单**。

### 4.2 回填闭环（**P0，成本已大幅下降**）

现状：`raw_records` 19 列**没有任何地理字段**；`store_entities.city` / `address_local` 两列已预留但**实测 100% 为空**。

但 §1.3 已证实：**地址一直在源文件里**（第 [21]/[22] 列），只是解析层没提取。因此 P0 **不需要改打卡端**：

```
① 解析层扩充（唯一必须写代码的一步）
   50 列布局里多提取：地址[21]/[22]、都道府県[4]、区域[24]/[25]/[26]、
   业态[12]、门店照[23]  → 落 bd_store_raw / 回填 store_entities.address_local
        ↓
② 离线地理编码（国土地理院，免费无 key，已实测）
   地址 → 坐标 → 逆地理编码 → muniCd + 町丁目 → bd_area
        ↓
③ 丁目 → 网格归属（§3.2 打包算法）
        ↓
④ 覆盖率立刻可算（空间覆盖率，不看门店名单）
        ↓
⑤ 后续可选增强：打卡端补 GPS 精度 / 水印 / 停留时长（= L4 防作弊，见 §7.3）
   —— 但这是"提高可信度"，不是"能不能做网格"的前提
```

**关键结论：「扫店必带位置」不再是阻塞项。** 现有源文件已足以建网格；客户端采集属于后续的**可信度增强**，与网格建设解耦。

> 代价与边界：地址填充率约 **50%**（`import#1/#4`），另 50% 行无地址 → 这部分门店暂时无法定位，只能落在"未定位"桶里，待后续补采。这是**渐进改善**，不影响先建网格骨架（骨架依赖行政区划，不依赖单店坐标）。

### 4.3 门店宇宙（回流累积）

用户已确认：**BD 扫店时新增并回流成宇宙**。

| 优点 | 代价与缓解 |
|---|---|
| 零采购成本；门店信息由一线采集，鲜活 | 永远只有"扫过的店"，**门店覆盖率没有完整分母** |

**缓解方案（关键洞察）**：

| 指标 | 需要什么 | 现在能算吗 |
|---|---|---|
| **门店覆盖率** | 完整门店名单 | ❌ 没有 |
| **空间覆盖率** | 网格边界（丁目）+ 已扫门店的**位置** | ✅ **补采坐标即可** |

即：**先把丁目级网格建起来，空间覆盖率立刻可算**——分母是"网格内应覆盖的丁目"，不是门店名单。门店名单在网格边界内累积，累积越多门店覆盖率才越准。`bd_store` 因此同时承担**开拓进度台账**的角色。

## 五、数据模型

> 全部新增表，`bd_` 前缀；沿用仓库既有约定（Integer 自增主键、`DateTime default=_now`、`JSON` 用 `sqlalchemy.JSON`）。

### 5.5 过程留痕（可选，取决于打卡端能力）

## 六、过程指标与覆盖率算法

### 6.1 三类覆盖率

| 指标 | 公式 | 分母来源 | 现在可算 |
|---|---|---|---|
| **空间覆盖率** | 本期有访问的丁目数 ÷ 网格内丁目总数 | `bd_grid_area` | ✅ 补坐标即可 |
| **门店覆盖率** | 本期访问过的宇宙门店 ÷ 网格内宇宙门店 | `bd_store` | ⚠️ 随宇宙累积逐步变准 |
| **开拓率** | 本期**新发现**门店数 ÷ 人天 | `bd_store.first_seen_*` | ✅ |

### 6.2 其他过程指标

| 指标 | 口径 | 防注水作用 |
|---|---|---|
| 出勤天数 | 有访问记录的日期数 | — |
| 人均产出 | 访问门店数 ÷ 出勤天数 | 与日产能上限对照 |
| 重复访问率 | 访问已扫过门店的次数 ÷ 总访问 | 异常高 = 只在熟地打转 |
| 撞店数 | 同期同店被 >1 负责人访问 | **网格生效后应趋近 0** |
| 空网格/低覆盖网格 | 覆盖率低于阈值的网格 | 主管的抓手 |

> **与结算域的一致口径**：`重复访问率`、`撞店数` 的原始事实来自结算域 `raw_records`（只读）；作业域只做**归集与展示**，不回写。

### 6.3 准确性保障

过程指标只使用**已落库的事实**（打卡位置、`raw_records` 判定结果），**不做估算**。AI 只用于生成文字解读，不参与任何指标计算——与结算域既有原则一致（「数字一律由程序算，模型只写评语」）。

## 七、目标 → 任务（Mission-to-Task 落地）

> 本节机制骨架来自 PoliSales 公开描述（SEC F-4：「With a "Mission-to-Task" model, it breaks down separate sales tasks for our sales representatives, offers them a range of business developing activities to choose from on a daily basis, and helps optimize such efforts with data analytics to improve efficiency. Sales managers can also have visibility on the progress reports of the team」）。
> **更深的产品级机制（KPI 口径、激励、防作弊）待研究补齐后增补本节。**

### 7.1 拆解链

```
月度目标（bd_target, scope=company/team/grid）
   ↓ 按网格负载 + 历史产能分解
网格目标（bd_target, scope=grid）
   ↓ 按认领关系落到人
个人目标（bd_target, scope=person）
   ↓ 按日产能切分
每日任务（bd_task, task_date）
   ↓ BD 执行（打卡 + 扫店）
实际产出（结算域 raw_records → formal_records，只读）
   ↓ 回填完成度

```

### 7.2 任务类型

| task_type | 含义 | 对应结算域信号 |
|---|---|---|
| `new_visit` | 开拓新店（宇宙内未访问） | `bd_store.first_seen` 新增 |

| `a_plus` | 物料投放（2 点店） | `formal_records.points = 2` |

### 7.3 主管工作台（manager view）

- **目标达成**：目标 vs 实际（按网格/团队/个人）
- **过程漏斗**：计划任务 → 已执行 → 有效访问 → 2 点店
- **覆盖热力**：网格覆盖率排序，低覆盖网格置顶
- **异常预警**：撞店、重复访问率异常、长时间未出勤、日产能突变

## 十二、过程 KPI 与防作弊（方法论参照，已带来源）

> 本节是**横向参照**（快消/B2B 外勤的通行做法），不是对 PoliSales 内部实现的推测。
> 标记：✅ 有公开来源｜🔵 归纳建议。

### 12.1 网格与频次的设计维度

- ✅ **辖区按"工作量"平衡**，平衡维度应显式包含：网点数、拜访频次、销售目标、有效拜访数、通勤要求、外勤产能（[Bizom·Sales Territory Management](https://bizom.com/blog/how-to-design-a-sales-territory/)）
- ✅ **按潜力而非纯地理划分**：原文——"网点少但潜力高的辖区，可能比网点多但潜力低的辖区更需要投入"
- ✅ **频次分级**（可直接照抄的分档）：A 类核心店 **每周 ≥1 次**；B 类稳定店 **每半月 1 次**；C 类普通店 **每月 1 次**（[小步外勤](https://www.xiaobuwq.com/blog/how-to-verify-sales-customer-visit-reality-practical-tips)）
- ✅ **日产能标杆**：印度 GT 快消计算器默认 **40 calls/day**；有效拜访率顶四分位 **75–85%**（[FireAI](https://fireai.in/tools/fmcg-beat-productivity-calculator)）
- 🔵 **取舍三角**：`覆盖广度 × 拜访深度 × 频次`，人日产能固定时只能取二。反推网格规模：`网格门店数 ≈ 日产能 × 周期工作日 ÷ 目标频次`

### 12.2 任务化：必须是"动词 + 对象 + 判定标准"

- ✅ **快消「终端拜访八步法」**（可直接落成日任务模板）：出门准备 → 店外检查 → 入店问候 → 店情检查（陈列/POP/货龄/竞品）→ 清点库存 → 销售陈述 → 下订单 → 回顾总结；其中第 ⑦ 步 **"预约下次拜访"天然生成下一条任务**，不必靠人排班（[超快消](https://www.chaokuaixiao.com/classroom/details/1901)）
- ✅ **SFA 四阶段**：计划 → 执行 → 检查 → 分析修正，覆盖路线拜访 / 线路协访 / 查访 / 铺货 / 活动举证等场景（[纷享销客](https://www.fxiaoke.com/crm/information-97965.html)）
- 🔵 任务单位应是**"今天去 A 店 → 完成门头照 + POSM 核查"**，不是"拜访 30 家"这种纯数量表述

### 12.3 KPI 口径与"手段目的化"陷阱（本项目最需要警惕的一条）

- ✅ **日本乾经营咨询的"手段の目的化"四连锁**：`经营者只问件数 → 只有件数被记录 → 只有被记录的被开会讨论 → 只有被讨论的进入评价`；原文强调 **"不需要恶意或怠惰，三年就会自动走到那里"**（[乾経営コンサルティング](http://www.inui-consulting.com/column/)）
  → **对按点数结算的组织，这条是最贴身的警告**：一旦"点数"成为唯一被统计、被开会、被评价的对象，组织会自动走向刷点数
- ✅ **"有效拜访"必须有结果动作定义**（"有下单或达成既定动作"），而不是"人到店"——这是给过程指标上锁的标准手法（纷享销客）
- ✅ **人均拜访数的结构性误读**：原文——"有人一天跑三十家店，有人一天跑八家，差距往往不来自勤奋程度，而来自**线路和门店结构**"（纷享销客）
  → 这正是 §1.2 实测的 256 倍人均差；**所以看人均产出前必须先修网格，否则会冤枉人**
- 🔵 **本项目可复用的现成检测器**：`cross_file_dup`（同店同日重复）+ `master_late`（同店异日重复）**天生就是"刷店检测器"**；`staff_report_compare_*` 的准确率/应填未填口径已可直接复用，不必新造

### 12.4 防作弊（按投入排序）

| 手段 | 做法 | 来源 |
|---|---|---|
| 地理围栏 | 以门店坐标为中心**半径约 100m**，进入范围签到按钮才激活 | ✅ 小步外勤 |
| 防作弊水印 | **App 内置相机实时拍摄**、禁相册上传；水印写入**人 + 实时时间 + 地点** | ✅ 小步外勤 |
| 停留时长 | 签到/签退之间持续记录；**签到后 2 分钟即离开** → 含金量由数据说话 | ✅ 小步外勤 |
| 多重定位交叉 | GPS + 基站 + WiFi 三源比对；检测模拟定位/ROOT | ✅ 小步外勤 |
| 轨迹回放 | 检查绕路/折返、**行程与拜访报告是否相符** | ✅ 小步外勤 |
| 陪访/协访 | 协访与查访覆盖率**本身就是指标** | ✅ 纷享销客 / BeatRoute |

### 12.5 激励结构（若将来要挂钩）

✅ **阿里零售通 401 城市拍档新政**（最贴近本场景的公开案例）：把"卖多少拿多少"的单一提成拆成四块——
**① 基础服务费**（用**过程指标**换保底：出勤次数/拜访门店数/带给小店的实际帮助）
**② 销售佣金**（老店**分佣率递减**，引导精力转向新店拓展）
**③ 任务执行收入**（陈列/活动/新品推销，现实中部分拍档此项已超佣金）
**④ 明星基金**（借用 361 排名：前 30% / 60% / 尾 10%）
目标原话："80% 的拍档收入依然能增加，100% 的拍档能通过多劳实现多得。"（[零售老板内参](https://m.sohu.com/a/306369620_650513/)）

🔵 **对本项目的意义**：纯按量结算的组织，升级路径不是提高单价，而是**给过程动作开一条独立收入通道**——且必须走独立奖金池，不进点数口径（§2.2）。

### 12.6 主管工作台第一屏应该是什么

🔵 应是 **"这周该去哪儿 / 谁需要陪访 / 哪条线路不公平"**，而不是"拜访总数排行榜"——后者正是 §12.3 手段目的化的入口。
可参照：目标达成、过程漏斗（计划→执行→有效访问→2 点店）、覆盖热力（低覆盖网格置顶）、异常预警、陪访计划。

## 十五、与已交付「日期计划」的衔接（2026-10-01 合并 main 后补）

> 本节是**合并 main 后新增**的。合并进来的 `feat/date-plan`（半月出勤登记，
> 规格 `docs/specs-date-plan.md`）**本身就属于作业域**，且与 BD 作业层是**上下游**关系。
> 需求原文（`AGENTS.md`）："员工在每个半月开始时登记未来半个月的出勤（每月 3 号 / 18 号前），
> **管理员据此分配任务**" —— **"分配任务"正是本方案要建的层**。

### 15.1 上下游关系（必须按这个方向接）

```
员工登记出勤（已建成）                      本方案要建的层
staff_date_plans（人×日，available）
  ├─ 谁在哪些天可出勤   ────────────────→  据此排任务 / 派网格
  ├─ roster_start_map（≈入职日） ──────→  网格认领的生效起点
  └─ 半月 period（H1 1–15 / H2 16–月末）→  目标与任务的周期单位
```

### 15.2 明确的分工边界（不要重复建）

| 关注点 | 归属 | 表 |
|---|---|---|
| **能不能来**（可用人力） | ✅ 已建成 date-plan | `staff_date_plans` |
| **来干什么**（工作内容） | 本方案 | `bd_task` / `bd_target` |
| **去哪片**（地盘） | 本方案 | `bd_grid` / `bd_grid_assignment` |

> ⚠️ **`bd_task` 与 `staff_date_plans` 都建在 (person, date) 上，极易重复建模。**
> 铁律：**`bd_task` 绝不存"是否出勤"**，需要时只读 `staff_date_plans`。
> 排任务时**只在 `available=1` 的日子派活**（读 date-plan，不重算）。

### 15.3 必须复用的既有实现（禁止另起一套）

| 既有实现 | 位置 | 本方案怎么用 |
|---|---|---|
| `date_plan.period_of / period_bounds / period_label` | `app/services/date_plan.py` | 目标与任务的周期单位，**直接用**，不新造周期概念 |
| `date_plan.roster_start_map` | 同上 | 网格认领 / 任务派发的**生效起点**（入职前不派活） |
| `date_plan.cell_state` 的五态口径 | 同上 | 任务态可对齐 `done/on/off/none/na` 语义（**`na`＝入职前，不计任何统计**） |
| `date_plan.staff_home` | 同上；`AGENTS.md` 注明是**唯一来源** | 员工端新增「我的任务」页后，**必须改 `staff_home` 这一处**，不要在各路由另写跳转 |
| `date_plan.short_code`（编号后 5 位） | 同上 | 网格/任务看板与导出**同口径** |
| 「自报写透」反范式 + 守门测试 | `staff_date_plans.reported`；`test_admin_matrix_reads_only_plan_table` | 网格归属可同样**冗余到行**（避免关联查询），并配同样的守门测试 |

### 15.4 派活时点必须晚于出勤登记截止

date-plan 的窗口是：H1 登记到 **3 号**、H2 登记到 **18 号**（4–8 号、19–23 号是间隙）。因此：

- **目标下达 / 任务生成应在登记截止之后**（3 号、18 号后），否则拿不到完整的可用人力；
- 间隙期（4–8 / 19–23）**正好是派活窗口**——与 date-plan 的"间隙不催办"设计天然互补；
- 未填的人按 `unfilled_default` 处理（老员工→不出勤、新入职→可出勤），
  **本方案排任务时沿用该默认值，不自行判断**。

> 🔵 **建议**：把"派活"做在 `/staff-plans`（已建成矩阵）的**下一页**——
> 主管看完谁可出勤，直接在同一屏分配网格与任务，避免在两个系统间来回切。
