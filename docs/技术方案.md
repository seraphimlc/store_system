> 版本：v1.0（2026-09）｜维护人：听云（engineering 角色）
> 配套文档：`AGENTS.md`（冷启动/基准/坑）、`docs/索引.md`（模块速查）、`docs/产品设计-系统逻辑全览.md`（业务逻辑）、`docs/结算主流程设计-v3.md`（主流程细节）

## 1. 系统概述与目标

### 1.1 一句话
FastAPI + SQLAlchemy 2 + Alembic + Jinja2 + htmx 的单体 Web 应用，把「巡店 Excel → 逐行判定 → 申诉/绩效确认 → 正式表 → 绩效工资（月内两期发薪）→ 月度对账（归因 + AI）→ 薪资找平（找平执行 + 上月余量递延）」整条链路线上化。本地 SQLite 开发/演示，线上 Docker Compose（PG 16 + uvicorn）+ Nginx HTTPS。

### 1.2 技术目标
| 目标 | 技术落地方式 |
|---|---|
| 每行可解释 | 判定结果**固化在 `raw_records` 行上**（`clean_status` / `filter_reason` / `filtered_by_raw_id`），不做事后重算推断 |
| 全程可追溯 | 申诉（`appeals`）、找平（`adjust_records`）、店铺归并（`store_merge_logs`）、对账任务版本（`recon_tasks.params.replaced_by`）全部留痕 |
| 口径稳定 | 判重规则（月窗口 + 店名 trim + 组内最早）与工资规则（点数×单价 + 每满 68 点奖 3000）集中实现，不散落页面 |
| 读快写稳 | 绩效/发薪读**物化表**（`month_perf_records` / `payroll_period_rows`），写路径统一走服务层事务 + 幂等（先删后插 / upsert） |
| 演示可复现 | 关键基准（正式表条数、点数、工资）由脚本可重建；「月度重算」一键恢复整月口径 |
| 人机双友好 | `__PAGE_STATE__` JSON 注入页面 + 关键控件 `data-testid`，便于 agent/自动化走查 |

### 1.3 明确不做
- 不做多租户、不做跨组织权限模型（仅 `admin` / `staff` 两角色）；
- 不做消息队列/分布式任务（对账用进程内后台线程，见 §6.3）；
- 不做前端 SPA 框架（Jinja2 服务端渲染 + htmx 局部刷新，页面表单直提）；
- AI 只做**解释与表头解析**，不参与任何金额/判定决策（AI 失败必须能整体回退）。

## 2. 技术栈与部署架构

### 2.1 技术栈
| 层 | 选型 | 说明 |
|---|---|---|
| Web 框架 | FastAPI（`app/main.py::create_app`） | 同步路由 + `Depends` 注入 `Session`；异常直接 `HTTPException` |
| ORM | SQLAlchemy 2（DeclarativeBase，`app/db.py`） | `future=True`；`SessionLocal` 全局 sessionmaker；`get_db()` 生成器依赖 |
| 迁移 | Alembic（`alembic.ini` → `migrations/`） | 27 个 revision，head = `e8f9a0b1c2d3`；**线上自动化、本地手动** |
| 模板/交互 | Jinja2 + htmx（`app/templates/`） | 服务端渲染；表单 POST + 303 重定向（PRG 模式），提示走 `?msg=` |
| Excel | openpyxl（`read_only=True, data_only=True`） | 解析原文件与生成结果报告/导出 |
| 认证 | argon2（口令）+ itsdangerous（签名 cookie `ss`） | 载荷 `{"uid", "csrf"}`，TTL 由 `SESSION_TTL_HOURS` 控制（默认 12h） |
| AI | httpx 调用 OpenAI 兼容 `/chat/completions`（`app/services/ai_chat.py`） | 失败重试 2 次（共 3 次），仍失败抛异常由调用方回退 |
| 数据库 | SQLite（本地）/ PostgreSQL 16（线上） | 同一 ORM 兼容三库（含 MySQL 8，已验证未切换） |

## 3. 数据模型与关系

### 3.1 核心表职责

| 表 | 模型类 | 职责 | 关键约束 |
|---|---|---|---|
| `users` | `User` | 登录账号；`role=admin/staff`，staff 经 `person_code` 绑人员；`status` active/leave/disabled/resigned；`must_change_password` 首登强制改密 | `username` 唯一 |
| `imports` | `ImportFile` | 上传文件档案：sha256、落盘路径、解析诊断（`parsed_sheets`/`warnings`/`errors`）、`status` uploaded/parsed/failed | `file_sha256` 唯一（同内容拒传） |
| `raw_records` | `RawRecord` | **原样底账 + 判定结果**：原始列（店名/编号/时间戳/提交人/visible/deploy）+ `clean_status`/`filter_reason`/`filtered_by_raw_id`/`confirm_state` | `(import_id, sheet_name, excel_row)` 唯一 |
| `persons` | `Person` | 员工档案（`code` 主键、姓名、首见文件） | `code` 主键 |
| `formal_records` | `FormalRecord` | **唯一权威绩效依据**：一条有效店记录 = 人/店/日本日期/点数/来源文件 | `raw_record_id` 唯一（一 raw 最多入表一次） |
| `person_daily_stats` | `PersonDailyStat` | 人×日汇总（店数/1点/2点/点数），入表/重算时刷写；**对账本地侧 & 分期点数来源** | `(person_code, ref_date)` 唯一 |
| `month_perf_records` | `MonthPerfRecord` | 月绩效**物化**：月×人 records/p1/p2/points/salary/`per_point`（锁价）+ 对账回填（settle/diff 点与额） | `(month, person_code)` 唯一 |
| `payroll_period_rows` | `PayrollPeriodRow` | 薪资找平**快照**：月×人 两期点数/金额/奖金/店数快照 + settle/prev/diff（系统参考）+ adjust（人工执行） | `(month, person_code)` 唯一 |
| `recon_tasks` | `ReconTask` | 对账任务：`kind`（person_points/daily_records/monthly_v3）、`status`、`params`（month/file/kind/path/version/current/replaced_by/single_date/unmatched/result_path）、`summary`（compared/diff_count/sys_only/attribution/ai_interpret/error） | — |
| `recon_data_rows` | `ReconDataRow` | 对账文件**全量**人×日落库（点/行数） | `(task_id, ref_date, person_code)` 唯一 |
| `recon_day_rows` | `ReconDayRow` | **只存问题行**：`sys_points`/`rep_points`/`diff`/`side`(both/local_only/report_only) | `(task_id, ref_date, person_code)` 唯一 |
| `recon_results` | `ReconResult` | 人月差异行（`system_value`/`report_value`/`diff`/`family`） | — |
| `adjust_records` | `AdjustRecord` | 找平留痕：点数增减 + **锁存单价 `per_point`** + 生效月 `applied_to_month=次月` | `(source_task_id, person_code)` 唯一（幂等） |
| `appeals` | `AppealRecord` | 申诉：`status` pending/approved/rejected + 理由 + 处理人/时间 | `raw_record_id` 唯一（一条只能申诉一次） |
| `store_entities` / `store_pairs` / `store_merge_logs` | 店铺主从档 | 同店多编号归一：主档 `master_id` 自指，从档指向主档，冗余 `master_store_id`/`master_raw_data_id`；候选对 exact/fuzzy；归并留痕 | `store_id_raw` 唯一；`(entity_a, entity_b)` 唯一 |

### 3.3 关键枚举
- `raw_records.clean_status`：`valid` / `master_late` / `from_sub` / `cross_file_dup` / `visible_blank` / `no_ref`
- `raw_records.confirm_state`：`pending` / `approved` / `disputed` / `auto_ok` / `auto_approved`（valid 自动生效）

- `payroll_period_rows`：`diff_*` = 系统参考（自动刷）；`adjust_*` = 人工执行（增量累计）

## 4. 核心流程技术实现

### 4.1 文件导入与判定

**入口**：`POST /files/upload`（`app/routers/files_r.py`），管理员 + CSRF 校验后逐文件：

```
upload_and_store(filename, content, user_id, db)      # app/services/importer.py
  ├─ 仅 .xlsx；大小 ≤ MAX_UPLOAD_MB（默认 50MB）
  ├─ sha256 落盘 uploads/<sha>.xlsx（已存在则不重写）
  └─ imports.file_sha256 已存在 → DuplicateUpload（同内容拒传）
parse_file(imp, db)
  ├─ store_settle.loader.load_workbook(path, filename)  # 自动识别表头行/数据起始行/列
  ├─ 解析异常或 res.failed → status=failed + errors（不猜测、不半写）
  └─ 成功：单事务写 raw_records（原样列 + original_row JSON）+ persons 补全；status=parsed
process_import(db, import_id)                          # app/services/v3_flow.py
  ├─ sync_store_for_import     # 文件内 distinct store_id 建实体（自引用 FK 中间态按 dialect 关校验）
  ├─ promote_or_link_entities  # 同名归并：主档 = 组内最早可见记录所在 store；其余 from_sub 候选
  ├─ update_earliest_anchor    # 每店 raw_data_id = 全库最早「可见(YES/NO)」行（比较完整时间戳）
  ├─ judge_import              # 逐行判定（下表）
  └─ ensure_persons            # 新人员编号 → persons + users（登录名自动生成、首登改密、默认口令）
```

**判重规则（实现要点，勿改）**——`v3_flow._name_month_min` + `judge_import`：

| 规则 | 实现 |
|---|---|
| 窗口 = 结算月 | 分组键 `(store_name_local_raw.strip(), modified_raw[:7])`，跨月行**永不互相压制** |
| 组内最早全时间戳行 valid | 比较 `modified_raw` 字符串（定宽 19 位 `YYYY-MM-DD HH:MM:SS`，字典序=时间序），取最小者为该组锚点 |
| 锚点唯一来源 | 仅可见行（`visible_raw ∈ {YES, NO}`）参与分组；空白可见性行不占锚点 |
| 同店同月非最早、同日 | `cross_file_dup`（重复导入，`auto_ok`，不可申诉） |
| 同店同月非最早、异日 | `master_late`（`auto_ok` 默认认可，可申诉） |
| 命中锚点但 store_id 不同 | `from_sub`（从档归并，可申诉） |
| 空 store_id 或空店名 | `no_ref`（不可申诉） |
| `visible_raw` 为空 | `clean_status=visible_blank`、`confirm_state=auto_ok`、不计点、不参与归因店标识 |
| valid | `filter_reason=None`、`confirm_state=auto_approved`（自动生效，无需员工确认） |

> 归并键刻意使用**原始店名 trim**而非 `name_norm`（NFKC/去空白/小写）：8 月基准证明「ざくろ銀座店」与「ざくろ 銀座店」是两家店，归一化会误并。`store_entities.name_norm` 只用于候选对（`store_pairs`）人工/AI 判定。

**点数规则**：`store_settle.rules.point_for(japan_date, deploy, boundary=2026-07-09)` —— 日本日期 ≥ 边界且 `deploy == "YES"` → 2 点，否则 1 点；对账文件若自带「标准点数/Store Total Amount」列则以该列为准（`parse_daily_records` 优先直给值）。

**入表与重算**（`v3_flow.finalize_import` / `rebuild_month`）：
- `finalize_import(db, import_id)`：**门槛**该文件存在 `appeals.status='pending'` → 拒绝入表（返回 `ok=False`）；通过后删除该文件全部 `formal_records` 再按 `clean_status=='valid'` 重建（**幂等、先删后插**）；随后按涉及月份调用 `v3_perf.sync_month_stats(db, month)`（同步 `person_daily_stats` 并物化 `month_perf_records`）。
- `rebuild_month(db, month)`：门槛该月有 pending 申诉 → 拒绝；对该月有 raw 的**全部文件**重跑 `judge_import`（修正同月补传造成的双算）；随后把已认可申诉（`appeals.status='approved'`）的 raw **恢复 `valid`**（申诉成果不被重判推翻）；按 `clean_status=='valid' and modified_raw LIKE 'month%'` 重建该月 `formal_records`；再 `sync_month_stats`。返回 `formal_before/after`、`points_before/after` 供页面提示。
- 页面：绩效确认页 `POST /files/{fid}/finalize`（`valid != formal` 时按钮显示「重新入表(N)」），月度重算页 `POST /month/rebuild`。

**申诉闭环**：`create_appeal`（员工端 `POST /my/appeal/{raw_id}`）先校验 `raw.submitter_code == person_code`（归属校验）且 `clean_status ∈ APPEALABLE`，再写 `appeals(pending)` 并把 raw 置 `confirm_state='disputed'`；管理员 `POST /files/{fid}/appeals/{aid}/resolve`：accept → raw 改判 `valid`（`confirm_state='approved'`），reject → 维持被滤（`confirm_state='auto_ok'`，定案不可再申诉），两者都写 `handled_by/handled_at`。

### 4.2 绩效与工资

**数据流**：`formal_records` →（`sync_month_stats`）→ `person_daily_stats` →（`sync_month_perf`）→ `month_perf_records` →（`sync_period_table`）→ `payroll_period_rows` → 页面读 `half_map` + `half_stats`。

- `sync_month_stats(db, month)`：删该月 `person_daily_stats` 后按 `formal_records` 重算（人×日 records/p1/p2/points），末尾**串联** `sync_month_perf`。
- `sync_month_perf(db, month)`：按 `formal_records` 聚合该月每人 → upsert `month_perf_records`；**单价锁存**：该月已有行的 `per_point` 优先（设置过单价后重物化不冲回 250）；该月已无正式记录的人**同步删除**行；`rate37 = p2/(p1+p2)`，`pass37 = rate37 >= 0.37`（仅展示，不算钱）。
- 页面只查物化表（`month_perf`），明细经「详细」查正式表/统计表 → 打开绩效页不再实时聚合正式表。

**工资公式（`v3_perf.salary_for`）**：
```python
salary = 0 if points <= 0 else points * per_point + (points // bonus_group) * bonus_amount
# 默认 per_point=250 円/点，bonus_group=68，bonus_amount=3000（BONUS_GROUP/BONUS_AMOUNT 可配）
# 奖金「每满 68 点奖 3000」按整月点数滚动，不跨月；单点 ≥ 0 才算
```
- `month_per_point(db, month)`：该月锁存单价（`month_perf_records.per_point` 首行），无则全局 250。
- `set_month_per_point(db, month, pp)`（`POST /perf/per-point`）：改写该月所有月绩效行 `per_point/salary`，并调用 `v3_period.sync_period_table(month, per_point=pp)` 重算分期金额；**已确认的 `adjust_records` 因锁存单价而不受影响**（纠偏不随本月单价漂移）。

**月内两期发薪（`v3_period.sync_period_table`）**：
```python
h1 = Σ person_daily_stats.points where day <= 15
h2 = Σ person_daily_stats.points where day >= 16
b1 = (h1 // g) * amt                 # 上半月奖金
rem = h1 % g
b2 = ((rem + h2) // g) * amt         # 下半月奖金：上半月余点带下来，整月滚动不跨月
half1_amount = h1 * per_point + b1
half2_amount = h2 * per_point + b2
```
- 同时固化**两期店数快照**（`half1_records/p1/p2`、`half2_records/p1/p2`），页面期视图（`half_stats_map`）只读快照，人×日表后续变动不会让已生成的分期数字漂移。
- 页面 `GET /perf?period=half1|half2`：把 `payroll_rows` 折成 `half_map[code] = (h1, h1_amt, h1_bonus, h2, h2_amt, h2_bonus)`；「上月找平」列与应付合计取 `carry_map`（同一张 `payroll_period_rows`，与薪资找平页同源）。
- 导出 `GET /perf/export?period=` 生成发薪表 Excel（按期 + 日明细）。

### 4.3 月度对账

**任务生命周期**（`v3_recon`）：
```
POST /recon/upload2 ──> submit_task(db, month, filename, content, user_id, sync=RECON_SYNC=='1')
  ├─ start_task: 文件落盘 uploads/recon_<sha>.xlsx；guess_kind(path) 判类型；
  │             登记 recon_tasks(kind='monthly_v3', status='pending', params={month,file,kind,path})
  ├─ 同月已有当前版本 → 旧任务 params.replaced=True/replaced_by=新id（保留可查=「上一版」）
  │             新任务 params.version = len(older)+1、current=True
  └─ launch_task: threading.Thread(daemon=True) → _task_worker（新建独立 Session）→ run_task
```
- `guess_kind`：扫全部 sheet 前 12 行表头 → `daily_records`（店+人+日期三类列齐）> `person_points`（姓名+点数）> `store_list` > `unknown`。

**解析（AI 优先、规则兜底）**：
- `ai_parse_daily_cols(path)`：取前 3 sheet × 14 行文本化预览（`[列号]值`），让模型只返回 JSON 列映射；**可信性校验**：列号必须是 `0 ≤ v < ncols` 的 int（bool 剔除），且至少能定位 `date + store_id + (person_name|person_code)`，否则返回 `{}` 回退规则。
- `parse_daily_records(path, month, db, ai_cols)`：`ai_cols` 覆盖规则探测（`_DAILY_COL_KEYS` 子串变体表）；sheet 优先「最终有效/有效明细/有效数据」；只计 `month` 内的日期；存在 Visible 列时空白行不计；人员解析优先级 `员工编号 → "姓名(编号)" → 姓名匹配 Person`（重名时优先当月有正式记录者）；未匹配员工记入 `params.unmatched`（页面/分析提示）；点数优先「标准点数/Store Total Amount」列，否则按 `point_for` 边界规则。
- **账单日文件处理**：若解析出的日期集合只有 1 个值（如 Statement Date 固定），标记 `params.single_date=True` + `single_date_val`，日级对比仅作参考，**以人月差异为准**（AI 解读 prompt 会显式告知模型这一点）。

**比对与落库**（`run_task`）：
1. 清空该任务旧结果（`recon_day_rows` / `recon_results` / `recon_data_rows`），`status='running'`。
2. `daily_records`：解析结果**全量**写 `recon_data_rows`（人×日 点/行数）；同时按人汇总得 `report`。
3. 人月差异：`compare_person_points` 与月绩效物化表对比，`diff != 0` 才写 `recon_results`（`note="<姓名> 点数差异"`）；`system_only_codes` 输出「系统有而对账文件无」的反向名单（`summary.sys_only`）。
4. 日级差异：本地侧取 `person_daily_stats`（`_local_daily_from_stats`，空则先 `ensure_month_stats` 刷一次），逐人逐日比对；`side='both'` 且 `diff==0` 跳过，**只写问题行**到 `recon_day_rows`。
5. 归因 `attribute_daily(db, path, month)`（确定性规则，行级）：对账文件每行以 `(store_id, modified)` 为键（无时间戳则退化为 `(store_id,)`）与本地正式表比对 → `consistent` / `only_system` / `only_report`（按系统 `clean_status` 拆 `from_sub`/`master_late`/`cross_file_dup`/`no_ref`/`not_found`）/ `net = only_system - only_report`；写入 `summary.attribution`。
6. 生成结果 Excel：`build_report(db, task_id, "系统")` → 落盘 `uploads/recon_result_<task_id>.xlsx`，路径记入 `params.result_path`；下载入口 `GET /recon/result`（与 `/recon/report` 同一文件）。
7. `status='done'` + `finished_at`；随后**两个可选后置动作，失败均只回滚不改变任务状态**：`_ai_auto_enabled()` 时 `interpret_task`（AI 解读存 `summary.ai_interpret`，含 model/时间）；`sync_period_table(db, month)` 回填 settle/diff 到 `payroll_period_rows` 与 `month_perf_records`。
8. 异常：`db.rollback()` + `status='failed'` + `summary.error=str(e)`（页面可重传）。

**AI 分析**：
- `interpret_task`：`build_interpret_prompt` 只喂**可引用事实**（比对/归因/合计/问题行样例/反向名单/特殊标记），要求四节结构化输出（总体结论/差异构成/风险核对/建议动作），约束不得编造数字、不得臆测文件外原因、中文、限字数。
- `ai_employee_notes`：为差异员工生成一行大白话解读（≤70 字）写入报告「说明」列；结果缓存于 `summary.ai_employee_notes`（只调一次模型），失败返回 `{}`。
- 统一出口 `_chat()` → `app.services.ai_chat.chat`（httpx，超时 120s，失败自动重试 2 次）；`ai_configured()` 只需 `AI_API_KEY + AI_BASE_URL` → **未配置即整体降级为纯规则**，对账功能不受影响。

### 4.4 薪资找平

**双轨语义（核心设计）**：

| 列 | 语义 | 谁写 | 刷新策略 |
|---|---|---|---|
| `diff_points` / `diff_amount` | 系统**参考值**：`settle − (h1+h2) + prev`，金额 = `calc × per_point` | `sync_period_table` | 每次生成/更新**自动整体刷新**，不接受人工写 |
| `adjust_points` / `adjust_amount` | 人工**执行值**：实际找平累计，金额 = `adjust_points × 该月单价` | `set_period_values`（增量）/ `confirm_adjust`（一键全找平） | **只增不减**（除显式撤销），默认 0 |
| `prev_adjust_points/amount` | 上月**未找平余量**递延：`(上月 diff − 上月 adjust) × 上月单价` | `sync_period_table` | 每次刷新 |
| `settle_points/amount` | 对账点数与「工资规则×对账点数」金额，取自该月**当前**对账任务（`_current_recon`：`kind='monthly_v3'`、`params.month` 匹配、无 `replaced_by`、id 最大者） | `sync_period_table` | 每次刷新 |

**写入路径**：
1. `sync_period_table(db, month)`（`POST /payroll-settle/generate`，对账任务完成后也自动调用）：员工集合 = 该月 `person_daily_stats` ∪ 对账文件人员；逐人 upsert；已存在行只更新系统侧列，**保留 `adjust_*` 不动**（手改/执行值不丢）。末尾把 settle/diff 回填 `month_perf_records`（月绩效页直接可见「对账 / 偏差金额」）。
2. 找平执行（`POST /payroll-settle/{month}/{code}/update` → `set_period_values(..., adjust_delta)`）：输入框值 = `diff − adj`（剩余未找平），保存的是**本次增量** → `adjust_points += delta`（累计制）。例：偏差 −190、已找平 −190 → 输入框自动归 0；再填 5 → 总执行 −195。同时写 `updated_by/updated_at` 留痕。
3. 对账页「确认找平」（`POST /recon/{task_id}/adjust/{code}`，action=add）→ `confirm_adjust`：写 `adjust_records`（`amount = 对账点 − 系统点`，**锁存当月单价** `per_point`，`applied_to_month = 次月`，`source_task_id` 关联），并**同步**把 `payroll_period_rows` 该员工当月 `adjust_points` 一次性补齐（`delta = diff − adjust` → 等于「一键全找平」）；`(source_task_id, person_code)` 唯一保证幂等（重复确认返回已有记录，不重复加钱）。`action=remove` → `cancel_adjust` 撤销记录并回撤执行值。
4. 上月余量递延 `carry_map(db, month)`：读**上月** `payroll_period_rows`，`remain = diff − adjust`，金额 = `remain × 上月单价`（`v3_perf.month_per_point(pm)`）；非 0 才返回。绩效页「上月找平」列与「应付合计（含找平）」均取此函数；`sync_period_table` 里 `prev_adjust_*` 用同一公式，保证两处一致。
5. 工资端体现：`v3_perf.adjust_map(db, month)` 取 `applied_to_month == month` 的 `adjust_records`，金额按**每条锁存单价**折算（纠偏额不随本月单价变化）。

## 5. 关键技术决策与权衡

| 决策 | 选择 | 理由 | 代价 / 权衡 |
|---|---|---|---|
| 绩效与分期数据 | **物化**（`month_perf_records`、`payroll_period_rows`）而非实时聚合 | 页面只查单表；发薪数字需要「当时口径」的稳定性（快照） | 必须保证物化时机（入表/重算/对账完成）与幂等；物化不全 → 页面与正式表不一致（`/month` 页有 `need_rebuild` 检测） |
| 分期店数 | **落库快照**（`half1_records/p1/p2`…） | 发薪单据不能随 `person_daily_stats` 后续变化漂移 | 快照过期需重新 `sync_period_table`；已在页脚说明「生成时固化」 |
| 偏差 vs 找平 | **双轨字段**：`diff_*` 系统参考自动刷 / `adjust_*` 人工执行累计 | 系统算的是参考，人实际找平多少是业务事实；两者必须能分别追溯、不能互相覆盖 | 页面必须清楚区分（输入框显示剩余量），误填会累计（用增量制 + 留痕 `updated_by/at` 兜底） |
| 单价 | **按月配置 + 发生月锁存**（`month_perf_records.per_point`、`AdjustRecord.per_point`） | 单价变更（250→其他）不应回改历史纠偏金额 | 需在改单价时明确「历史 adjust 不动」，已在 `set_month_per_point` 与 UI 文案中固化 |
| 奖金 | `default_factory` 读 `BONUS_GROUP/BONUS_AMOUNT`（默认 68/3000），**整月滚动不跨月** | 规则可配、口径简单；两期发薪时上半月余点带向下半月，避免月初重置造成多发 | 奖金必须在**整月**点数上计算；两期拆分只能用「累计差分」实现（`b2 = ((h1%g)+h2)//g*amt`），不可各期独立整除 |
| AI 角色 | **解释 + 表头解析**，不决策；规则兜底 | 每月对账文件表头不同，规则维护成本高；AI 不确定性不能污染金额 | 需要可信性校验（列号范围 + 必需字段）与整体回退；解读标注 model/时间存档 |
| AI 可用性 | `ai_chat.chat` 自动重试 2 次；未配置 → `ai_configured()=False` → 全链路静默降级 | 外部 API 抖动不应阻塞对账主流程 | 无重试上限以外的高级退避/熔断；失败只在 `summary`/`msg` 体现 |
| 对账执行方式 | **进程内 daemon 线程**（`launch_task`），非队列 | 单机、34 人量级，最简依赖 | 无持久队列/重试；进程重启后任务停在 `pending`（可手动重跑）；多 worker 下任务跑在处理请求的 worker 内 |
| 对账版本化 | 同月重传：旧任务标 `replaced/replaced_by` **保留可查**（「上一版」徽标），新任务 `version+1` 为当前 | 历史产物/留痕可回溯；找平关联不丢 | `_current_recon` 必须显式排除 `replaced_by` 并取最大 id，避免取错版本（已实现） |
| URL 兼容 | 每条 V3 路由**同时注册无 `/v3` 与 `/v3/*` 两个装饰器** | 新前端链路用短路径；旧链接/书签不 404 | 路由表体积翻倍；新增路由需成对注册（易漏，靠 `test_templates.py`/走查兜底） |
| 三库兼容 | SQLite（本地）/ PG 16（线上）/ MySQL 8（已验证未切换） | 本地零依赖、线上稳、迁移路径预留 | 方言差异需显式处理：JSON 用 `sqlalchemy.JSON`；TEXT 默认值 `sa.text("('')")`；唯一键含 TEXT 用 `VARCHAR(255)`；`store_entities` 自引用 FK 中间态按 dialect 临时关校验（MySQL `FOREIGN_KEY_CHECKS`、PG `DISABLE TRIGGER ALL`） |
| 判定固化位置 | 结果写回 `raw_records`（而非独立判定表） | 一行一结论，追溯直观；重判即覆盖 | 全库重判成本随文件数线性增长（见 §6.2） |

## 6. 性能与可扩展注意点

### 6.1 当前量级（34 人级）
- `formal_records` 单月 ~1.25 万行；页面读物化表（34 行量级）→ 交互无压力。
- 已知的全表扫描点（当前可接受，数据增长后是热点）：
  - `v3_perf._fetch(db)`：`db.query(FormalRecord).all()` 全表取回（月绩效/日绩效派生共用）；
  - `v3_flow._name_month_min(db)`：每次 `judge_import` 扫描**全库** `raw_records` 构建分组锚点；`rebuild_month` 对当月每个文件调用一次 → 文件数 × 全库扫描；
  - `v3_recon.compare_daily` / `attribute_daily`：同样全表遍历正式表与 raw；`attribute_daily` 每次**重新 `load_workbook`** 解析对账文件（与 `parse_daily_records` 重复一次 IO/解析）；
  - `/month` 与 `/perf` 页面用 `db.query(FormalRecord).all()` 现场推导月份列表。

### 6.2 优化方向（不改变口径）
1. 月过滤下推 SQL：`_fetch` → `filter(japan_date >= lo, < hi)`；`_name_month_min` 增加月份/文件范围参数（判重窗口本就是月，天然可分区）。
2. 判定锚点可缓存：`store_entities.raw_data_id` 已是「最早可见行」的持久锚点，可按 (店名, 月) 建索引/物化辅助表，避免每次全库分组。
3. 索引补齐：`raw_records(store_name_local_raw, modified_raw)`、`raw_records(clean_status, modified_raw)`、`formal_records(japan_date, person_code)`、`payroll_period_rows(month)` 等（现有唯一约束覆盖了部分查询）。
4. 对账解析复用：一次 `load_workbook` 结果同时供 `parse_daily_records` 与 `attribute_daily`，避免重复解析大文件。
5. 数据归档：历史月 `raw_records`/`recon_data_rows` 冷归档（演示库只保留 7/8 月的做法可泛化为保留策略）。

### 6.3 并发/一致性注意
- **SQLite 本地**：单写者，串行上传/重算时可能 `database is locked`；写路径均为「提交即结束」的短事务，避免长事务。
- **线上 uvicorn `--workers 2` + 线程化对账**：任务在线程中执行且用**独立 `SessionLocal`**（`_task_worker`），与请求会话隔离；但同一 worker 内多任务并发会争抢 DB 连接池（默认 pool），对账任务应保持「一次一个」的运维约定（页面上是人工触发，风险低）。
- **幂等性约定**：`finalize_import`（先删后插）、`rebuild_month`（按天窗口重建）、`sync_period_table`（upsert + 保留 adjust）、`sync_month_stats`（删月重算）、`confirm_adjust`（唯一键幂等）——重复执行安全，是「可以放心重跑」的基础。
- **事务边界**：服务层函数内部自行 `db.commit()`；`run_task` 失败走 `db.rollback()` 后**重新 `db.get(ReconTask)` 再写 failed**（避免读到回滚掉的对象）。

### 7.2 迁移（Alembic）
