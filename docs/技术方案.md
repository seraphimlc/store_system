# 巡店结算系统 · 技术方案

> **状态**：现状｜**最后更新**：2026-10-17｜版本 v1.0（2026-09）
> **一句话**：技术实现与决策（架构/数据模型/流程落地/权衡）。
> 业务流程口径以 `docs/产品设计-系统逻辑全览.md` 为准；基准表与发布流程见 `AGENTS.md`；主流程历史确认稿见 `docs/结算主流程设计-v3.md`。

---

## 1. 概述

- **形态**：FastAPI + SQLAlchemy 2 + Alembic + Jinja2 + htmx 的单体 Web 应用，把「巡店 Excel → 逐行判定 → 申诉/绩效确认 → 正式表 → 绩效工资（月内两期发薪）→ 月度对账（归因 + AI）→ 薪资找平」线上化。本地 SQLite，线上 Docker Compose（PG 16 + uvicorn）+ Nginx HTTPS。
- **技术目标**：每行可解释（判定固化在 `raw_records`，不事后重算）；全程留痕（`appeals`/`payroll_adjusts`/`payroll_payments`/`store_merge_logs`/`recon_tasks.params.replaced_by`）；口径集中在服务层（判重、工资不散落页面）；读写分离（页面读物化表，写路径服务层事务 + 幂等）；可核对（验收 = 与同库 SQL 直查一致，**不钉数字**）；agent 友好（`__PAGE_STATE__` + `data-testid`）。
- **明确不做**：多租户/跨组织权限；消息队列（对账用进程内线程）；SPA（服务端渲染 + htmx）；AI 参与金额/判定（AI 只做解释与表头解析，失败整体回退）。
- **角色三档**：`admin` / `leader` / `staff`。

## 2. 技术栈与架构

| 层 | 选型 | 要点 |
|---|---|---|
| Web / ORM | FastAPI（`app/main.py::create_app`）+ SQLAlchemy 2（`app/db.py`） | 同步路由 + `Depends(get_db)`；`SessionLocal` 全局 sessionmaker |
| 迁移 | Alembic（`alembic.ini` → `migrations/`） | **65 个 revision，head = `ab12cd34ef56`**；线上容器启动自动 upgrade，本地手动 |
| 模板 / 交互 | Jinja2 + htmx（`app/templates/`） | 服务端渲染；POST + 303（PRG），提示走 `?msg=` |
| Excel | openpyxl | `read_only=True, data_only=True` |
| 认证 | argon2（口令）+ itsdangerous（签名 cookie `ss`） | 载荷 `{uid, csrf}`，TTL = `SESSION_TTL_HOURS`（默认 12h） |
| AI | httpx → OpenAI 兼容 `/chat/completions`（`ai_chat.py`） | 失败重试 2 次后抛错，由调用方回退 |
| 数据库 | SQLite（本地）/ PostgreSQL 16（线上） | 曾评估 MySQL 8 并做过兼容适配，**已弃用该路线** |

- **线上拓扑**：`Nginx(443, store.visitworld.me) → web(127.0.0.1:3660) → db(PG16, 127.0.0.1:5433)`；`web` 容器 entrypoint = `alembic upgrade head && uvicorn --workers 2`，挂 `store_uploads`；`db` 挂 `store_pgdata`；**`mcp` 容器不跑迁移**（统一由 `web` 负责）。发布目录 `/opt/store-settle/releases/<TS>` + `current` 符号链接（回滚 = 切链 + `compose up -d`）；生产配置 = `<release>/deploy/.env`（标准副本 `/opt/store-settle/deploy.env`，`chmod 600`）；健康检查 `GET /healthz`（`SELECT 1`，失败 503）。**发布/回滚细节见 `AGENTS.md` §发布流程。**
- **本地**：`./scripts/dev_server.sh`（source `.env`）→ uvicorn `127.0.0.1:8000`；库 `store_settle_live.db`；`app/config.py::Settings` 每字段 `default_factory` 读 env，`get_settings()` 带 `lru_cache`。本地不自动跑 alembic（改模型手动 `create_all`/`ALTER`）。
- **环境变量**（`app/config.py`）：`DATABASE_URL`/`SECRET_KEY`/`SESSION_TTL_HOURS`/`UPLOAD_DIR`/`MAX_UPLOAD_MB`/`ADMIN_USERNAME`/`ADMIN_PASSWORD`/`DEFAULT_STAFF_PASSWORD`/`AI_API_KEY`/`AI_BASE_URL`/`AI_MODEL`/`BONUS_GROUP`/`BONUS_AMOUNT`/`BONUS_GROUP_SCHEDULE`/`BONUS_AMOUNT_SCHEDULE`/`RECON_SYNC`/`AI_AUTO_INTERPRET`。

## 3. 数据模型

| 表 | 职责 | 关键约束 |
|---|---|---|
| `users` | 账号；`role=admin/leader/staff`，staff 经 `person_code` 绑人；`status` active/leave/disabled/resigned；`must_change_password` 首登改密 | `username` 唯一 |
| `imports` | 上传档案：sha256 / 落盘路径 / 解析诊断 / status | `file_sha256` 唯一（同内容拒传） |
| `raw_records` | **原样底账 + 判定结果**（`clean_status`/`filter_reason`/`filtered_by_raw_id`/`confirm_state`） | `(import_id, sheet_name, excel_row)` 唯一 |
| `persons` | 员工档案（`code` 主键、姓名、首见文件） | `code` |
| `formal_records` | **唯一权威绩效依据**：人/店/日本日期/点数/来源 | `raw_record_id` 唯一 |
| `person_daily_stats` | 人×日（店/1点/2点/点数）；对账本地侧与分期点数来源 | `(person_code, ref_date)` 唯一 |
| `month_perf_records` | 月绩效物化（records/p1/p2/points/salary + 锁存 `per_point` + 对账回填 settle/diff） | `(month, person_code)` 唯一 |
| `payroll_period_rows` | 月×人**应发快照**（两期点/额/奖金/店数 + settle/prev/diff 参考 + adjust 执行） | `(month, person_code)` 唯一 |
| `payroll_payments` | **实发台账，不可改写**（金额/点数 + 抵扣 `adjust_applied` + 递延 `adjust_leftover`）；**导出即登记** | `(month, person_code, seq)` |
| `payroll_adjusts` | **找平进度的唯一权威**（原始额 / `settled_amount` / `remaining` + 状态） | `(source_month, person_code)` |
| `payroll_settlement_links` | 发放 ↔ 找平 FIFO 核销关联 | — |
| `adjust_records` | 对账确认的**点数纠偏留痕**（锁存 `per_point`，`applied_to_month=次月`；供 `perf.adjust_map` 计入发生月） | `(source_task_id, person_code)` 唯一（幂等） |
| `recon_tasks` | 对账任务：kind/status / `params`(month,file,kind,path,version,current,replaced_by,single_date,unmatched,result_path) / `summary`(compared,diff_count,sys_only,attribution,ai_interpret,error) | — |
| `recon_data_rows` | 对账文件**全量**人×日（点/行数） | `(task_id, ref_date, person_code)` 唯一 |
| `recon_day_rows` | **只存问题行**：sys/rep points、diff、side | 同上 |
| `recon_results` | 人月差异行（system/report/diff/family） | — |
| `appeals` | 申诉（pending/approved/rejected + 理由 + 处理人/时间） | `raw_record_id` 唯一 |
| `store_entities` / `store_pairs` / `store_merge_logs` | 店铺主从档：主档 `master_id` 自指、从档指向主档，冗余 `master_store_id`/`master_raw_data_id`；候选对 exact/fuzzy；归并留痕 | `store_id_raw` 唯一；`(entity_a, entity_b)` 唯一 |

- **关系**：`imports→raw_records→formal_records`（`raw_record_id` 唯一）；`raw_records→appeals`（1:1）；`formal_records→person_daily_stats→month_perf_records`；`month_perf_records↔payroll_period_rows`（回填 settle/diff）；`recon_tasks→{recon_data_rows, recon_day_rows, recon_results}`；`recon_results→confirm_adjust→adjust_records`（次月生效）；`payroll_period_rows` 的 diff 由 `sync_adjusts` upsert 到 `payroll_adjusts`，再由 `payroll_payments` 经 `payroll_settlement_links` FIFO 冲销；`store_entities.raw_data_id → raw_records`（展示/追溯锚点，判定不依赖主从）。
- **关键枚举**：`clean_status` = valid / master_late / from_sub / cross_file_dup / visible_blank / no_ref；`confirm_state` = pending / approved / disputed / auto_ok / auto_approved；`appeals.status` = pending / approved / rejected（可申诉 `APPEALABLE=(master_late, from_sub)`）；`recon_day_rows.side` = both / local_only / report_only；`payroll_period_rows`：`diff_*` = 系统参考（自动刷）、`adjust_*` = 人工执行（增量累计）。

## 4. 核心流程实现

### 4.1 导入与判定（`importer.py` / `flow.py`）

`POST /files/upload`（管理员 + CSRF）→ `upload_and_store`（仅 .xlsx、≤ `MAX_UPLOAD_MB`、sha256 落盘、同内容拒传）→ `parse_file`（自动识别表头/起始行/列，单事务写 `raw_records` + `persons`；失败 `status=failed` 不半写）→ `process_import`：`sync_store_for_import` → `promote_or_link_entities` → `update_earliest_anchor` → `judge_import` → `ensure_persons`（新编号建 `persons`+`users`，首登改密）。

**判重规则**（`flow._name_month_min` + `judge_import`，勿改）：

| 规则 | 实现 |
|---|---|
| 窗口 | 结算月（`modified_raw[:7]`），跨月行**永不互相压制** |
| 键 | `(店名, 月)`；**2026-09 起店名归一** = `flow._norm_name`（NFKC + 去半/全角空格 + lower），历史月用原始 trim |
| 组内优先级（≥2026-09） | ① `deploy=YES`（→2 点）② `visible ∈ {OTHER, AUDIT_SUCCESS, YES, NO}`（→1 点）③ 其余（→0 点，不入表）；同级取 `modified` 最早。历史月不分优先级，最早即最优 |
| 落败行 · 同一 store | 同日 → `cross_file_dup`（不可申诉）；异日 → `master_late`（可申诉） |
| 落败行 · 不同 store | `from_sub`（可申诉） |
| 空 store_id / 空店名 | `no_ref`（不可申诉） |
| `visible` 非候选 | `visible_blank`（不计点）。候选口径 = 该文件布局 `value_map.visible`（`rules.visible_is_candidate`） |
| 锚点行 | `valid`、`filter_reason=None`、`confirm_state=auto_approved`（自动生效，无需员工确认） |

**点数**：`rules.point_for(japan_date, deploy, boundary=2026-07-09)` —— 日期 ≥ 边界且 `deploy=="YES"` → 2 点，否则 1 点；对账文件带「标准点数」列则以该列为准。

**入表/重算**：`finalize_import`（该文件有 pending 申诉 → 拒绝；否则删本文件 `formal_records` 按 `valid` 重建，**幂等先删后插**，再 `sync_month_stats`）；`rebuild_month`（当月有 pending → 拒绝；对当月全部文件重跑 `judge_import`，把已认可申诉恢复为 `valid`，重建整月后 `sync_month_stats`）。页面：`POST /files/{fid}/finalize`（`valid≠formal` 显示「重新入表(N)」）、`POST /month/rebuild`。

**申诉闭环**：员工 `POST /my/appeal/{raw_id}`（校验 `submitter_code==person_code` 且 `clean_status∈APPEALABLE` → `appeals(pending)` + `disputed`）；管理员 `POST /files/{fid}/appeals/{aid}/resolve`（accept → `valid`/`approved`；reject → `auto_ok` 定案；均留 `handled_by/at`）。

### 4.2 绩效与工资（`perf.py` / `period.py`）

**数据流**：`formal_records` →`sync_month_stats`→ `person_daily_stats` →`sync_month_perf`→ `month_perf_records` →`sync_period_table`→ `payroll_period_rows`（页面读 `half_map`/`half_stats`）。

- `sync_month_stats`：删月重算人×日，末尾串联 `sync_month_perf`。
- `sync_month_perf`：按正式表聚合 upsert；**单价锁存**（该月已有 `per_point` 优先，重物化不冲回 250）；该月已无正式记录的人删行；`rate37 = p2/(p1+p2)` 仅展示。
- **工资**：`salary = 0 if points<=0 else points*per_point + (points//bonus_group)*bonus_amount`；默认 250 円/点、门槛 68、奖额 3000，可按月配（`BONUS_GROUP_SCHEDULE`/`BONUS_AMOUNT_SCHEDULE`，当前 2026-09 覆盖 75 点 / 1250 円）。奖金**整月滚动、不跨月**。
- `month_per_point` 取该月锁存单价（无则 250）；`set_month_per_point`（`POST /perf/per-point`）改写该月 `per_point/salary` 并重算分期；已确认 `adjust_records` 因锁存单价不受影响。
- **两期发薪**（`sync_period_table`）：`h1=Σday≤15`、`h2=Σday≥16`、`b1=(h1//g)*amt`、`b2=((h1%g+h2)//g)*amt`、`half1=h1*pp+b1`、`half2=h2*pp+b2`；同时固化两期店数快照（`half1_records/p1/p2`…），期视图只读快照。导出 `GET /perf/export?period=` **即登记发放台账**（`payroll_payments`）。

### 4.3 月度对账（`recon.py`）

- **生命周期**：`POST /recon/upload2` → `start_task`（落盘、`guess_kind`、登记 pending）→ 同月旧版本标 `replaced/replaced_by`（保留「上一版」）+ 新任务 `version+1` → `launch_task`（daemon 线程 + 独立 Session）→ `run_task` → done/failed。
- **`guess_kind`**：扫全部 sheet 前 12 行表头 → `daily_records`（店+人+日期齐）> `person_points` > `store_list` > `unknown`。
- **解析**：`ai_parse_daily_cols`（前 3 sheet × 14 行预览，模型只返回 JSON 列映射；校验列号范围 + 能定位 `date + store_id + (person_name|person_code)`，否则回退规则）；`parse_daily_records`（sheet 优先「最终有效/有效明细/有效数据」；只计当月；人员优先级 编号 →「姓名(编号)」→ 姓名匹配；未匹配入 `params.unmatched`；点数优先「标准点数」列）；解析出的日期只有 1 个值 → `params.single_date=True`，日级仅参考，**以人月差异为准**。
- **`run_task`**：清旧结果 → 全量写 `recon_data_rows` → 人月差异（`diff≠0` 才写 `recon_results`；反向名单 `summary.sys_only`）→ 日级只写问题行（本地侧 `person_daily_stats`）→ 归因 `attribute_daily`（对账每行按 `(store_id, modified)` 比对正式表 → consistent / only_system / only_report（按 `clean_status` 拆 from_sub/master_late/cross_file_dup/no_ref/not_found）/ net）→ 生成 `uploads/recon_result_<id>.xlsx`（`GET /recon/result` 与 `/recon/report` 同一文件）→ done + `finished_at`；后置 `interpret_task`、`sync_period_table`（失败只回滚、不改任务状态）；异常 → `rollback` + `failed` + `summary.error`。
- **AI**：`interpret_task` 只喂可引用事实（比对/归因/合计/问题行样例/反向名单/标记），四节结构化输出、禁编造数字；`ai_employee_notes` 每差异员工 ≤70 字，缓存 `summary.ai_employee_notes`；未配 `AI_API_KEY + AI_BASE_URL` → 整体降级为纯规则。

### 4.4 薪资找平

| 列（`payroll_period_rows`） | 语义 | 谁写 | 刷新 |
|---|---|---|---|
| `diff_points/amount` | 系统参考：`settle − (h1+h2) + prev` | `sync_period_table`（并 upsert `payroll_adjusts`） | 自动整体刷新，不接受人工写 |
| `adjust_points/amount` | 人工执行累计 | `set_period_values`（增量）/ `confirm_adjust` | 只增不减，默认 0 |
| `prev_adjust_points/amount` | 上月余量**生成时快照**（非权威） | `sync_period_table` | 每次刷新 |
| `settle_points/amount` | 该月当前对账任务的点数与折算金额 | `sync_period_table` | 每次刷新 |

- `sync_period_table`：员工 = 当月 `person_daily_stats` ∪ 对账人员；upsert 只更新系统侧、**保留 `adjust_*`**；回填 `month_perf_records`，按 diff upsert `payroll_adjusts`（进度保留、不重置已找平）。
- `set_period_values`：输入框 = `diff − adj`，保存的是**本次增量** → `adjust_points += delta`（累计制），留 `updated_by/at`。
- `confirm_adjust`（`POST /recon/{id}/adjust/{code}`）：写 `adjust_records`（`amount = 对账点 − 系统点`，锁存当月单价，次月生效），并同步补齐当月 `adjust_points`；`(source_task_id, person_code)` 唯一幂等；`cancel_adjust` 撤销。
- **跨月债务唯一权威 = `period.prior_debt_map()`**：读 `payroll_adjusts.remaining`（`allocate_settlement` 按 FIFO 冲销维护）。`carry_map`、`record_payment` 扣款、各页「上月找平」都走它。⚠️ `prev_adjust_amount` 只是生成时快照，拿它扣钱会**重复扣**（2026-10-17 实测全公司多扣 ¥592,500）；`record_payment` 已改为 `remaining = carry`（不再 `carry + absorbed`）。
- 工资端：`perf.adjust_map` 取 `applied_to_month == month` 的 `adjust_records`，按每条锁存单价折算（纠偏额不随本月单价变化）。

### 4.5 权限与安全

- **会话**：itsdangerous 签名 cookie `ss`（含 `uid` + `csrf`，TTL `SESSION_TTL_HOURS`）；口令 argon2；`must_change_password` → 除 `/my/password*`、`/logout` 外 302 `/my/password?must=1`。
- **员工/队长隔离（第一层）**：`STAFF_ALLOWED`（`LEADER_ALLOWED = STAFF_ALLOWED`）白名单——`/my/{password,confirm,appeal,perf,report,plan,leave,tasks,self-report}`、`/messages`、`/tasks/`（**仅 GET**）、`/static`、`/healthz`、`/login`、`/logout`、`/product`、`/oauth/`、`/.well-known/`；白名单外 → 302 落地页（**无论路由是否自校验都兜底**）；权威列表见 `app/main.py::STAFF_ALLOWED`。
- **管理端隔离（第二层，纵深防御）**：每个管理路由首行 `if user is None or user.role != "admin": return _denied()`。
- **CSRF**：所有写操作表单带 `csrf_token`（会话内比对，失败 400；`logout` 也要）。未登录 → 302 `/login`。资源归属按 `person_code` 过滤（申诉校验 `submitter_code`）。员工 `disabled/resigned` 禁登录，数据与历史记录永不删除。

## 5. 关键技术决策与权衡

| 决策 | 选择 | 理由 | 代价 / 权衡 |
|---|---|---|---|
| 绩效与分期数据 | **物化**（`month_perf_records`、`payroll_period_rows`）而非实时聚合 | 页面只查单表；发薪要「当时口径」的稳定性 | 必须保证物化时机与幂等；物化不全 → 页面与正式表不一致（`/month` 有 `need_rebuild` 检测） |
| 分期店数 | **落库快照**（`half1_records/p1/p2`…） | 发薪单据不能随 `person_daily_stats` 后续变化漂移 | 快照过期需重新 `sync_period_table` |
| 偏差 vs 找平 | **双轨**：`diff_*` 系统参考自动刷 / `adjust_*` 人工执行累计 | 两者是不同事实，必须分别追溯、不能互相覆盖 | 页面须清楚区分（输入框显示剩余量）；误填会累计（增量制 + 留痕兜底） |
| 跨月债务 | **唯一权威 `payroll_adjusts.remaining`**（`prior_debt_map()` 读账表） | 结转链 `prev_adjust_amount` 是快照，会把已扣的再扣一次 | 扣款/页面/绩效三处都必须走 `prior_debt_map()` |
| 单价 | **按月配置 + 发生月锁存** | 单价变更不应回改历史纠偏金额 | 改单价时须明确「历史 adjust 不动」（已固化） |
| 奖金 | 默认 68 点 / 3000 円，**整月滚动不跨月**，可按月配 | 规则可配、口径简单；上半月余点带向下半月，避免月初重置多发 | 奖金须在**整月**点数上算；两期拆分只能用累计差分，不可各期独立整除 |
| AI 角色 | **解释 + 表头解析**，不决策；规则兜底 | 每月表头不同、规则维护贵；不确定性不能污染金额 | 需可信性校验 + 整体回退；解读标注 model/时间存档 |
| AI 可用性 | 自动重试 2 次；未配置 → 静默降级 | 外部 API 抖动不应阻塞主流程 | 无高级退避/熔断；失败只在 `summary`/`msg` 体现 |
| 对账执行方式 | **进程内 daemon 线程**，非队列 | 单机、数十人量级，最简依赖 | 无持久队列/重试；重启后任务停在 pending（可手动重跑） |
| 对账版本化 | 同月重传：旧任务标 `replaced/replaced_by` **保留可查**，新任务 `version+1` | 历史产物可回溯；找平关联不丢 | `_current_recon` 必须排除 `replaced_by` 并取最大 id |
| URL 兼容 | 每条 V3 路由**同时注册无 `/v3` 与 `/v3/*`** | 新链路用短路径；旧书签不 404 | 路由表翻倍；新增路由需成对注册（易漏） |
| 数据库方言 | SQLite（本地）/ PG 16（线上）；MySQL 已弃用 | 本地零依赖、线上稳 | 方言差异显式处理：JSON 用 `sqlalchemy.JSON`；TEXT 默认值 `sa.text("('')")`；唯一键含 TEXT 用 `VARCHAR(255)`；自引用 FK 中间态按 dialect 关校验 |
| 判定固化位置 | 结果写回 `raw_records`（非独立判定表） | 一行一结论，追溯直观；重判即覆盖 | 全库重判成本随文件数线性增长（见 §6） |

## 6. 性能与可扩展

- **量级**：`formal_records` 单月约 1.3–2.3 万行（2026-10 全库 52441 行）；页面只读物化表（数十行），交互无压力。
- **已知全表扫描点**（当前可接受，增长后是热点）：`perf._fetch`（全表取正式表）；`flow._name_month_min`（每次 `judge_import` 扫**全库** `raw_records`，`rebuild_month` 每文件调一次）；`recon.compare_daily`/`attribute_daily`（全表遍历，且 `attribute_daily` 重新 `load_workbook`，与解析重复 IO）；`/month`、`/perf` 现场取月份列表。
- **优化方向（不改口径）**：月过滤下推 SQL；`(店名,月)` 索引/物化锚点；补索引 `raw_records(store_name_local_raw, modified_raw)`、`raw_records(clean_status, modified_raw)`、`formal_records(japan_date, person_code)`；一次 `load_workbook` 复用给解析与归因；历史月冷归档。
- **并发/一致性**：本地 SQLite 单写者（短事务，避免长事务锁）；线上 `--workers 2` + 线程化对账用**独立 `SessionLocal`** 与请求会话隔离，运维约定对账「一次一个」；`finalize_import`/`rebuild_month`/`sync_period_table`/`sync_month_stats`/`confirm_adjust` 均幂等，可放心重跑；`run_task` 失败 `rollback` 后**重新 `db.get(ReconTask)`** 再写 failed。
