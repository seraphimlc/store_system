## 3. 分阶段步骤、阶段目标和验收

### P0 — 补齐生产发布能力与就绪检查

目标：生产使用明确的运行参数，发布失败保持原入口。

- [ ] 只读核实第2节信息，完成schema/路径/私有文件/旧新路由兼容清单。

验收：正式域名全站进入同一新release；只有新系统写入；关键统计与最终备份基线一致；Worker健康；无丢附件、会话异常或地图授权错误。任何未满足项保持冻结或执行回滚，不先解除再补验收。

## 4. 回滚判据与操作矩阵

只要出现资金/权限/数据完整性问题即停止相关写入，不等待错误率阈值。普通故障建议触发条件：核心页面/API持续不可用5分钟、发布后新出现的持续5xx、两端登录/任务入口普遍失败、Worker无法消费且无法快速恢复、业务统计与同库SQL无法解释地不一致。具体阈值在P0根据真实基线确认，不能把低流量下单次请求等同百分比事故。

| 时点/故障 | 应对 | 数据库与队列 |
|---|---|---|
| 构建、上传、候选启动失败，尚未切流 | 终止候选，保留旧入口 | 不动生产DB；候选进程/卷按身份定向清理 |
| 已切入口、尚未放开写入 | 反向切回旧上游，停止新Worker/API | 同一生产DB，不恢复备份；确认旧任务排空状态后恢复旧Worker |
| 已放开新写入，旧代码兼容新记录 | 冻结→排空新事务/任务→备份当前→核对增量→切回旧应用 | **保留同一DB和新合法数据**；新队列封存，未完成任务逐类核对，不能交旧Worker盲跑 |
| 新栈release之间代码回滚 | 优先同DB、同私有文件/队列回退已验收新release | 校验旧镜像支持当前待办类型；不支持则冻结/隔离任务，不能自动丢弃 |
| 发现错误金融写入或数据损坏 | 立即冻结，停止相关Worker，进入事故恢复 | 不直接全库回灌；当前库/文件/队列先快照保全，隔离恢复并核对合法增量 |

### 4.1 应用回滚步骤

1. 开启维护/冻结写入，通知执行人和验收人；记录决定时间、故障、当前release和正在执行任务。
2. 排空新API事务，停止新Worker。超时任务区分未执行/已执行/结果未知；先查requestId/台账/审计，不无条件重试。
3. 备份当前DB、私有文件与队列；确认待回退镜像与当前数据语义兼容。检查新店核实形成的bd_*增量、日报、找平/发薪记录、附件引用，不能删除新合法数据以适配旧代码。
4. 启动已保留的旧Web/待回退新release，连接**当前同一生产DB**；旧Web若入口脚本会自动Alembic，必须使用已确认不会改变schema的恢复方式，不能无审查`compose up`。
5. Nginx还原上一份已验证上游配置，`nginx -t`通过再reload；检查域名/健康/权限/统计/文件。
6. 队列分别恢复：旧业务任务只用旧实现能识别且确认无重复副作用的队列；新任务卷保持封存，不转换成旧任务。未完成任务登记负责人和补偿动作。
7. 回退验证通过后解除旧系统写冻结，只保留一个写入端；需要时用户重新登录。记录回滚后DB/文件/队列位置。

**目标而非承诺**：schema与数据兼容、镜像已保留且无待决事务时，应用回滚争取10分钟内完成；以演练实测值为准。正常应用回滚不丢已提交数据（RPO目标0），数据损坏恢复不作相同承诺。

### 4.2 数据恢复（单独决策）

- 禁止把“回滚”理解成将生产全库恢复到切流前备份；这会丢掉上线后合法日报、巡店、消息、发薪/找平等数据。
- 冻结后先保全当前库、WAL/日志（若已配置）、上传/照片与队列；备份恢复到隔离新库，确认受影响时间、表、行和合法增量。
- 优先按明确主键、requestId、审计和事务边界做可复核的定向修复；金融台账更正必须按既有业务补偿口径处理，不直接覆盖已发台账。
- 只有无法定向修复且完成业务负责人批准后，才评估全库恢复；明确预计数据损失、合法增量补录、文件一致性与停机时间。未配置/验证PITR时不得宣称任意时间点恢复可用。
- 恢复后的库与文件引用、工资/找平/实发一致性、任务分母与历史快照通过同库验证后，再决定恢复哪一个应用。备份可用的RPO/RTO依P2演练填写。

### 4.3 当前本地回滚的特别限制

当前本地新release连接`store_settle`，上一候选c连接`store_settle_refactor_p1`。直接执行旧c的rollback会同时切数据库目标，**不能当作保留新数据的回滚演练**。正式演练须准备“同一隔离DB＋同一私有文件/任务卷”的两个兼容release，再验证双向切换。不能修改旧manifest/runtime伪造曾验收配置。
