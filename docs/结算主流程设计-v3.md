# 结算主流程设计（v3 · 2026-09-08 与万总确认版）

> 本文档记录已与万总逐条确认的结算主流程与实体定义，
> 是后续改造「去重/员工对账/正式表/工资/对账找平」的唯一依据。

## 一、实体（3 个）

| 实体 | 说明 | 不可变 |
|---|---|---|
| raw data | Excel 原样入库，全系统底账 | ✅ 永不改动 |
| 店铺数据 | 分**主档 / 从档**，指向同一真实店铺 | 主/从可人工调整 |
| 正式数据 | 由"有效 raw"组成，**专门算绩效** | 一经入表作绩效依据 |

## 二、店铺数据（主档/从档）

- 主档 `master_id` 自指；从档 `master_id` 指向所属主档。
- 一条店铺记录对应一个 store_id；同一真实店铺可有多个 store_id（主档 + 从档）。
- 店铺表每条带 **raw_data_id** = 该店在原始数据中**最早出现**那条 raw 的 id。
- **从档冗余存两字段**（为后续少一次查询）：
  - 主档 store_id
  - 主档 raw_data_id
- 新增 store_id 处理：店铺表不存在 → 新增记录 → 按店名比对判定主档/从档；
  已存在 → 跳过。

## 三、主流程（按导入文件逐轮执行）

1. **上传 Excel → raw data**（原样入库）。
2. **店铺处理**：遍历本次新增 distinct(store_id)，店铺表不存在则新增并定主/从档。
3. **去重判定**（遍历本次新增 raw，store_id 查店铺表）：
   - 店铺是主档 且 其 raw_data_id == 本条 → **有效数据**
   - 店铺是主档 但 raw_data_id ≠ 本条 → **被过滤**（原因=枚举）
   - 店铺是**从档** → **被过滤**，并标识主档 raw_data_id（原因=枚举）
   - **跨文件同日同店重复 → 自动过滤（原因=数据重复），不进入员工判断**
   - 每条被过滤数据都带过滤原因（枚举）。
4. **员工处理**：遍历本次新增 distinct(员工编号)，不存在则新建
   （登录名唯一 / 员工编号 / 默认密码）。
5. **绩效确认（详见 §七）**：判定后**默认全部认可、不打扰员工**——
   有效记录自动入绩效；被滤(master_late/from_sub)默认已认可滤除；
   重复导入(cross_file_dup)自动滤、员工端不出现。员工只在认为某条
   **被滤错**时主动申诉。管理端「绩效确认」处理申诉并按文件入正式表。
6. **数据入正式表**：有效记录判定后即自动具备入表资格；文件存在**未决
   申诉**时先处理申诉再入表。
7. **入正式表后**生成：员工日绩效表、月绩效表、汇总表、结算工资表
   （管理端可导出 Excel）。
8. **月度完成 → 外来对账 Excel**：与正式表对账，生成对账数据。
9. **先发工资 → 后对账**：对账发现偏差（超发/少发）→
   **下月工资找平**，全程留痕可查。

## 四、点与钱规则（沿用已确认口径）

- 绩效点数 = 1点店数 × 1 + 2点店数 × 2（例：10 条 1点 + 10 条 2点 = 30 点）。
- 1点/2点：分界日 **2026-07-09**。之前一律 1 点；
  当天起 Deploy=YES → 2 点，否则 1 点。
- **37% 店铺成功率 = 2点店 ÷ (1点店+2点店)，仅作员工完成情况展示，与工资无关**。
- 薪资计算为独立模块：以绩效点数为输入套**全局配置**算工资；
  全局薪资配置仅一条——**68 点 = 20,000 円，超过 68 点每点 +250 円**。
  （注：无 60 点概念，此前口误，已更正。）

> 员工确认最终形态见 §七）。

1. 入正式表时机：判定后有效记录自动具备入表资格；有未决申诉先处理再入。✅

## 六、最终判重口径（2026-09 万总裁决，以 8 月基准 Excel 校准）

> 8 月真实数据端到端验证发现：主档+全局最早 raw_data_id 会压错跨月记录；
> 以「8月全月巡回最终结算.xlsx 月度总览」为唯一裁决逐行对齐后定稿如下。

- **判重窗口 = 结算月**：同名店（店名 trim 相同）当月只保留最早一次巡店；
  同店跨月（7 月已巡、8 月再巡）互不压制，各月各自有效。
- 判重键 = (行原始店名 trim, modified 月)；组内 modified 完整时间戳最早一条
  → **有效数据**；其余过滤，原因枚举：
  - 与组内最早同 store 同日 → `cross_file_dup`（数据重复，自动认可、不进员工任务）
  - 与组内最早同 store 异日 → `master_late`（默认认可滤除，可申诉改判有效）
  - 组内其它编号（从档候选）更早 → `from_sub`（默认认可滤除，可申诉改判有效）
- 店名不得 NFKC/去空白归一（ざくろ銀座店 vs ざくろ 銀座店 是两家店）；
  visible_blank 行不参与判重；modified 比较取完整时间戳。
- store 实体主/从档与 raw_data_id 仍维护（实体层，供展示/人工调档/追溯），
  但 judge 判定不再依赖主从关系。
- 本地验证（全量导入 4 文件含 7 月行）：8月 valid 12511、重复 533、
  1点 8231/2点 4280/总点 16791/工资 4,266,750 —— 与基准月度总览逐项全等。

> 备注：当前系统内全部数据为测试数据，改造可直接重算、无需兼容旧数据。

## 七、员工确认 / 绩效确认最终形态（2026-09 定稿）

> 经用户逐点确认后，原「判定任务 + 超时默认认可」「按天逐条认可」均废弃，
> 定稿为**默认全部认可、只留申诉**：有效自动入绩效、被滤默认滤除，
> 员工零操作负担，只在认为某条被滤错时主动申诉。

### 判定 → 记录状态（judge 后即定，无任何"待办"）
- `valid`（当月最早有效）→ confirm_state=auto_approved，**自动计入绩效**，
  员工无需任何操作、员工端不出现。
- `cross_file_dup`（同日同店跨文件 = **重复导入**）→ confirm_state=auto_ok
  自动滤除，员工端完全不出现，仅管理端文件总览的「重复导入」列计数。
- `master_late`（同店跨日疑似重复）/ `from_sub`（从档归并）→
  confirm_state=auto_ok，**默认已认可滤除**（滤除定案），不打扰员工；
  员工如认为该条应算有效，可对其申诉。

### 申诉（按条留痕，appeals 表：raw_record_id unique / reason / status）
- 员工申诉 → AppealRecord(pending)，该 raw confirm_state 置 `disputed`。
- 重复申诉 / 非本人 / 非可申诉类型（如 cross_file_dup）→ 拒绝。
- 管理端处理：**认可** → 该 raw 改判 `valid`（confirm_state=approved，
  下次入表计入绩效）；**驳回** → 维持滤除（confirm_state 回 auto_ok 定案）。

### 员工端（极简、零心智负担）
- 登录落地「**我的绩效**」：本人日/月报表（月份切换；月汇总卡：有效店/1点/2点/
  总点/本月工资/2点占比；每日明细表），数据只来自正式表。
- 「**我的申诉**」：系统已默认全部认可。仅列出本人**被滤且未申诉过**
  （master_late/from_sub）的记录（按天倒序，只显示店铺/原因，无文件、编号、
  raw 等技术信息）；认为哪条被滤错就点申诉填原因；已申诉显示
  待处理/成立(已算有效)/未过(维持滤除)。全清显示 🎉 没有需要申诉的记录。
- 不再有"待确认/认可"列表。

### 管理端「绩效确认」（admin）
- 顶部按员工查看其被滤记录与申诉状态（默认认可滤除 / 申诉待处理 /
  申诉成立·已算有效 / 申诉驳回·维持滤除）。
- 处理申诉：认可 → 该 raw 改判 valid（下次入表计入绩效）；
  驳回 → 维持滤除(auto_ok)。
- 文件总览：有效 / 被滤(默认认可) / 重复导入 / 申诉 / 正式表状态；
  无未决申诉且未入表时可「入正式表」。
- 「绩效工资」页可导出当月结算工资表 Excel（月度绩效·工资 + 日明细，
  合计与基准 12511/8231/4280/16791/4,266,750 一致）。

### 入正式表门槛
文件存在 `pending` 申诉（appeals.status=pending）时拒绝入表——
先处理申诉，认可后该条改判有效一并计入；其余有效行判定后即可入。
