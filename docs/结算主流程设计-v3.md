# 结算主流程设计（v3 · 2026-09-08 与万总确认版）

> **状态**：设计文档（现状）｜**最后更新**：2026-10-17
> **一句话**：结算主流程 v3（与万总逐条确认版，客户交付用）。
> 本文档记录已与万总逐条确认的结算主流程与实体定义，是「去重/员工对账/正式表/工资/对账找平」的依据。
> **数字以系统实时为准**（`/month` 页与 SQL 直查），本文不钉死数字。

## 一、实体（3 个）

| 实体 | 说明 | 不可变 |
|---|---|---|
| raw data | Excel 原样入库，全系统底账 | ✅ 永不改动 |
| 店铺数据 | 分**主档 / 从档**，指向同一真实店铺 | 主/从可人工调整 |
| 正式数据 | 由「有效 raw」组成，**专门算绩效** | 一经入表作绩效依据 |

- 店铺表每条带 `raw_data_id` = 该店在原始数据中**最早出现**那条 raw 的 id；从档冗余存「主档 store_id / 主档 raw_data_id」。新增 store_id：店铺表不存在 → 新增并按店名比对定主/从档；已存在 → 跳过。

## 二、主流程（按导入文件逐轮执行）

1. **上传 Excel → raw data**（原样入库）。
2. **店铺处理**：遍历本次新增 distinct(store_id)，店铺表不存在则新增并定主/从档。
3. **去重判定**（遍历本次新增 raw）：店铺是主档且 `raw_data_id == 本条` → **有效数据**；主档但非本条 → **被过滤**；**从档** → **被过滤**（并标识主档 `raw_data_id`）；**跨文件同日同店重复 → 自动过滤（原因=数据重复），不进入员工判断**。每条被滤数据都带过滤原因（枚举）。
4. **员工处理**：遍历本次新增 distinct(员工编号)，不存在则新建（登录名唯一 / 员工编号 / 默认密码）。
5. **绩效确认（详见 §五）**：判定后**默认全部认可、不打扰员工**——有效记录自动入绩效；被滤(master_late/from_sub)默认已认可滤除；重复导入(cross_file_dup)自动滤、员工端不出现。员工只在认为某条**被滤错**时主动申诉。管理端「绩效确认」处理申诉并按文件入正式表。
6. **数据入正式表**：有效记录判定后即自动具备入表资格；文件存在**未决申诉**时先处理申诉再入表。
7. **入正式表后**生成：员工日绩效表、月绩效表、汇总表、结算工资表（管理端可导出 Excel）。
8. **月度完成 → 外来对账 Excel**：与正式表对账，生成对账数据。
9. **先发工资 → 后对账**：对账发现偏差（超发/少发）→ **下月工资找平**，全程留痕可查。

## 三、点与钱规则

- 绩效点数 = 1点店数 × 1 + 2点店数 × 2（例：10 条 1点 + 10 条 2点 = 30 点）。
- 1点/2点：分界日 **2026-07-09**。之前一律 1 点；当天起 `Deploy=YES` → 2 点，否则 1 点。
- **37% 店铺成功率 = 2点店 ÷ (1点店 + 2点店)，仅作员工完成情况展示，与工资无关**。
- 工资：**每点 ×250 円 + 每满门槛点奖 3000 円**（默认门槛 68；`BONUS_GROUP_SCHEDULE` / `BONUS_AMOUNT_SCHEDULE` 按月可配，如 2026-09 覆盖为 75 点 / 1250 円）；奖金**整月滚动、不跨月**。（无 60 点概念，此前口误，已更正。）

## 四、最终判重口径（2026-09 万总裁决，以 8 月基准 Excel 校准）

- **判重窗口 = 结算月**：同名店当月只保留一次巡店；同店跨月（7 月已巡、8 月再巡）互不压制，各月各自有效。
- 判重键 = （**归一店名**，modified 月）；**2026-09 起店名判重已做 NFKC + 去半/全角空格 + lower 归一**（`flow._norm_name`），历史月沿用原始店名 trim。
- 组内保留优先级（2026-09 起）：① `deploy=YES`（→2 点）② `visible ∈ {OTHER, AUDIT_SUCCESS, YES, NO}`（→1 点）③ 其余（→0 点，不入表）；同级取 modified 完整时间戳最早。历史月取最早。
- 过滤原因枚举：与组内胜出**同 store 同日** → `cross_file_dup`（数据重复，自动认可、不进员工任务）；**同 store 异日** → `master_late`（默认认可滤除，可申诉改判）；**不同 store（从档候选）** → `from_sub`（默认认可滤除，可申诉改判）。
- `visible_blank` 行不参与判重；store 实体主/从档与 `raw_data_id` 仍维护（供展示/人工调档/追溯），但 **judge 判定不再依赖主从关系**。

## 五、员工确认 / 绩效确认最终形态（2026-09 定稿）

> 经用户逐点确认，原「判定任务 + 超时默认认可」「按天逐条认可」均废弃，定稿为**默认全部认可、只留申诉**：有效自动入绩效、被滤默认滤除，员工零操作负担，只在认为某条被滤错时主动申诉。

- **判定 → 记录状态（judge 后即定，无任何「待办」）**：`valid`（当月组内胜出）→ `auto_approved`，**自动计入绩效**，员工端不出现；`cross_file_dup`（同日同店跨文件 = 重复导入）→ `auto_ok` 自动滤除，员工端不出现，仅管理端「重复导入」列计数；`master_late` / `from_sub` → `auto_ok` **默认已认可滤除**，可申诉。
- **申诉**（`appeals` 表：`raw_record_id` unique / reason / status）：员工申诉 → `pending`，该 raw 置 `disputed`；重复申诉 / 非本人 / 非可申诉类型（如 `cross_file_dup`）→ 拒绝。管理端处理：**认可** → 改判 `valid`（`confirm_state=approved`，下次入表计入绩效）；**驳回** → 维持滤除（回 `auto_ok` 定案）。
- **员工端（极简）**：登录落地「我的绩效」（本人日/月报表，月汇总卡：有效店/1点/2点/总点/本月工资/2点占比；数据只来自正式表）；「我的申诉」仅列本人**被滤且未申诉过**（master_late/from_sub）的记录（按天倒序，只显示店铺/原因，无文件/编号/raw 等技术信息），已申诉显示 待处理/成立/未过；全清显示 🎉。**不再有「待确认/认可」列表。**
- **管理端「绩效确认」**：按员工查看被滤记录与申诉状态；处理申诉（认可改判 valid / 驳回维持）；文件总览显示 有效 / 被滤(默认认可) / 重复导入 / 申诉 / 正式表状态，无未决申诉且未入表时可「入正式表」；绩效工资页可导出当月结算工资表 Excel（月度绩效·工资 + 日明细，**合计以实时查询为准**）。
- **入正式表门槛**：文件存在 `pending` 申诉时拒绝入表——先处理申诉，认可后该条改判有效一并计入；其余有效行判定后即可入。
