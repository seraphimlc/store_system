# 生产部署与回滚手册：本地构建 → ZIP → Google Cloud Storage → Docker

更新：2026-11-13（Asia/Singapore）。适用于已经运行 React / NestJS 的生产系统日常发布。

本文规定后续镜像传输统一使用 **Google Cloud Storage（GCS）单个 ZIP**。2026-11-12 集团云分卷仅为历史归档，不再作为日常发布步骤。本文及新增打包上传命令不代表本轮已经上传或发布新版本。

## 2. 一次发布必须满足什么

1. release ID 唯一、不覆盖旧版本，例如 `prod-20261113-login-a`。来源提交和是否有未提交修改写入 manifest；发布范围不能夹带其他 agent 尚未验收的改动。
2. 按影响范围完成检查：纯员工登录文案只需员工端现有类型检查、构建和关键页面；接口/业务逻辑改动需相邻测试和相应构建。现有完整构建命令内部仍会跑全套检查，不需要在调用前再重复跑一遍。
3. 本地 Docker 或开发环境确认需求；生产验收不创建员工、不导入文件、不重算、不导出发薪表、不改密码。发薪导出具有业务写入副作用。
4. 此发布流程不运行迁移、不复制本地库、不修改生产表结构。需要 schema 变更时另作兼容迁移计划，不能顺带执行旧 Alembic。
5. 新旧 API、任务格式与当前数据库兼容；仅一个 Worker 消费正式任务卷。后端升级若无法确定旧任务可读、未完成任务能安全续跑，停在切换前。
6. 旧镜像、旧 HTML、旧 CDN 资源、私有配置和上一版状态可恢复；不在发布期间清理 Docker 镜像或对象。

### 2.0 先提交、再打时间 Tag、再发布（每次必做）

每次发布都必须先将本次范围内的代码、测试和发布说明提交，然后在该提交上创建 annotated tag；禁止从未提交的改动构建发布产物。提交时只暂存本次文件或差异块，不能把其他 agent 的修改一并提交。工作区存在其他修改时，从 tag 对应的已提交源码构建，或从上一正式产物按白名单替换本次已提交文件，并记录复用摘要；不能直接把整个 dirty 工作区打包上线。

Tag 与 release ID 统一为 `prod-YYYYMMDD-HHmmss`，时间使用 **Asia/Singapore（UTC+8）**，例如 `prod-20261113-013045`。精确到秒；同名已存在时重新取时间，禁止覆盖、移动或删除既有 tag。Tag 指向此次发布源码提交，不指向之后的验收记录提交。失败的发布保留 tag 并记录失败；重做产物或修改源码必须另建提交及新 tag。

```bash
# 先审查并提交此次范围；不要使用 git add . 或 git add -A
# 只按需要列出此次文件，或用 git add -p 暂存独立差异块
git diff --cached --check
git diff --cached --stat
git commit -m "说明本次发布的实际改动"
RELEASE="prod-$(TZ=Asia/Singapore date +%Y%m%d-%H%M%S)"
git tag -a "$RELEASE" -m "Production release $RELEASE"
git show --no-patch --format=fuller "$RELEASE"
```

若用户或其他 agent 已提交本次全部改动，无需制造空提交，核对该提交后直接打 tag。发布 manifest、上传回执关联记录和服务器验收记录都必须记录 `releaseTag`、tag 解析出的完整 `sourceCommit`、实际生效组件及复用组件版本；构建前后核对 tag 指向未变化。发布完成后向用户报告 tag、commit、发布结果和回滚点。仓库若配置了远端，在用户授权推送的范围内同步提交和 tag；本地已打 tag 不代表已推送，须明确区分。

### 2.1 发布前先确定最小范围（每次必做）

比较基准必须是**上一实际部署版本的源码快照及产物manifest**，不能只用HEAD或上一个Git提交替代。若该版本是dirty构建，应结合留存的源码差异/构建上下文与资源摘要确认；无法确认基准时先查清，不能将未知改动一并上线。

核对已提交差异、暂存/未暂存差异、新文件，以及共享包、依赖锁文件、构建配置和API契约的影响；排除其他agent未验收修改。发布前简要列出“变更文件 → 受影响组件 → 必须替换的产物”，并记录复用的旧产物摘要。

| 本次实际改动 | 最小构建/发布范围 | 保留内容 |
|---|---|---|
| 仅文档、发布工具 | 文档或对应工具；无需发布网站 | 全部业务容器与静态资源 |
| 仅员工端展示 | 员工端JS/CSS/HTML、新Gateway镜像；ZIP仅包含新Gateway镜像 | 管理端HTML/资源、API/Worker镜像与容器及生产配置 |
| 仅管理端展示 | 管理端JS/CSS/HTML、新Gateway镜像；ZIP仅包含新Gateway镜像 | 员工端HTML/资源、API/Worker镜像与容器及生产配置 |
| 共享前端包/主题 | 按真实依赖关系构建受影响前端及Gateway | 未受影响的后端 |
| API/Worker业务、依赖或契约 | 按调用/共享镜像关系确定服务，执行后端交接与兼容验收 | 未受影响的前端资源和持久数据 |

前端单端更新时，从上一正式产物复用另一端HTML与资源地址，不能为了新release ID顺带重建另一端。当前API和Worker共用同一镜像，是否需要同时替换/重启应依据共享实现和任务兼容性判断，不能机械只看文件所在目录。

**当前工具限制**：`release:build`仍是全量构建，`release:bundle pack`当前要求API与Gateway完整包；它们是后文完整发布路径，不能直接冒充最小发布能力。执行前端小改发布前，需要先支持对应的组件选择与增量manifest/单Gateway ZIP，或按可审查的人工步骤制作等价产物；不能因工具默认全量而扩大本次发布范围。此处记录要求，不表示增量构建器已经实现。

例如当前员工登录欢迎语调整：只发布员工端与Gateway，管理端、API、Worker和数据库均保留；同时修改的部署文档/上传工具不构成重启业务服务的理由。

## 3. 本地构建正式产物

以下命令在项目根执行。凭证保存在已有未跟踪环境文件中，不写进命令参数、manifest或文档。

```bash
export RELEASE=prod-20261113-login-a  # 每次换成新的唯一 ID

pnpm release:build -- --env local --assets cdn \
  --platform linux/amd64 --release "$RELEASE" --config .env.next.docker.local
```

该命令完成隔离测试、类型检查、应用构建、两个镜像构建和 `images.tar.gz`。产物位于 `.release/$RELEASE/`；构建失败不能拿残留目录发布，修复后使用新 ID。

注意：Apple Silicon 上的 amd64 正式产物不能直接通过当前本地原生平台 deploy 校验。日常本地8000验收使用原生镜像，正式包使用同一份已验收源码；上线前还需检查 amd64 原生依赖加载及候选健康。不要把本地 runtime.env 上传服务器。

### 3.1 确保生产 Gateway 保留 HTTPS 语义

当前通用 Gateway 模板也供本地 HTTP 使用；生产 Gateway 在外层 TLS Nginx 后面，必须向 API传递 `X-Forwarded-Proto https`，并使用 Secure Cookie。不要把本地 HTTP 豁免带到生产。

现有构建器没有独立 production 配置阶段，因此先调整**新产物目录**的 Gateway 配置，再重建该镜像及归档；不修改已经发布的目录。执行下列准备块，随后才做 ZIP：

```bash
python3 - <<'PY'
import os,json,subprocess,gzip,shutil
from pathlib import Path
r=os.environ['RELEASE'];d=Path('.release')/r
p=d/'gateway-context/default.conf';text=p.read_text()
old='proxy_set_header X-Forwarded-Proto $scheme;'
new='proxy_set_header X-Forwarded-Proto https;'
if old in text:text=text.replace(old,new)
if new not in text:raise RuntimeError('核对当前 Gateway 的 forwarded-proto 实现后再继续')
p.write_text(text)
m=json.loads((d/'manifest.json').read_text())
subprocess.run(['docker','buildx','build','--load','--platform','linux/amd64',
 '-t',m['images']['gateway'],str(d/'gateway-context')],check=True)
for name,tag in m['images'].items():
 image=json.loads(subprocess.check_output(['docker','image','inspect',tag]))[0]
 if image['Os']!='linux' or image['Architecture']!='amd64':raise RuntimeError('镜像架构错误')
 m['imageDigests'][name]=image['Id']
with gzip.open(d/'images.tar.gz.tmp','wb') as target:
 proc=subprocess.Popen(['docker','image','save',*m['images'].values()],stdout=subprocess.PIPE)
 try:shutil.copyfileobj(proc.stdout,target)
 finally:proc.stdout.close()
 if proc.wait()!=0:raise RuntimeError('镜像归档失败')
(d/'images.tar.gz.tmp').replace(d/'images.tar.gz')
(d/'manifest.json').write_text(json.dumps(m,indent=2)+'\n')
print('生产 Gateway 和镜像摘要已准备')
PY
```

前端-only更新也必须保留原有 API/Worker的生产配置。**仅构建出新镜像不代表应当重启 API/Worker。**

### 3.2 本地原生依赖检查

涉及 API/Worker 的发布，在新 amd64 镜像中检查实际使用的 `argon2`、`sharp`等依赖可加载，并运行相应健康/业务检查。可沿用首次上线时的原生依赖 smoke 脚本；没有通过就不发布。本文不把“amd64 镜像构建成功”当成“所有原生模块运行正常”。

## 4. 上传前端资源、打 ZIP、上传 GCS

### 4.1 配置

复用已有以下变量：

```dotenv
NEXT_OSS_PROVIDER=gcs
STORE_FILES_OSS_BUCKET=visitworld-assets
STORE_FILES_OSS_ENDPOINT=
STORE_FILES_CDN_BASE=https://cdn.visitworld.me
# OSS_ACCESS_KEY_ID、OSS_ACCESS_KEY_SECRET：已有 GCS HMAC 凭证，不在这里填写

```

区域默认 `asia-northeast1`，端点留空会选择 `https://storage.googleapis.com`。若设置 `NEXT_OSS_*`，它们优先于 `STORE_FILES_*`，需要核对没有遗留的集团云/阿里云配置覆盖。命令不会调整桶权限、CORS或生命周期。

该桶已配置公开读取；镜像对象也可公开下载，因此**ZIP只包含指定的公开发布产物**。不能将整个 `.release/<id>/`、`.env`、runtime-private.json、Compose私有环境配置、数据库备份或容器 inspect 导出压进包。

### 4.2 命令

```bash
# 先让新HTML将引用的JS/CSS/字体全部可用，按生产Origin核对CORS与内容摘要
NEXT_OSS_PROVIDER=gcs NEXT_PUBLIC_ORIGIN=https://store.visitworld.me \
  pnpm release:bundle -- assets --release "$RELEASE"

# 只打包 images.tar.gz、筛选过的manifest.json、SHA256SUMS
pnpm release:bundle -- pack --release "$RELEASE"

# 流式上传单个ZIP到独立私有GCS桶，校验本地摘要和远端metadata/大小
export NEXT_RELEASE_BUCKET=你的私有发布桶  # 与公开前端资源桶不同，必须 enforced 公共访问防护
NEXT_OSS_PROVIDER=gcs pnpm release:bundle -- upload --release "$RELEASE"
```

`release:bundle`默认读取根 `.env` 与 `.env.next.local`。如果凭证仅放在其他文件，可显式使用同一脚本，例如：

```bash
node --env-file-if-exists=.env --env-file-if-exists=.env.next.local \
  --env-file=.env.next.docker.local scripts/release-bundle.mjs upload --release "$RELEASE"
```

产物：

- `.release/$RELEASE/images-$RELEASE.zip`：单个ZIP，内层镜像已gzip，不再重复压缩。
- `.release/$RELEASE/bundle.json`：ZIP字节数、SHA256、内层镜像归档摘要和架构。
- `.release/$RELEASE/bundle-upload.json`：公开下载URL、对象Key和上述校验信息；不包含HMAC。

对象Key带 release 和完整SHA256。相同包重复上传校验后复用；远端同Key内容不一致则拒绝。上传失败不执行生产切换，可重跑upload；命令不会把失败自动标成发布成功。

## 5. 服务器下载、校验、导入

先用SSH建立新目录，复制**不含凭据的上传回执**，不要复制本地环境文件。下列命令在本地执行：

```bash
ssh visitworld "install -d -m 700 /opt/store-next/releases/$RELEASE"
scp ".release/$RELEASE/bundle-upload.json" \
  "visitworld:/opt/store-next/releases/$RELEASE/bundle-upload.json"
```

然后进入服务器：

```bash
ssh visitworld
sudo -i  # 若SSH本身已是root则无需执行
export RELEASE=prod-20261113-login-a  # 与本地完全一致
export NEXT_RELEASE_BUCKET=你的私有发布桶  # 必须与上传回执一致，并已配置授权读取身份
```

下载及解压使用固定文件白名单，先核对完整ZIP再导入Docker：

```bash
python3 - <<'PY'
import os,json,hashlib,subprocess,zipfile,shutil
from pathlib import Path
r=os.environ['RELEASE'];d=Path('/opt/store-next/releases')/r
record=json.loads((d/'bundle-upload.json').read_text())
if record['release']!=r or record['platform']!='linux/amd64':raise RuntimeError('版本/架构错误')
bucket=os.environ['NEXT_RELEASE_BUCKET']
uri=record['uri']
if record['bucket']!=bucket or not uri.startswith('gs://'+bucket+'/store-next/releases/'+r+'/'):
 raise RuntimeError('下载地址不属于配置的私有发布桶')
p=d/record['file'];tmp=d/'download.tmp'
subprocess.run(['gcloud','storage','cp',uri,str(tmp)],check=True)
def sha(path):
 h=hashlib.sha256()
 with path.open('rb') as stream:
  for b in iter(lambda:stream.read(1024*1024),b''):h.update(b)
 return h.hexdigest()
if tmp.stat().st_size!=record['size'] or sha(tmp)!=record['sha256']:raise RuntimeError('ZIP校验失败')
tmp.replace(p)
with zipfile.ZipFile(p) as z:

  raise RuntimeError('ZIP内容不合规')

  with z.open(name) as source,(d/name).open('wb') as output:shutil.copyfileobj(source,output)

if m['id']!=r or m['platform']!='linux/amd64':raise RuntimeError('manifest版本错误')
print('ZIP与镜像归档校验通过')
PY
cd "/opt/store-next/releases/$RELEASE"
sha256sum --check SHA256SUMS
docker load -i images.tar.gz
```

加载后将 `docker image inspect` 的 `.Id`与manifest的 `imageDigests`逐个比较，并核对 `.Architecture=amd64`；任意不一致即停止。导入镜像不会自动更新正在运行的容器。

## 6. 日常更新的稳定运行目录和发布前快照

以下为**人工执行步骤**，不是新增的一键升级脚本。逐段执行、检查退出码，不将多个变更藏进一条不检查结果的命令。

### 6.1 识别当前生产，不凭容器名称猜测

服务器执行：

```bash
cat /opt/store-next/production-state.json
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
```

从当前正式 Gateway 的Compose标签取得真实项目名和配置位置，不打印容器环境变量：

```bash
# 首次日常更新时当前容器为下列名称；以后以docker ps确认
export GATEWAY=store-next-prod-20261112-gateway-1
export PROJECT=$(docker inspect --format '{{ index .Config.Labels "com.docker.compose.project" }}' "$GATEWAY")
export OLD_COMPOSE=$(docker inspect --format '{{ index .Config.Labels "com.docker.compose.project.config_files" }}' "$GATEWAY")
printf 'project=%s\ncompose=%s\n' "$PROJECT" "$OLD_COMPOSE"
```

本文只处理单一JSON Compose文件。确认标签不为空、只有一个配置文件、项目为当前正式项目后继续。**不新建另一个独立的正式Compose项目**，否则API DNS别名/端口/Worker可能冲突。

### 6.2 切换前备份

```bash
export SNAPSHOT="/opt/store-next/backups/$RELEASE"
install -d -m 700 "$SNAPSHOT"
# 确认本次目录无旧操作快照，避免覆盖一份已有回滚点
[ ! -e "$SNAPSHOT/state.before.json" ]
cp -a /opt/store-next/production-state.json "$SNAPSHOT/state.before.json"
cp -a "$OLD_COMPOSE" "$SNAPSHOT/compose.before.json"
cp -a /etc/nginx/conf.d/store.conf "$SNAPSHOT/nginx.before.conf"
```

将当前Compose的`env_file`解析为相对于`OLD_COMPOSE`的绝对路径；API/Worker都应使用同一生产runtime.env。将这份文件以600权限复制为`$SNAPSHOT/runtime.before.env`，不能复制本地配置，不能在日志里输出文件内容。

**仅前端发布**不会执行数据库写入，不要求每次重做首次迁移的备份恢复演练。**包含后端行为改动**则应先取得本次数据库快照，并确认有既有恢复演练记录：

```bash
docker exec deploy-db-1 pg_dump -U store_settle -d store_settle \
  -Fc --no-owner --no-acl > "$SNAPSHOT/database.before.dump"
# 必须检查上一条退出码、文件大小和pg_restore --list可读取，再继续
chmod 600 "$SNAPSHOT/database.before.dump"
```

备份不上传公开GCS桶。`pg_dump`可用不等于已验证任意时间点恢复。

### 6.3 首次日常更新建立稳定运行目录

不可变release目录只存产物；日常修改的Compose和私有运行配置放 `/opt/store-next/runtime/`。第一次将旧Compose原样复制到这里，将各服务`env_file`改为稳定目录内的绝对路径，保留其他字段。此处**不能改变**：

- `$PROJECT`，它继续使用当前正式Compose项目名；
- `jobs`的external name `store-next-prod-jobs`；
- `database`的external network `deploy_default`；
- private网络、API服务名和127.0.0.1:8000映射；
- 历史上传只读挂载、资源限制、健康检查、Worker命令；
- 生产数据库、会话密钥、Secure Cookie以及`NEXT_WORKER_RECONCILE=false`。

可以使用以下准备块复制稳定配置（已持有发布锁，且`OLD_COMPOSE`、`SNAPSHOT`均已确认）。所有私有内容只在服务器内部复制，不输出：

```bash
python3 - <<'PYCODE'
import os,json,shutil
from pathlib import Path
source=Path(os.environ['OLD_COMPOSE']).resolve();snapshot=Path(os.environ['SNAPSHOT'])
c=json.loads(source.read_text());runtime=Path('/opt/store-next/runtime')
runtime.mkdir(mode=0o700,exist_ok=True);os.chmod(runtime,0o700)
envs=[]
for service in ['api','worker']:
 files=c['services'][service]['env_file']
 if len(files)!=1 or not isinstance(files[0],str):raise RuntimeError('需人工核对env_file配置')
 envs.append((source.parent/files[0]).resolve())
if envs[0]!=envs[1]:raise RuntimeError('API与Worker配置源不同')
shutil.copy2(envs[0],snapshot/'runtime.before.env');os.chmod(snapshot/'runtime.before.env',0o600)
shutil.copy2(envs[0],runtime/'runtime.env');os.chmod(runtime/'runtime.env',0o600)
for service in ['api','worker']:c['services'][service]['env_file']=[str(runtime/'runtime.env')]
p=runtime/'compose.json';p.write_text(json.dumps(c,indent=2)+'\n');os.chmod(p,0o600)
print('稳定运行配置已准备，未启动容器')
PYCODE
```

复制后的私有配置必须700目录/600文件；`docker compose -p "$PROJECT" -f /opt/store-next/runtime/compose.json config --quiet`通过。后续发布直接使用此稳定文件。仅准备文件不运行`up`，所以尚未切流。

```bash
export COMPOSE=/opt/store-next/runtime/compose.json
```

从第6节准备快照之前即需持有`/opt/store-next/deploy.lock`独占锁（例如进入`flock /opt/store-next/deploy.lock bash`后设置并export上述变量），不能和其他发布、首次迁移脚本并行。锁应覆盖配置准备、切换、验收和失败恢复，退出该shell才释放。

## 7. 切换分两类

### 7.1 只有前端页面、文案和样式变化

例如员工登录欢迎语这次改动，采用此路径：

1. GCS/CDN资源已全部上传并验证，ZIP已导入并核对镜像ID。
2. 修改稳定Compose的 **gateway.image** 为新manifest的Gateway tag。API/Worker镜像、环境变量、卷、项目名均不变。
3. 验证新Gateway内Nginx配置，并执行：

```bash
docker run --rm --entrypoint nginx "store-next-gateway:$RELEASE" -t
docker compose -p "$PROJECT" -f "$COMPOSE" up -d --no-deps gateway
```

4. 检查Gateway健康/页面/响应头；GET `/api/health/ready`应成功。API/Worker容器ID应与更新前一致。
5. 两端页面与新版本号通过后才更新production-state。字段应区分`current`（当前前端release）、`apiRelease`（实际API/Worker版本）、`composeProject`和`composeFile`，不能把混合部署误记为所有组件都升级。

替换Gateway有短暂重建窗口，**当前Compose方式不承诺零中断**。不需要为登录文案暂停Worker、停止数据库或回灌数据。

### 7.2 包含API/Worker的业务或依赖变化

除了第7.1的检查，还必须：

1. 先验证新API/Worker兼容当前schema、历史任务格式、当前任务卷和旧客户端请求；确认本次不含迁移。后端候选验证使用隔离恢复库/独立队列，不能让候选Worker消费正式卷。
2. 宿主机Nginx临时开启维护入口，返回503并带`Retry-After`；保留TLS、ACME和独立`/yamanote/`。以备份为基准修改，`nginx -t`成功才reload；不能用会丢失嵌套location的简单正则替换整站。
3. 排空已有请求与事务；确认任务无running项，或有经过验证的安全恢复机制。维护页只阻挡新请求，不等于已有导入/发薪事务已结束。
4. **先停止旧Worker，再停止旧API**；等待正常退出。若超时/任务状态不明，停止升级并恢复旧入口，不直接kill后宣称安全。
5. 对有业务写入风险的版本，在写冻结后补一份最终数据库备份；记录正式任务卷文件、任务状态和上传文件位置。保持卷不变。
6. 修改稳定Compose的api/worker镜像为新manifest的API tag、gateway镜像为新Gateway tag。启动API、确认健康和同库只读查询正常，再启动唯一Worker、Gateway：

```bash
# 服务名api、worker、gateway；停止前先完成上面的排空条件
# Compose里worker使用profile，因此启动时显式启用
docker compose -p "$PROJECT" -f "$COMPOSE" --profile worker stop -t 60 worker api
# 此处完成镜像配置替换，确认runtime.env仍是生产配置
docker compose -p "$PROJECT" -f "$COMPOSE" up -d --no-deps api
# 必须等api容器health=healthy，再执行以下两条
docker compose -p "$PROJECT" -f "$COMPOSE" --profile worker up -d --no-deps worker
docker compose -p "$PROJECT" -f "$COMPOSE" up -d --no-deps gateway
```

7. 内部健康和Worker检查通过后恢复原生产Nginx路由，测试配置并reload；进行公网验收。任何阶段失败按第9节恢复。

## 8. 验收和完成标记

服务器基础检查：

```bash
curl -fsS http://127.0.0.1:8000/api/health/ready
curl -fsS https://store.visitworld.me/api/health/ready
curl -fsSI https://store.visitworld.me/ | head -20
curl -fsSI https://store.visitworld.me/admin/ | head -20
docker compose -p "$PROJECT" -f "$COMPOSE" --profile worker ps
```

确认响应头 `X-Store-Release`是新Gateway版本。Nginx reload/容器重建后允许有限次数重试；不能以某一次旧连接成功掩盖仍在返回旧版本。对真实业务请求不要自动重试具有写入副作用的操作。

浏览器关键验收按本次范围：

- 登录页、中文/日文切换、欢迎语/布局；既有账号登录和路由跳转。
- 管理端和员工端均可打开，JS/CSS/字体无404、MIME或CORS错误。
- 本次更新相关页面；纯样式不重复跑全部业务闭环。
- 涉及后端时核对权限、只读统计/明细、Worker心跳及无重复消费者；不能为验收而导出发薪表。
- CDN旧版本资源仍在；新开页面用新HTML，原有打开页面仍可加载旧chunk。

仅在验收成功后原子更新 `/opt/store-next/production-state.json`：保留旧字段，记录`current`、`previous`、`apiRelease`、`composeProject`、`composeFile`、`updatedAt`及备份目录。将effective Compose（私有）及公开manifest分别保存到本次release记录中；其中私有文件仅服务器保存。

验收日志应包含release、来源commit、ZIP与镜像摘要、实际生效镜像、检查结果、时间、操作者以及回滚点。不要写入会话Cookie、口令、HMAC或数据库密码。

## 9. 失败处理与应用回滚

### 9.1 什么情况回滚

- 新Gateway打不开、静态资源不可用、登录被破坏；
- API无法健康、权限或核心业务口径错误；
- Worker无法恢复/重复消费、持久卷挂载错误；
- 生产配置误连本地或其他库、Secure Cookie失效。

CDN上传或ZIP下载/校验失败时尚未切流，**不需要回滚生产**，保留旧入口并修复产物链路。

### 9.2 前端回滚

1. 取本次`$SNAPSHOT/compose.before.json`中的原Gateway镜像tag/ID。
2. 只把稳定Compose的gateway.image改回该镜像，原API/Worker不动。
3. 执行`docker compose -p "$PROJECT" -f "$COMPOSE" up -d --no-deps gateway`。
4. 核对旧版本响应头、两端页面及原CDN资源可访问。
5. 恢复上一版production-state；记录本次失败release和原因，不删除失败包。

这不会修改数据库，不需要恢复数据库备份。通常只需一次Gateway重建与验收；具体耗时取决于就绪速度。

### 9.3 API/Worker回滚

1. 重新打开维护入口，停止接收业务写入；排空请求和事务。
2. 停新Worker，确认停止消费，再停新API。保留正式任务卷、上传文件和上线后的合法数据。
3. 核对旧API/Worker仍能读当前数据库与新产生的任务/文件；若任务结构不兼容，保持维护，不能直接启动旧Worker处理未知任务。
4. 将稳定Compose和runtime.env恢复为切换前快照。快照里若使用相对路径，先解析并改成稳定运行目录绝对路径；复用相同项目、数据库网络和`store-next-prod-jobs`。恢复镜像tag后同时校验旧镜像ID。
5. 先启动旧API并确认健康，再启动唯一旧Worker和旧Gateway，恢复Nginx原配置并`nginx -t`、reload。
6. 公网、权限、关键查询和Worker状态通过后恢复旧production-state，并补记失败版本和原因。

**正常应用回滚保留当前数据库，不执行pg_restore。** 用户已提交的日报、巡店、消息、工资/找平台账以及新上传文件不能随应用版本一起倒退。严禁`docker compose down -v`、清理正式卷或把切流前全库备份覆盖回生产。

如果新代码已写入旧代码无法理解的数据，应用回滚并不自动安全。先保全现场、保持维护，再评估定向修复或兼容补丁。

### 9.4 数据损坏恢复：单独的事故流程

数据库备份用于事故恢复，不是每次回滚命令的参数。发生数据损坏时：冻结写入 → 备份当前库和新文件/队列 → 将历史备份恢复到隔离库 → 确认受影响表、时间范围及合法增量 → 审核定向修复。全库回灌必须明确数据损失、增量补录与停机方案并单独批准；未验证PITR不承诺任意时间点恢复。

### 9.5 退回旧Python系统的特别限制

`production-release.py rollback prod-20261112`是首次迁移保留的紧急工具，目标为旧Python，不是上一版NestJS。日常升级后，不能把它当作通用rollback按钮。只有重新确认当前数据/队列兼容、保全新上传文件并决定退回旧系统时，才按[首次迁移计划](../docs/计划-生产迁移与回滚.md)执行。不能手动unpause旧Web/MCP造成双写。

## 10. 保留、清理和时间预算

- 至少保留当前版、上一稳定版和当前观察期内需要的发布产物、Docker镜像与资源。清理前根据production-state及实际容器核对；不设置会自动删除正在使用对象的桶生命周期。
- 当前HTML由Nginx提供，不长期缓存；有哈希的JS/CSS/字体按不可变资源保留。发布通常无需全站刷新CDN，不能复用同名文件覆盖旧内容。
- 后续若使用私有镜像桶，应单独配置服务账号/签名下载方案。本流程只使用已有公开桶，HMAC留在本地，不传给生产下载机。
- 缓存正常时，前端更新的构建、上传、Gateway替换和验收可按约5～15分钟安排；全量镜像包或网络较慢时可能更久。包含后端更新另加任务排空、备份和业务验收时间，不能仅按上传时长预估。首次运行稳定目录/人工流程应留额外操作时间。
